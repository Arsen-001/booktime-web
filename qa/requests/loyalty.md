# Запросы раздела loyalty (не мои файлы — прошу владельцев)

## journal: нужен хост расширения «окно оплаты визита» (пачка b04, 24.09.2026)

F-06-063…067, F-06-074, F-06-096…098, F-06-123, F-06-083/084 (реферальная скидка при оплате) и
F-06-073 (мобильное приложение бизнеса) по ТЗ живут в отдельном окне «Оплата визита» — со строками
оплаты, плитками способов оплаты («Акция», «Наличные», «Банковские карты», «Сертификат/абонемент»),
удалением строки оплаты корзиной и итогом «К оплате». Сейчас такого окна/хоста в приложении нет:
`bookingWindow` — это окно СОЗДАНИЯ/РЕДАКТИРОВАНИЯ записи (лобби, время, клиент, услуги), а не оплата;
`BookingDraft` несёт только необязательный `total`, без построчной структуры оплаты.

Без отдельного хоста «paymentWindow» (или расширения текущего `bookingWindow` построчной структурой
оплаты + списком применённых скидок/списаний с возможностью удаления строки) раздел loyalty не может
1:1 построить: применение скидки по акции как способ оплаты, несколько карт подряд, частичное
списание бонусов, оплату сертификатом/абонементом по коду, отмену оплаты лояльностью, рефералку при
оплате.

Что сделано в разделе loyalty БЕЗ этого хоста (компромисс на эту пачку):
- `bookingWindow:loyalty` показывает клиенту доступные карты/абонементы/сертификаты с балансами
  (F-06-061, F-06-193) — только чтение, витрина «чем можно заплатить», без интерактивных плиток;
- после сохранения записи в статусе «Клиент пришёл» с непустой суммой начисляется кэшбэк на карты
  клиента автоматически, идемпотентно по `bookingId` (F-06-070) — но это ОДНОСТОРОННЕЕ начисление, не
  через плитку оплаты, и без строки скидки/списания, которую можно было бы удалить.

Прошу: когда journal спроектирует окно оплаты (или строчную структуру `BookingDraft`), завести хост
`paymentWindow` (или расширить `bookingWindow`) с пропсами: строки оплаты (тип, сумма, ссылка на
источник — promotionId/certificateId/membershipId/referral), `onAddLine`/`onRemoveLine`, итог
«К оплате». Раздел loyalty достроит F-06-063…067, 074, 083/084, 096…098, 123 поверх него.

F-06-073 (мобильное приложение Altegio Business) — в проекте нет отдельного мобильного приложения
для бизнеса (веб-кабинет — наш основной кабинет мастера по решению F-00 из ТЗ), поэтому пункт
неприменим без отдельного проекта/раздела «приложение»; не мой запрос — фиксирую как открытый вопрос
для решений проекта, не для правки чужого файла.

## Обновление (пачка b04, починка 1, 25.09.2026): движок построен, свой interim-UI тоже

Хоста «оплата визита» у journal/finance по-прежнему нет (при этой починке в дереве уже видно, что
journal начал `src/areas/journal/components/booking-window/PaymentSheet.tsx` и читает
`@/api/loyalty` — это то самое место, где приведённые ниже функции пригодятся).

Чтобы не ждать хоста ещё одну пачку, `bookingWindow:loyalty` теперь сам — интерактивная панель
`src/areas/loyalty/components/LoyaltyPaymentPanel.tsx`: плитки акций (F-06-063/064, скидка каждой
следующей — от уже уменьшенного остатка), списание бонусов целиком/частично (F-06-065, «Разделить
оплату»), витрина сертификатов/абонементов держателя + поиск ЛЮБОГО сертификата/абонемента бизнеса по
коду (F-06-067/096/098/123 — именные не находятся, у них `code=''`), реферальная скидка по телефону
приглашающего с проверкой «впервые в бизнесе» (F-06-083/084), «Отменить оплату лояльностью» после
сохранения записи (F-06-074). Применённые строки коммитятся в реальные балансы шагом «после
сохранения» записи (`registerAfterSave`) — они переживают перезагрузку.

Это ПОДМЕНА настоящего окна оплаты, а не хост: плитки — свои (не «Наличными»/«Банковской картой» —
эти способы не наши), сумма «К оплате» не связана с реальной кассой journal/finance, и когда
появится `paymentWindow`, весь UI-слой (`LoyaltyPaymentPanel`) можно будет заменить на тонкую обвязку
вокруг движка. Сам движок — новые функции в `src/api/loyalty.ts` — рассчитан на переиспользование ЛЮБЫМ
хозяином окна оплаты, без переделки:

- `listApplicablePromotions(businessId, clientId, remaining)` — акции держателя, применимые к остатку
  чека (discountFixed/discountAccumVisits/discountAccumSum; discountConditional — n-я услуга — НЕ
  посчитана, там нужен состав визита, а не сумма — ❓/assumed, следующей пачке).
- `getBonusChargeInfo(businessId, cardId, remaining)` — максимум списания бонусов (лимиты типа карты
  F-06-026/027 + баланс + остаток).
- `findLoyaltyByCode(businessId, code)` — сертификат/абонемент ЛЮБОГО клиента бизнеса по коду (именные
  не находятся, истёкшие/погашенные — тоже).
- `getReferralEligibility(businessId, referrerPhone, inviteeClientId, remaining)` — рефералка: активна
  ли программа, приглашённый впервые ли, у пригласившего есть ли карта нужного типа; ❓ ТЗ не говорит,
  что если карты нет — assumed: не начисляем (см. reason `referrerNoCard`).
- `commitLoyaltyPayment(businessId, locationId, bookingId, clientId, lines)` /
  `reverseLoyaltyPayment(businessId, bookingId)` — коммит и полный откат строк оплаты (балансы карт,
  сертификатов, абонементов, реферальный бонус); идемпотентно по `bookingId`
  (`state.paidBookingIds`, срез `loyalty`, версия 5).
- `getLoyaltyPaymentSummary(businessId, bookingId)` — уже проведённая оплата лояльностью визита (для
  «Отменить»).

Плюс: `Membership` (`src/domain/loyalty.ts`) получил поле `code?: string` — раньше `sellMembership`
принимал код в форме продажи, но нигде его не сохранял (абонемент нельзя было найти по коду вообще);
теперь сохраняется и проверяется на уникальность, как у сертификата.

Прошу: когда появится реальный хост «Оплата визита», вызывать эти функции напрямую вместо
`LoyaltyPaymentPanel` — сигнатуры стабильны, менять буду только с уведомлением здесь.
