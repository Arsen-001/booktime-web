## 2026-09-25 · 1. Абонементы, сертификаты и карты — одна правда для салона и приложения (major, новое)
- Цепочки: C27.S2, S3, S4, S6; C21.S1, S3, S4.
- Что не так. Раздел loyalty построен и хозяин этих сущностей по AREAS. Приложение клиента держит свои копии:
  `client.memberships`, `client.certificates`, `client.cashbackCards`, `client.membershipTemplates`, `client.certificateTemplates`,
  `client.membershipUsedForBooking`. Результат:
  - абонемент у салона «Безлимит на месяц 3/11», в приложении «5 массажей спины 1/5»;
  - сертификат, погашенный клиникой, в приложении «12 000 ֏»;
  - в приложении 3 бонусные карты, у салонов — ни одной;
  - выставленный на продажу онлайн тип клиенту не виден;
  - купленное в приложении салон не видит.
- Что именно:
  1. Функции чтения loyalty для приложения, которые отдают DTO (без CRM-полей):
     - `listClientMemberships(appUserId)`, `listClientCertificates(appUserId)`, `listClientCards(appUserId)` — по номеру
       пользователя через карточки клиента во всех бизнесах (`findClientByPhone` / `ensureClientForAppUser`);
     - `listOnlineSaleItems(businessId)` — типы с `onlineSale.enabled`.
  2. Команда продажи из приложения: `sellMembership` / `sellCertificate` с `appUserId` (карточка по номеру, как `placeBooking`),
     один `request()`.
  3. Приложение переходит на них. Срезы client удаляются: строка в «Хозяева сущностей» уже есть, в ней `waitlist`,
     теперь сюда же membership/certificate/cards.
  4. Оплата визита абонементом (C21.S5) — вклад loyalty в окно записи, списание визита — той же сущностью.

## 2026-09-25 · 2. Оплата визита — одна команда finance; «оплачено» везде одно (major, новое)
- Цепочки: C28.S2–S5, C25.S4b, C25.S6, C01.S14.
- Что не так. «Оплатить» в окне записи (journal) пишет только `journal.extras.paidAmount`: без способа оплаты и без операции finance.
  Окно после оплаты по-прежнему «К оплате 5 000 ֏ · Посещение не оплачено». Выручка дня — два числа:
  сводка журнала 5 000 ֏, финансы 82 000 ֏. Карточка CRM сама себе противоречит («Оплачено 5 000 из 5 000» и «Должник»).
  Приложение показывает выдуманные оплаты.
- Что именно:
  1. Команда finance `payVisit(bookingId, { method, amount, accountId? })` — синхронная, для `coreTx`. Она создаёт операцию
     «Оплата услуг» (`refId` = запись, клиент, мастер, способ) и, для карты, комиссию эквайринга, как в сиде.
     Возврат — `refundVisit`.
  2. Чтение для всех: `getVisitPayment(bookingId)` → `{ total, paid, method, status }`. Его читают:
     - окно записи;
     - «Историю визитов» и суммы карточки clients;
     - приложение клиента (DTO: итого, оплачено, способ, без касс);
     - payroll и reports.
  3. Сводка дня журнала (F-01-011) — `getDayCashSummary`. После перехода удалить `BookingExtras.paidAmount`
     (AREAS «Хозяева сущностей»: «оплачено» — finance).

## 2026-09-25 · 3. Окна для картинок и каталога — одна функция (major)
- Цепочки: C22.S0 (новое), C18.S4 (повтор).
- Что не так. Запись к Ани сегодня предлагает 15:45, 16:00, 16:30, 17:45. В то же время:
  - картинка сторис «на сегодня» пишет «свободных окон нет», и её нельзя опубликовать;
  - карточка мастера показывает ближайшие окна только с воскресенья;
  - в «Свободно рядом» Ани нет.
- Что именно: картинка сторис, карточка мастера, «Свободно рядом» и `/book` берут окна одной функцией —
  `getNearestSlots` / `freeSlots` из schedule поверх ядра. Своих расчётов в `api/client.ts` не заводить.

## 2026-09-25 · 4. Палитра из склада — функция чтения stock для приложения (major, новое)
- Цепочка: C01.S5.
- Что именно: `listShadeOptions(businessId, locationId, serviceId)` в stock. Это товары-оттенки с остатком > 0, без просрочки,
  с «показывать клиентам» (F-00-143, F-00-140, F-00-144). Ответ — DTO: название, цвет, «под заказ». Связь «услуга → категория
  оттенков» — в карточке услуги (services) или в техкарте (stock).
  Приложение показывает «В наличии» только по этой функции.
