# Просьбы раздела «resources» к общему

## 2026-09-26 · b01-fix1 · `resourcesAvailable` (schedule/slots.ts) сравнивает id ресурса с id экземпляра

- Зачем: измеритель нашёл (пачка b01, F-16-001/008/011/012) — `resourcesAvailable()` в `src/api/schedule/slots.ts`
  (`used = core.bookings.filter(b => ... b.resourceIds.includes(res.id))`) считает `b.resourceIds.includes(res.id)`,
  где `res` — `Resource` (id самого ресурса, «Кабинет 1»), а `Booking.resourceIds` хранит id **экземпляров**
  (`res.instances[].id`, «Кресло №1», «Кресло №2» — так решает ручной выбор в окне записи, F-16-013, и мой
  автоподбор `pickFreeInstances`/`pickFreeResourceInstances`, который я подключил в этой пачке к
  `booking-flow.ts`/`online.ts`/`EventCreateScreen.tsx`). Id ресурса никогда не совпадает с id его экземпляра →
  `used` всегда 0 → `resourcesAvailable` всегда возвращает true → виджет продолжит предлагать окна, где нужный
  ресурс на самом деле занят (F-02-070, F-16-012 «в каталоге не должно быть ложного свободного окна»).
- Что именно (не мой путь — `src/api/schedule/**` принадлежит разделу `schedule`, AREAS.md):
  `if (!b.resourceIds.includes(res.id))` → `if (!b.resourceIds.some((id) => res.instances.some((i) => i.id === id)))`.
- Пока жду: я нашёл и не правлю (чужой файл). Занятость самой записи (`instanceBusy`,
  `checkInstancesFree` в `src/domain/resources.ts`) и её подключение к созданию записи (`booking-flow.ts`,
  `online.ts`) я в этой пачке уже почин­ил — третья запись на ресурс с 2 экземплярами теперь блокируется
  РЕАЛЬНО (планировщик записи проверяет занятость экземпляров сам, `checkSlot`/`resourcesAvailable` в
  `slots.ts` — это отдельный, более ранний фильтр «какие окна вообще ПОКАЗЫВАТЬ клиенту», и он до правки
  выше остаётся дырявым: покажет окно, которое сама запись потом всё равно отклонит с `resource_unavailable`
  (не тихая дыра, но плохой UX — клиент увидит ошибку после выбора времени, а не отсутствие слота).
