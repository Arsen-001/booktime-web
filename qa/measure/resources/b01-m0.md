## Дефекты

### Дефект 1 — BLOCK — ресурсы никогда не занимаются автоматически, и фильтр окон по ресурсам фактически мёртв
**Затронуты:** F-16-001, F-16-008, F-16-011, F-16-012 (все пункты «Готово, когда» про автоматическое ограничение).
**Метод:** чтение кода (не воспроизведено кликами — записал явно).

- `src/areas/resources/extensions/BookingWindow.tsx:32` — `const selected = draft.resourceIds ?? [];` — у новой записи всегда пусто, пока администратор сам не откроет «+ Добавить» и не выберет экземпляр вручную. Нигде при выборе услуги её `resourceIds` не подставляются автоматически.
- `src/domain/rules/booking-flow.ts` (`planBooking`, вызывается и из журнала, и из виджета через `placeBooking`) и `src/domain/rules/busy.ts` (`checkSlot`) — ни разу не упоминают `resource`/`resourceIds`: доступность ресурса при СОХРАНЕНИИ записи не проверяется вообще, ни для журнала, ни для онлайн.
- `src/api/online.ts:793` — прямая онлайн-запись создаётся с `resourceIds: []` явным литералом — ресурс никогда не резервируется даже формально.
- `src/api/schedule/slots.ts` (`resourcesAvailable`, вызывается из `computeFreeSlots`) — единственное место, где вообще есть логика лимита по ресурсу: считает `used = count(bookings, b => b.resourceIds.includes(res.id))`. Поскольку ни один путь создания записи не заполняет `resourceIds` (кроме ручного выбора администратором в каждой отдельной записи), `used` всегда равен фактическому числу записей, где администратор вручную это сделал, а не реальной занятости кресла/кабинета — то есть онлайн-виджет физически не может заблокировать 3-ю запись на солярий, если только КАЖДАЯ из первых двух записей не была вручную довооружена ресурсом администратором в журнале (для клиента, который сам записался онлайн, это структурно невозможно — клиент вообще не видит поле «Ресурсы», F-16-015).

**Как воспроизвести:** создать услугу с привязанным ресурсом на 1 экземпляр → записать онлайн (или из журнала, не трогая поле «Ресурсы») двух разных клиентов на то же время → виджет/журнал не покажет конфликт, 3-я запись тоже пройдёт беспрепятственно, хотя по ТЗ (F-16-001) она обязана быть невозможна.

**Почему не «уже покрыто b02+»:** F-16-011/012 — прямые пункты пачки b01, а не follow-up; это ядро смысла всего раздела «Ресурсы» («чтобы нельзя было записать больше клиентов, чем есть мест» — из собственного подзаголовка `/biz/resources`).

### Дефект 2 — major — новый участник группового события всегда помечен «другой посетитель»
**Затронуты:** F-16-051 (частично F-16-047, F-16-050 — не в списке b01, но проявляется на том же экране).
**Метод:** live-сценарий (`qa/scenarios/resources/resources-b01-participant.json`) + подтверждение чтением кода.

При добавлении участника в `AddParticipantSheet` (в `EventWindowScreen.tsx`) поля «Записывает другого посетителя» / `visitorName` в форме нет вообще — только имя, телефон, места, комментарий. Тем не менее `addParticipant()` (`src/api/resources.ts`) передаёт `client: { phone, name }` в `placeBooking`, а `planBooking` (`src/domain/rules/booking-flow.ts:288`) вычисляет:
```
const visitorName = input.visitorName ?? (who?.phone ? who.name?.trim() || undefined : undefined);
```
— то есть при отсутствии `input.visitorName` (а его всегда нет — поля нет в форме) `visitorName` подставляется из ИМЕНИ САМОГО НОВОГО КЛИЕНТА, а не остаётся пустым. `ParticipantRow` показывает бейдж «другой посетитель», если `booking.visitorName && client` — оба условия всегда истинны для только что созданного участника.

**Живое воспроизведение:** `qa/shots/resources-b01-scenario2/…after-add-2-full.png` — оба добавленных участника («Тест Тестов», «Второй Клиент», оба — новые самостоятельные клиенты, чекбокс «посетитель» никто не отмечал) несут синий бейдж «другой посетитель».

**Эффект:** администратор не может отличить настоящего «посетителя, записанного под чужим номером» (F-16-050) от обычного нового участника — метка на экране всегда врёт.

## Разное, замечено попутно (не в счёте checked/passed выше — не входит в список пунктов «Готово, когда» b01)

- **Ложная тревога, НЕ дефект.** Первый прогон `/biz/groups/events/new?lang=ru` при параллельном (`concurrency: 3`) замере показал 544 ошибки консоли «Router action dispatched before initialization» на ru и 0 на en. Пересняв тот же URL изолированно (`--concurrency 1`), получил 0 ошибок. Это HMR-гонка дев-сервера между параллельными вкладками измерителя, а не баг приложения — см. `qa/shots/resources-recheck1/report.json`.
- **Персона `master` (рядовой сотрудник) открывает `/biz/resources` по прямому URL** и видит полный список ресурсов (`qa/shots/resources-b01-perm/biz-resources__master…`), хотя в её боковом меню пункта «Ресурсы» нет. Правило F-16-002 требует права «Ресурсы» у администратора — для мастера доступ, видимо, не должен быть открыт вообще, но соответствующего явного правила в b01 нет (это F-16-026 «Права на ресурсы», НЕ входит в пачку b01) — фиксирую как наблюдение, не завожу как дефект b01.
- Персона `owner` со `--sphere fitness` НЕ переключает реальный бизнес на фитнес-салон (business выбирается по паре `kind === 'salon'`, а Арман — `kind: 'individual'`), поэтому групповые функции по умолчанию нужно смотреть под персоной `individual` — учтено во всех сценариях выше, но стоит знать при повторных замерах этого раздела.
