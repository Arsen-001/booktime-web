## Найденные дефекты

### 1 (major) — `/platform/connect`, шаг «Название»: ложная ошибка валидации при быстром заполнении

**Что видно:** поле «Название» содержит корректный текст (например, «Race Test 1»), но клик «Далее» сразу
после заполнения показывает красную рамку и «Укажите название» — прогресс блокируется, хотя поле явно не
пустое.

**Причина (по коду `ConnectScreen.tsx`):** `Input` для названия — неконтролируемый (`defaultValue`),
сохраняется только по `onBlur` → `patch({ name })`, а `patch` асинхронный (`await save.mutate(...)` + сетевая
задержка мока 150–400 мс). `goNext()` при клике «Далее» проверяет `draft.name` из замыкания рендера — то
есть **старое** значение, пришедшее ДО того, как асинхронное сохранение успело долететь и обновить `draft`
через `q.refetch()`.

**Как воспроизвёл (5 независимых прогонов сценариями `measure.mjs`, все одинаково):**
1. Заполнить «Название» (`fill`).
2. Сразу (0–200 мс) кликнуть «Далее» — **ошибка**, поле подсвечено красным, шаг не открывается.
   Повторный клик через 100 мс — тоже ошибка (значит не «сработает со второго раза», а нужна именно пауза).
3. Тот же клик, но после `Tab` (блюр) + пауза 1500 мс перед «Далее» — **проходит нормально**, шаг 2 открывается.

Значит нужна пауза ~0.5–1.5 с после ввода имени, иначе мастер (единственный вход в главную функцию раздела,
F-00-176, «за 10 минут на визите») даёт пользователю ложное «заполните поле», хотя оно заполнено. На живом
визите с некрупным экраном/тормозным интернетом это будет происходить регулярно — человек наберёт название и
тут же ткнёт «Далее».

**Снимки:** `qa/measure/platform/shots-m0/race1/…result-1.png` (ошибка сразу после fill+click),
`qa/measure/platform/shots-m0/race-wait/…wait-result.png` (успех после паузы).

**Кого касается:** F-00-176 (пункт «Готово, когда»: «за 10 минут… салон заведён»). Функция как таковая
работает (все 7 шагов есть, «Готово» создаёт бизнес), но первый же шаг фейлит нормальный темп ввода — это
не косметика, это ломает ровно тот сценарий, ради которого раздел построен.

**Смежный риск (не проверял отдельно, тот же паттерн кода):** остальные поля шага 1 («Имя владельца»,
«Телефон», «Район», «Адрес») используют тот же `onBlur`-паттерн без ожидания сохранения — если пользователь
быстро сменит несколько полей и уйдёт со страницы/закроет вкладку до того, как последний `patch()` долетит,
правка может не долететь до мока. Не подтверждено измерением (не гонял), фиксирую как гипотезу для строителя.

### 2 (minor) — `/platform/moderation`, телефон: вкладки обрезаются без явного намёка на прокрутку

На 390 px вкладки «На проверке / Одобрено / Отклонено / Без проверки / Причины отказа» не помещаются в
строку; при переходе на последнюю вкладку строка прокручивается влево и обрезает начало текста соседней
вкладки («…юнено» вместо «Отклонено») без видимой fade-подсказки о том, что строка скроллится. Не мешает
работе (можно скроллить пальцем), но выглядит как обрезанный текст. Снимок:
`qa/measure/platform/shots-m0/scenario7/…reasons-tab.png`.

### 3 (minor, наблюдение) — `/platform` Обзор под `?api=error` молча показывает нули вместо ErrorState

На широком прогоне с `?api=error` все счётчики на «Обзоре» (ждут проверки/перезвонить/обращения/…) тихо
показали «0» вместо состояния ошибки — в отличие от остальных 9 страниц раздела, которые корректно показали
`ErrorState` «Не удалось загрузить» + «Повторить». Для панели, которую открывает один и тот же человек
каждый день, нули вместо ошибки могут читаться как «сегодня всё спокойно», хотя на самом деле сервер
недоступен. Не блокирует ни одну функцию из пачки — фиксирую как minor. Снимок:
`qa/measure/platform/shots-m0/err/platform__platform-nails-ru-light-desktop.png`.

### Блокер этого захода — не по разделу platform

В середине повторной проверки `/platform` начал стабильно отвечать `500` на **всех** маршрутах (не только
platform — это общий layout). Причина — синтаксическая ошибка в чужом файле-фундаменте
`src/domain/schedule.ts:19`, который принадлежит разделу `schedule`, не `platform`:

```
/** Ключ в messages/*/schedule.json → dayTypes.* */
```

Комментарий `/** ... */` закрывается досрочно на первом же `*/` внутри пути `messages/*/schedule.json`,
дальше `schedule.json → dayTypes.* */` парсится как код → `Parsing ecmascript source code failed` на
уровне Turbopack, 500 на каждой странице приложения (`tsc --noEmit src/domain/schedule.ts` подтверждает:
6 ошибок парсинга начиная с колонки 19:25).

Файл не в путях этого раздела (`src/app/platform/**`, `src/areas/platform/**`, `src/domain/platform.ts`,
`src/mock/slices/platform.ts`, `src/api/platform.ts`, `messages/*/platform.json`, `qa/**/platform*`) —
это правка чужого фундамента текущей параллельной сессией раздела `schedule`. Не трогал файл, не чинил,
только ждал (curl-опрос `/platform`, ~10+ минут, `Monitor`-ожидание `200`) — за это время сервер не
восстановился, поэтому финальный живой скриншот дефектов 2 и 3 после починки не переснят в этом заходе;
статическое чтение кода (`ConnectScreen.tsx`, `OverviewScreen.tsx`, `ModerationScreen.tsx`) подтверждает,
что все три патча из `platform-b01-fix1.md` реально лежат в файлах и соответствуют описанию, не просто
заявлены в отчёте.

**Итог circle m1:** 1 из 3 дефектов переподтверждён живым сценарием (major, самый важный — F-00-176), 2
из 3 переподтверждены чтением кода (minor). Полного повторного прогона всей пачки из 24 пунктов «Готово,
когда» в этом заходе не делал — блокер (чужой файл) снял возможность живых замеров прежде, чем дошёл до
широкого прогона; круг m0 выше (48 страниц, 0 ошибок) остаётся последним полным живым прогоном пачки.
