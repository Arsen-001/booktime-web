## Дефекты

### 1. major · Новый тип карты у сети создаётся с пустым «Действует в локациях» — вопреки собственному умолчанию кода
- **F-id:** F-06-021 (умолчания формы), структурно ломает F-06-023 (списание бонусов только в отмеченных локациях)
- **Где:** `/biz/loyalty/card-types/new`, персона `network` (несколько филиалов)
- **Что видно:** комментарий в коде (`CardTypeFormScreen.tsx:100`) гласит: «Значения по умолчанию для
  нового типа: все локации отмечены сразу, чтобы не создать тип «без локаций» по невнимательности». На
  экране — чекбокс локации у нового типа **не отмечен**. Сохранил тип без изменений — после сохранения и
  перезагрузки (просмотр как «Тип карты», не форма создания) чекбокс всё ещё пуст: значение реально
  записалось пустым, это не баг рендера.
- **Причина (инференс по коду):** `CardTypeFormScreen` грузит `allLocationIds` через свой `locationsQ` и
  передаёт в `CardTypeFormBody` пропом; но ранний `return` с скелетоном стоит только под условием
  `isEdit && …` — для НОВОГО типа (`isEdit=false`) `CardTypeFormBody` монтируется немедленно, до того как
  запрос локаций успел ответить, и `useState(initial?.locationIds ?? allLocationIds)` фиксирует `[]`
  безвозвратно (эффекта, досылающего локации после ответа запроса, нет).
- **Почему важно:** у одноадресного бизнеса (persona `owner`) поле вообще не показывается, поэтому баг
  невидим в самом частом случае — но у сети (`network`) новый тип карты по умолчанию нигде не действует:
  бонусы можно накопить, но негде списать (F-06-023), пока владелец не заметит и не отметит локации вручную.
  Это ровно та ошибка «по невнимательности», которую умолчание должно было предотвратить.
- **Снимки:** `qa/shots/loyalty-b02/network/biz-loyalty-card-types-new__network-nails-ru-light-desktop__network-locations-field.png`
  (чекбокс пуст на форме создания), `…__network-created.png` (тот же пустой чекбокс уже на экране правки
  после сохранения — то есть в сохранённых данных).

### 2. minor · Подтверждение удаления типа карты с выданными картами грамматически рассогласовано (ru)
- **F-id:** F-06-030
- **Где:** `messages/ru/loyalty.json:445`, ключ `cardTypeForm.deleteConfirmTextCount`
- **Что видно:** для 44 карт диалог показывает «У 44 клиентов есть эта карта — они **будет удалена**
  вместе с накопленными бонусами» — подлежащее «они» (мн. ч., про клиентов/карты) не согласовано со
  сказуемым «будет удалена» (ед. ч., ж. р., про одну карту). Строка технически работает (число и смысл
  верны), но режет глаз носителю.
- **Как чинить:** глагол должен быть внутри самого ICU-плюрала (для `one` — «она будет удалена», для
  `few/many/other` — «они будут удалены»), а не общим хвостом после `{…}`.
- **Снимок:** `qa/shots/loyalty-b02/delete/biz-loyalty-card-types__owner-nails-ru-light-desktop__confirm-dialog-with-issued-count.png`

### 3. minor · Шумное предупреждение консоли при удалении типа карты со страницы правки
- **F-id:** F-06-030
- **Где:** `/biz/loyalty/card-types/[typeId]` → «Удалить тип» → подтверждение
- **Что видно:** после успешного удаления (тост «Тип карты удалён» показан, переход на список случился)
  в консоли остаётся предупреждение `[api] запрос не удался ["loyalty","cardType",…] ApiError: not_found` —
  видимо, фоновый повторный запрос той же карточки (`getCardType`) успевает выстрелить до размонтирования
  компонента и получает «не найдено», потому что запись уже удалена. UI не ломается, но это шум в консоли
  на ровном месте.
- **Снимок/источник:** `qa/shots/loyalty-b02/delete/report.json` → `results[0].console.warnings[0]`.
