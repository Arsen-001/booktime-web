## 🔴 Главный вывод: панель оплаты лояльностью визуально работает, но её результат некому сохранить

С прошлого измерения (`b04-m0`) в `src/areas/loyalty/components/LoyaltyPaymentPanel.tsx` (423 строки, отсутствовал
на момент m0) раздел `loyalty` сам построил интерактивную панель оплаты внутри своего вклада в хост
`bookingWindow` — плитки акций, бонусных карт («Списать бонусы» / «Разделить оплату»), поиск сертификата/абонемента
по коду, блок рефералки. Комментарий в файле объясняет, почему это здесь: «journal/finance пока не спроектировали
построчный хост „Оплата визита“» — задокументированное решение раздела, не тайный костыль.

**Реальным кликом** (не по коду) проверено: открыл запись клиента «Мариам Петросян» (владелец — «Нуне Шахбазян», карта
«Постоянный гость» 3000 ֏, применима акция «Скидка постоянному гостю» −800 ֏), вкладка «Лояльность» → клик по плитке
акции → строка добавилась, «К оплате» упало с 8000 до 7200 ֏ → клик «Списать бонусы» → вторая строка, «К оплате»
упало до 4200 ֏. Арифметика верна (F-06-063, F-06-065 — see таблицу). Скриншоты
`qa/shots/loyalty-b04-m1/scenario1/1-tab-open.png`, `…/2-lines-applied.png`.

**Но:** кнопка «Сохранить изменения» в подвале окна записи **осталась задизейблена** после применения обеих строк
лояльности — проверено `saveBtn.isDisabled()` → `true`. Причина в коде хозяина (`src/areas/journal/components/
BookingWindow.tsx`, строка 1392): `disabled={isEdit ? !touched || !canEditNow : !canEditNow}` — `touched` ставится
только правкой полей, которыми владеет `journal` (статус, услуги, комментарий и т. п.), а клик по плитке лояльности
этот флаг не трогает. Контракт вклада (`src/extensions/saveHooks.ts`) даёт только `registerBeforeSave`/
`registerAfterSave` — способа сказать хозяину «у меня есть несохранённые изменения, включи кнопку» в контракте нет
вообще. Это не имитация — я реально дождался состояния кнопки после реальных кликов.

Проверил обходной путь: тронул поле «Комментарий» (`textarea`) — кнопка включилась (`isDisabled() → false`), но
сохранение упёрлось в **отдельную** валидацию «Заполните обязательные поля: Дата согласия на обработку данных» —
это уже не про лояльность, а про обязательное поле согласия на этой конкретной тестовой записи/бизнесе (владелец
поля — не `loyalty`). Довести до реального `commit` (транзакция в истории, кнопка «Отменить оплату лояльностью»)
в отведённое время не успел — переоткрыл окно после (неудачной) попытки сохранения и увидел, что лояльность
вернулась в исходное состояние («К оплате 8000», без применённых строк) — то есть **применение лояльности
в принципе нигде не переживает переоткрытие окна записи без успешного сохранения хозяина**, а успешное сохранение
недостижимо без стороннего изменения плюс (в этом кейсе) без ещё одного обязательного поля не по теме лояльности.

**Вывод по всей пачке:** визуальная/счётная часть панели построена корректно и соответствует ТЗ по каждому пункту,
который я мог кликнуть, — но ни один `commit` (F-06-063 второй пункт «переживает сохранение», F-06-065, F-06-070,
F-06-074, F-06-083, F-06-096…098, F-06-123) физически недостижим через обычный поток «открыл запись → применил
лояльность → Сохранить», потому что кнопка сохранения не видит изменений вклада. Это новый, подтверждённый действием
дефект уровня **block**, отдельный от находки `b04-m0` «оплаты не было вообще» — теперь оплата ЕСТЬ, но не
коммитится в обычном потоке.

## 🔴 Второе препятствие: localStorage переполнен на каждой странице (0 из 76 сохранений)

Полный прогон `measure.mjs` (76 страниц) показал **на 100% страниц** (76 из 76) предупреждение консоли:

```
[mock-db] не удалось сохранить в localStorage QuotaExceededError: Failed to execute 'setItem' on 'Storage':
Setting the value of 'bp-mock-db' exceeded the quota.
```

Проверил отдельно: на **свежем профиле браузера** (`localStorage` пуст, `Object.keys(localStorage) === []`) первая
же попытка записи уже валится по квоте — значит дело не в «накопили за месяц использования», а в том, что весь
сид (`src/mock/db.ts`, «база большая» по собственному комментарию) физически больше лимита `localStorage` (обычно
5–10 МБ) уже при старте. Это не код `loyalty` (файл общий, не в путях раздела), но напрямую убивает пункт «Мерь:
сохранение после перезагрузки» для КАЖДОЙ функции этой пачки — прямо сейчас ничего, вообще ничего, не переживает
`location.reload()`, потому что снимок в `localStorage` никогда не записывается успешно. Внутри одной сессии без
релоада стор в памяти (zustand) исправен — мутации видны сразу (см. пример с 8000→4200 выше), теряется только
персистентность между перезагрузками/вкладками.

Это системная находка уровня «сообщить оркестратору/core», не дефект кода `loyalty` — путь `src/mock/db.ts` не мой.
