### 1. Окно записи: клиент — первым, короткий путь «клиент → услуга → Записать» (major, F-01-037, F-01-055/056, F-01-063/064, F-00-004)

**8 статусов** → Услуги/Товары → К оплате + «Оплатить» → и только **в самом низу** Телефон/Имя/Email. Постоянного клиента

натыкается на пять неисправностей (все проверены на снимках):

- **Поиск клиента по номеру не работает вообще.** Подсказка под полем обещает «Ищите по последним цифрам номера», но на
  «0017» и на «700» подсказок нет (`d03-new-phone-typed.png`, `e03-search-last-digits.png`); по имени «Мил» — есть
  (`e04-search-by-name.png`). Причина (по коду, проверено): `PhoneInput` отдаёт значение с префиксом — `"+374700"`,
  `ClientZone` кладёт его в поиск целиком, `searchClientsForBooking` берёт цифры `374700` и ищет их в местных 8 цифрах номера.
  Как: в `ClientZone.tsx` — `setQuery(v.replace(/^\+374/, ''))`, либо в `searchClientsForBooking` отрезать ведущие `374`
  у `digits`.
  ✅ исправлено (b03) — `searchClientsForBooking` теперь снимает код страны `374` с цифр запроса.
- **Первая услуга не меняет длительность записи.** Добавил «Маникюр классический · 45 мин» — запись осталась 10:00–11:00
  (`d05b-filled-scroll-1.png`); на телефоне «Укрепление ногтей гелем · 2 ч» сохранилось как 10:00–11:00 (`q04-service.png` →
  `q05b-after-save.png`). В `BookingWindow.tsx` `setDurationMin((prev) => prev + (serviceLines.length === 0 ? 0 : …))` —
  у первой услуги длительность не берётся. Как: первая услуга **заменяет** длительность на свою
  (`serviceLines.length === 0 ? service.durationMin : prev + service.durationMin`), если человек не менял длительность руками.
  ✅ исправлено (b03) — первая услуга заменяет длительность своей.
- **Кнопка «Создавать записи»** — неверная форма глагола (ключ `window.save.create`). Как: «Записать» (коротко, под большой

  ✅ исправлено (b03) — кнопка «Записать»/«Сохранить»/«Записать без клиента» (`window.save.create`).

  ✅ исправлено (b03) — подсказки скрываются, когда клиент выбран (полная карточка с крестиком «сменить» — ⏳ позже, отдельная задача редизайна окна).

### 2. Даты по-прежнему считаются по UTC — а теперь окно записи создаёт записи **на вчера** (major, F-01-009/013/043)

Главное №1 из ux-r1 не исправлено (`JournalToolbar.tsx`, `toISOString().slice(0, 10)`): стрелка «Следующий день» не листает
(«пятница, 25» → «пятница, 25»), «Сегодня» открывает «четверг, 24 сентября» (журнал шагов `ux-r2-log.txt`, первая строка).
Новое последствие b02: окно берёт дату из шапки, и после «Сегодня» «Новая запись» предлагает **24 сентября 2026**
(`d01-new-window-scroll-1.png`, `d08-expanded-tile.png`) — администратор записывает клиента на вчерашний день и не замечает
этого, потому что дата в окне — третье поле сверху и выглядит как любое другое.
Как: в `JournalToolbar.tsx` — `toISODate(parse(date).add(delta * (view === 'week' ? 7 : 1), 'day'))` и `today()` из
`@/lib/date`; по всему `src/areas/journal/**` не использовать `toISOString()` для дат (проверить `grep -rn toISOString src/areas/journal`).
Плюс защита на будущее: если дата записи в прошлом — в строке «когда» (см. №1, п.1) красная метка «вчера» / «в прошлом»,
а кнопка — «Записать задним числом».
Снимки: `d02b-after-save-empty.png` (шапка «Четверг, 24 сентября» после «Сегодня»), `d01-new-window-scroll-1.png`.

> ✅ исправлено (g2-3): та же правка, `JournalToolbar` не использует `toISOString()`; окно записи берёт
