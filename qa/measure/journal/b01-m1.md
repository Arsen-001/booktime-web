## Дополнительно (не привязано к одному F-id)

1. **Новый major-дефект: растягивание записи (F-01-031) открывает лишнее окно «Новая запись».**
   Тот же класс утечки клика, что чинили для F-01-029, вернулся на соседнем контроле. Причина по коду
   (`BookingBlock.tsx: startResize`) — `e.stopPropagation()` стоит только на `pointerdown`, а не на
   синтетическом `click`, который браузер всё равно генерирует по паре mousedown/mouseup и который
   всплывает до `onClick` колонки (`handleColumnClick` → открывает «Новая запись»). Нужна такая же
   правка, как на статус-кнопке и перерыве: `onClick={(e) => e.stopPropagation()}` на самой ручке
   растягивания. Сборщик отчитался «Проверено сценарием: … лишнее окно не открылось» для F-01-029, но,
   похоже, не гонял отдельный сценарий именно на ручке растягивания — на неё регрессия не
   распространялась при правке.
2. **Статус-кнопка на блоке записи остаётся 32×32px** (десктоп и телефон) — не входит в fix1, дефект
   m0 не закрыт. В коде есть осознанная пометка «assumed»: соседние записи стоят вплотную без зазора,
   40px там физически не разместить без наложения. На телефоне это по-прежнему единственный вход в
   F-01-029 — **major** для тач-устройства, как и в m0.
3. **Метки статусов в фильтре по-прежнему не совпадают с ТЗ**: «Подтверждена» / «Клиент подтвердил» /
   «Пришёл» / «Не пришёл» вместо ожидаемых «Ожидание клиента» / «Клиент пришел» / «Клиент не пришел» /
   «Клиент подтвердил» — не затронуто фиксом, **minor**, как в m0.
4. **Ячейки мини-календаря 38×44px** (десктоп, чуть меньше 40 по ширине) — задокументировано сборщиком
   в `qa/requests/journal.md` как «как есть, визуально не критично» — **minor**, без изменений.
5. Собственный `overlap`-сценарий (`b01-m1-overlap.mjs`) промахнулся мимо пустой ячейки и попал на уже
   существующую запись — переиспользовал его только как лишнее подтверждение F-01-030, для F-01-215 в
   этом заходе новых данных не добавил (см. таблицу выше, инвентарь m0 остаётся источником для F-01-215).
