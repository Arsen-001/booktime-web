## 🔴 Главная находка ЭТОГО захода (BLOCK) — тонкие права F-01-178/F-01-179 не действуют на персону «мастер»

**Что видно:** владелец в Настройки → Цифровой журнал → Права доступа выбирает сотрудника (пробовал
и на мастере Ани Саргсян, и на администраторе Лилит Мкртчян), снимает «Перенос записи» и «Показывать
номера телефонов», жмёт «Сохранить» — настройка подтверждённо сохраняется (пережила `page.reload()`).
Дальше:
- Персона **admin** (Лилит Мкртчян) — право реально действует: курсор записи меняется с `grab` на
  `pointer`, перетащить нельзя (F-01-115 ✅), «только свои» реально сужает журнал до своей колонки
  (F-01-178 ✅).
- Персона **master** (Ани Саргсян) — та же самая настройка, сохранённая для того же сотрудника,
  **не действует вообще**: курсор остался `grab`, запись перетаскивается свободно, как будто права не
  снимали. Проверено дважды (drag реально переносит блок и даже ловит коллизию с соседней записью —
  значит перенос физически произошёл).

**Причина (нашёл в коде, `src/areas/journal/lib/rights.ts`):**
```ts
const q = useApiQuery(
  ["journal", "staff-rights", staffId],
  () => getStaffJournalRights(staffId!),
  { enabled: currentReady && Boolean(staffId) && persona === "admin" },   // ← только admin!
);
...
const override = persona === "admin" ? q.data : undefined;               // ← для master всегда undefined
```
Тот же паттерн один-в-один в `useWindowRights` (F-01-179) чуть ниже в файле — значит и 31 право «Окна
записи» для мастера тоже не читает персональный override, только `defaultMasterWindowRights()` плюс
грубые права фундамента. Итог: страница «Права доступа» в настройках журнала — рабочая витрина только
для роли «администратор»; для роли «мастер» (самая частая роль в салоне, ⭐ решение F-00-042 «мастер
видит свой календарь») весь блок настройки прав по сотруднику — бутафория.

**Задето:** F-01-115 (❌ для master), F-01-178 п.3 «история» и F-01-179 (весь блок, ❌ для master —
код идентичен, не проверял отдельно каждое из 31 права, но источник один), вероятно и F-01-180
(историческое окно для master, не проверял отдельно). F-01-085/F-01-154 — не задеты (там грубые
`useCan(...)` права фундамента, они по коду не завязаны на `persona === "admin"`).

Снимки: `qa/shots/journal/b05-rights-flow/02-owner-rights-journal-after.png` (владелец снял права),
`diag-after-reload.png` (право пережило перезагрузку), `05-master-journal.png` +
`07-master-after-drag-attempt.png` (мастер всё равно перетащил запись — тост «Это время у мастера уже
занято другой записью», не «нет прав»), `admin2-owner-set.png` + курсор `pointer` в логе (для admin
работает верно).

## Прочее замеченное по пути

- Базовый прогон `measure.mjs --area journal` (owner, ru/en, phone/desktop) — 0 ошибок консоли, 0
  сырых ключей, 0 вылетов по ширине; на `/biz/journal` **10 зон нажатия < 40px** на обоих языках и
  обоих устройствах (вероятно, точки-индикаторы в мини-календаре слева — не проверял, относятся ли
  они к этой пачке; отдельно не чиню, минорно).
- hy: на всех трёх маршрутах «на экране нет армянского текста» — ожидаемо по правилу проекта (hy пока
  не пишем), сырых ключей при этом 0.
- `useCan` (грубые права фундамента) корректно «побеждают» тонкие — сам код это специально
  комментирует и я это наблюдал (мастер и без override видит замаскированный телефон именно из-за
  грубого `clients.phones`, а не из-за тонкого права, которое как раз не читается).
