Отдельно проверил код `BookingWindow.tsx:434` — правый блок окна записи фильтрует доп. поля

кода**, а не отдельным живым прогоном на fixture-клиенте (это единственное не «увидено глазами
на живом клиенте», хотя код однозначен).

**Вывод: F-04-141 — ✅ passed**, в отличие от `m1` (был major).

## 🔴 Критическая находка этого прохода: персист откатывается ЖИВЬЁМ, не только по логам

В `m1`/`fix2` дефект `QuotaExceededError` уже описан по логам консоли. В этом проходе я
воспроизвёл его **как видимый откат данных**, а не только предупреждение:

1. `/dev/ext/settingsHub/clients` → «Клиент "давно не был", если нет визитов»: 60 дней → выбрал
   «180 дней» → значение на экране сразу стало «180 дней»
   (`qa/shots/clients-g3-2-m2-f123/…after-select-180.png`).
2. Перешёл (`goto`) на тот же `/dev/ext/settingsHub/clients` ещё раз в той же сессии — значение
   **откатилось на «60 дней»** (`qa/shots/clients-g3-2-m2-f123/…after-reload.png`), консоль в этот
   момент писала `[mock-db] … QuotaExceededError … 'bp-mock-db' exceeded the quota`.
3. Отдельно: создал клиента «Тест Полем141b» с доп. полем через полную форму — тост «в базе»
   показался, счётчик клиентов вырос 90→91 (`qa/shots/clients-g3-2-m2-f141b/…after-submit.png`), но
   **в новом браузерном контексте** (эквивалент перезагрузки/новой вкладки) поиск по «Полем141b»
   вернул «Найдено 90 из 90» — клиент не найден, счётчик снова 90
   (`qa/shots/clients-g3-2-m2-f141c/…search-result.png`). Записи потеряны.

Это тот же ядровой баг, что описан в `g3-2-m1.md`/`clients-g3-2-fix2.md`, — не новая находка по
причине, но впервые в отчётах раздела подтверждён **действием**, а не только логом: при живом
пороге localStorage побеждает случайная запись, и «Готово, когда» с формулировкой «после
перезагрузки» физически нельзя подтвердить, пока это не починено в `src/mock/db.ts` (не мои пути,
уже записано в `qa/requests/clients.md` прошлой пачкой).
