## Дефекты

1. **[major] F-04-001** — на «Клиентской базе» нет кнопки/меню «Действия» и нет «Операции с Excel» —
   они не реализованы вообще (не найдены ни в `ClientsListScreen.tsx`, ни где-либо в
   `src/areas/clients/**`). «+ Добавить клиента» на месте, но всегда `disabled` без объяснения —
   пользователь не может ни добавить клиента, ни выполнить массовое действие, ни выгрузить в Excel.
   → `src/areas/clients/ClientsListScreen.tsx:162,244`

2. **[major] F-04-009** — массовые действия над отмеченными клиентами отсутствуют полностью: есть
   только текст-счётчик «Отмечено N из M» (`ClientsListScreen.tsx:219-223`), но нет самого меню
   «Действия», из-за чего оба пункта «Готово, когда» невыполнимы в принципе.

3. **[major] F-04-002** — поиск работает не по спецификации: нет кнопки «Найти», результат
   применяется мгновенно по мере ввода (`debounceMs` не передан в `FilterBar`,
   `SearchInput` default = 0). Спецификация явно требует «результат появляется после нажатия
   «Найти»». Функционально поиск исправен (проверено), но по другому механизму, чем описано.

4. **[major] F-04-007** — сценарий приёмки «при 26 клиентах — вторая страница» невозможно
   воспроизвести: ни у одного демо-бизнеса нет >25 клиентов, кнопка «Добавить клиента»
   задизейблена. Либо нужен сид с 26+ клиентами хотя бы у одного бизнеса, либо рабочая кнопка
   добавления — иначе пачка не может считаться закрытой по этому пункту.

5. **[minor] a11y** — в меню колонок (`ColumnsMenu.tsx:62-69`) у всех 8 кнопок замка одинаковый
   accessible name «Закрепить»/«Открепить» без названия колонки — незрячему пользователю нечем их
   различить (сам я тоже не смог адресовать конкретную кнопку через `role=button[name=...]` и был
   вынужден брать `nth=N`).

6. **[minor] F-04-033** — в конструкторе фильтров у «Важность клиента» только 3 варианта
   (Золото/Серебро/Бронза), варианта «Без класса», явно требуемого спецификацией, нет
   (`36-filters-sales-expanded`).

7. **[minor] F-04-020 / F-04-024** — «Статус записей» и «Услуги» в конструкторе реализованы как
   одиночный `radio` (можно выбрать только один статус/одну услугу за раз), хотя структура данных
   (`f.status?: BookingStatus[]`, `f.serviceIds?: Id[]` в `lib/filters.ts`) и общий смысл фильтра
   («клиенты со статусом X» / «записанные на Y») подразумевают множественный выбор.

## Что понравилось (без действия не пишу «работает», но зафиксировать стоит)

Каркас (поиск, сортировка, закрепление/скрытие колонок, сегменты, панель клиента, deep-link по
`client_id`, пустое состояние, телефон/десктоп раскладка, ru/en локализация) — собран аккуратно и
именно так, как описано в CONVENTIONS.md §0: одна primary-кнопка, воздух, EmptyState с CTA, тосты на
действия, таблица→карточки на телефоне. За всё время прогонов — 0 ошибок консоли, 0 «сырых» ключей,
0 вылетов по ширине, 0 мелких зон нажатия (<40px), армянский шрифт в интерфейсе настоящий (nav-панель
на hy — реальные буквы, не квадраты). Разделение данных между бизнесами подтверждено действием:
Kaytsak Barbershop показывает свой отдельный список клиентов, не пересекающийся с Nuri Nail Studio.

**hy для раздела (вне контракта этой проверки, но для протокола):** `messages/hy/clients.json`
переведён только на 3 ключа из 104 — весь основной текст экрана на армянском языке показывается
по-русски (не сырой ключ, откат корректный). По ТЗ задания моей роли для hy проверялось только
отсутствие сырых ключей и настоящий шрифт — оба условия выполнены, поэтому в дефекты не выношу.
