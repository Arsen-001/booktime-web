# Архитектура services · arch-a1

Дата: 2026-09-25. Ревьюер архитектуры (код не правил).
Раздел ещё заглушка (код фундамента ~10–80 строк), поэтому замечаний к коду нет — ниже то, что уже построено соседями
на вашей территории и что нужно учесть с первого файла, чтобы не завести второй источник правды. Общие правила —
docs/ARCHITECTURE.md и CONVENTIONS.md §16; проверка — `node scripts/arch-check.mjs --area services`.

Первым делом (для всех новых разделов):
- данные среза — по `businessId` (никаких «общих на всех» настроек), ключи — фабрика `servicesKeys` с `['services', …]`;
- одна бизнес-операция = одна функция `src/api/services.ts` = один `request()`, внутри без `await coreCreate/updateBooking`;
- правила (суммы, сроки, остатки, статусы) — чистые функции в `src/domain/services.ts`;
- права — `useCan('services.*')` в экране и проверка в api, не `persona ===`;
- записи — `useApiMutation` + try/catch + тост; списки > 100 — фильтр и пагинация в api.

## Что уже есть у соседей (major — договориться до своих типов)

1. **Обязательность выбора оттенка** — в ядре `Service.shadeChoice` (k1, пишете вы) и черновик `shadeRequirement` в срезе client.
   Когда появится ваш экран услуги — client удалит черновик (его arch-a1 №1).
2. **«Услуга видна онлайн»** — `Service.onlineBookable` и `active` читают client (`listCatalog`), online (`isStaffOnlineVisible`,
   `isListable`) — каждый по-своему. Общее правило видимости — просьба №5; вы — хозяин полей, держите их смысл в комментарии типа.
3. **Цена «от–до» и длительность «от–до»** (`priceMax`, `durationMax`) — запись везде бронирует нижнюю границу
   (docs/backend/07-mock-only.md). Правило «какую длительность/цену брать при записи» — в `domain/rules/pricing.ts` (просьба №3),
   ваш экран задаёт значения.
4. Модерация фото услуги — `submitForModeration` из `src/api/platform.ts` при сохранении (CONVENTIONS §6).
