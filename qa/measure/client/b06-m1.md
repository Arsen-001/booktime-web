## Блокер #1 (BLOCK) — материалы никогда не проходят проверку размера

**Где:** `/biz/apps/branded`, блок «Материалы для публикации» (F-14-148, F-14-149, F-14-152, и как следствие —
F-14-145, F-14-147 «отправить заявку»).

**Что видно:** загружаю настоящий PNG ровно 2208×2208 (заставка) — тост «Картинка меньше 2208×2208 — загрузите
крупнее». То же для логотипа 1024×1024 и картинки Google Play Featured 1024×500 — обе отклоняются как «слишком
маленькие», хотя файл был ровно нужного размера.

**Причина (нашёл в коде, не мой файл — `src/ui/ImageUpload.tsx`, фундамент):** `ImageUpload` перед сохранением
уменьшает **любую** картинку до `MAX_SIDE = 800` px по длинной стороне (`toDataUrl`) — отдаёт `onValueChange`
уже уменьшенный data URL. `MaterialImage` в `BrandedAppScreen.tsx` затем сам грузит этот (уже уменьшенный) URL
новым `Image()` и сравнивает `img.naturalWidth/Height` с исходным требованием (2208, 1024, 1024×500) — и
уменьшенная картинка **всегда** меньше требуемого, поэтому проверка проваливается для любого файла, каким бы
качественным он ни был. Т.е. требование «2208×2208» физически невыполнимо в текущем виде экрана.

**Следствие:** ни один пункт материалов (F-14-148/149/152) не может быть отмечен «готово»; счётчик блокеров
никогда не доходит до нуля обычным путём → кнопка «Отправить заявку» остаётся недоступной для любого реального
черновика → F-14-145/147 («у бизнеса есть способ заказать» / «заказ уходит в работу, когда всё собрано») на
практике недостижимы, хотя логика самой заявки (`submitBrandedAppRequest`) корректна — до неё просто нельзя
дойти обычным путём.

**Как чинить (для сборщика, не делаю сам — я измеритель):** либо `MaterialImage` должен проверять размер
**исходного** файла (до `ImageUpload`/`toDataUrl`), либо `ImageUpload` должен сохранять оригинальные пиксельные
размеры отдельно и отдавать их наверх для валидации, либо `MAX_SIDE` для этого конкретного места поднять хотя бы
до 2208 (но тогда база разрастётся — сам компонент существует именно чтобы не раздувать localStorage).
Снимки: `flow-04-before-submit.png` (счётчик «не хватает 2 пункта» после того, как все документы и текстовые
поля уже заполнены).

## Блокер #2 (major) — ссылки на свои приложения клиенту не показываются

**Где:** F-14-144, второй пункт «Готово, когда».

**Что проверено:** `grep -rn "getBrandedAppRequest|iosLink|androidLink" src/areas/client/**` — единственное
использование во всём клиентском коде — сам экран `/biz/apps/branded`. В `BookScreen.tsx` (флоу записи и
подтверждения) этих полей нет. То есть сохранённые ссылки видит только владелец на своём же экране — клиент их
нигде после записи не получает. Первая половина пункта («бизнес может указать ссылки») работает и сохраняется,
вторая («клиент видит их после записи») не реализована совсем.

## Что подтверждено действием и выглядит корректно

- Чек-лист документов (4 галочки) корректно уменьшает счётчик блокеров, галочка не «откатывается» визуально при
  сохранении (специально обработано комментарием в коде — «фикс 1» — подтверждено на глаз).
- Ограничения длины полей (30/11/80/4000/100 символов) и запрещённый текст (телефон, ссылка) — проверены живым
  вводом, оба типа ошибок ловятся с понятным текстом на экране.
- Пересчёт годовой цены при добавлении филиала — живой (200 000 ֏ → 220 000 ֏ при +1 филиал), валюта — драм.
- Выбор типа аккаунта Apple (организация/ИП) корректно переключает список шагов инструкции; способ передачи
  доступа — два безопасных/небезопасных варианта с пояснением.
- Состояние «Заявка отправлена» (readOnly) на предзаполненном демо-бизнесе (сфера nails) — все поля недоступны
  для редактирования, статус-плашка и дата видны, экран не выглядит «сломанным» и на телефоне, и на десктопе.
- ru/en — полный перевод пачки (0 сырых ключей, 0 `[i18n:no-en]` внутри пачки), тексты понятные, без канцелярита;
  hy — не переведён намеренно (по правилу проекта), сырых ключей нет.
- Права: под персоной `client` маршрут `/biz/apps/branded` отдаёт экран «Здесь нет доступа» (не 404, не пустой
  экран, ответ 200 с понятным объяснением и кнопками входа) — доступ действительно закрыт для чужой персоны.
- Консоль чистая на всех измеренных страницах и сценариях (включая полный прогон формы) — hydration-ошибка,
  замеченная в одном из черновиков сценария, не воспроизвелась после починки самого сценария (была моя ошибка
  скрипта, не продукта) — не включаю её в список дефектов.
