## Новый прогон F-03-102 + F-03-076: не «тумблер проверен», а полный флоу действием

В m0 оба пункта стояли «⏳ не проверено действием». В этот проход прогнал вживую до конца (персона `individual`,
`sphere=fitness` → бизнес «Арман Геворгян · тренер», ссылка `arman-fit`, тип услуг «Индивидуальные и групповые»):

1. Открыл `/biz/online` → «Настроить» → «Групповая запись» → включил оба тумблера («Разрешить клиентам
   записываться на несколько событий» и «Добавлять дополнительные места в групповые услуги») — оба сохранились
   тостом «Сохранено», у каждого раскрылось числовое поле (макс. событий = 3, макс. мест = 1) — скрин
   `qa/shots/online-b04m1/...toggled-final` / доп. проверка `/tmp/shots-tmp10` (одиночный тумблер — визуально
   ровно ON, без расхождений).
   ⚠️ Замечено и перепроверено: при **двух кликах подряд с интервалом 300 мс** один снимок поймал второй
   переключатель визуально «выключенным», хотя зависимое поле уже отрисовалось как для «включено» — гонка
   перерисовки чек-состояния при двух почти одновременных мутациях. Повторил тот же тумблер отдельно с паузой
   1200 мс — отрисовался верно с первого раза. **Не блокер**: реальное состояние в базе правильное (числовое поле
   и последующий флоу это подтверждают), сбоит только доля секунды на кадре скриншота при частых кликах подряд —
   отмечаю как minor-наблюдение, не завожу как дефект.
2. Перешёл на `/b/arman-fit` (в том же браузерном контексте — persona/cookie сохранились) → «Записаться» → «Что вы
   хотите записать?» показал оба варианта (F-03-082 живьём, скрин `booking-type-step.png`) → «Групповое занятие» →
   список из 6 событий с датой, мастером и «N мест» (F-03-101 живьём, скрин `group-events-list.png`).
3. Кликнул «Растяжка в группе» — выбралось (подсветка + появилось поле «Сколько мест»: 1). Кликнул вторую строку

   событий: 2»** (F-03-102, скрин `two-events-selected.png`) — ровно первый пункт «Готово, когда» выполнен
   действием, не только код.
4. Дошёл до заполнения формы (имя, телефон, согласие) — на шаге автозаполнения поля «Имя» селектор `input[type=text]`
   не попал в нужное поле с первого раза (таймаут locator.fill) — это ограничение моего сценария (в разметке инпут
   без явного `type="text"`, только `type` не задан явно или задан иначе), не подтверждённый как дефект продукта:
   не успел подобрать точный селектор в рамках бюджета этой пачки и не гнал до конца отправку формы. Второй пункт
   «Готово, когда» F-03-102 («каждая созданная запись отменяется/переносится отдельно») и третий пункт F-03-096
   («запись из нескольких услуг под разные абонементы») остаются непроверенными действием — фиксирую честно ⏳, не
   пишу «работает».

## Новый дефект: непостоянная гидратация на /biz/online/settings

В одном из 48 прогонов широкого замера (owner/ru/**телефон**, остальные 47 комбинаций телефон/десктоп × ru/en —
чисто) страница `/biz/online/settings` поймала:
```
Error: Hydration failed because the server rendered HTML didn't match the client...
Can't perform a React state update on a component that hasn't mounted yet...
```
Скрин `qa/shots/online-b04/biz-online-settings__owner-nails-ru-light-phone.png` — на нём поверх экрана всплыл
дев-оверлей Next.js «2 Issues», перекрывающий нижнюю часть настроек. Перепрогнал тот же самый маршрут/персону/язык/
устройство ещё дважды отдельными сценариями (`qa/shots/online-b04m1/`) — оба раза 0 ошибок консоли, страница чистая.
**Вывод: дефект реальный, но плавающий** (похоже на гонку между `useEffect`, который читает что-то из `window`/дат в
блоке правил мастеров или загрузки списка сотрудников, и первым клиентским рендером) — не блокирует работу
(страница восстанавливается сама), но раз в ~1/50 показов пользователю на телефоне вылезет дев-оверлей с ошибкой.
Классифицирую **minor** (дев-режим, самовосстанавливается, воспроизвёл 1 раз из 3), но фиксирую явно — не мой код,
чинить не могу (я измеритель), передаю в отчёт.
