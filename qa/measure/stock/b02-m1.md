## Дефект 1 (major) — правка комментария в сохранённой операции незаметно меняет время документа

Открыл существующий документ № 100004 (приход, «7 сентября 2026, 19:35»), поправил **только** комментарий и
галочку «Оплачено» — остальное не трогал — нажал «Сохранить изменения» → тост «Изменения сохранены». Вышел
через «Назад» и заново открыл тот же документ кликом по строке (SPA, без `reload`) — «Дата» осталась «7 сентября
2026» (верно), но **«Время» стало 19:37** (было 19:35) — разница (2 мин) совпадает с реальным временем,
прошедшим между открытием документа и сохранением правки. Похоже, форма при сохранении подставляет текущее
время вместо того, чтобы сохранить исходное значение этого поля. Снимки: `edit-history4/…m1-50-doc-100004-open.png`
(19:35) vs `…m1-53-reopen-after-save.png` (19:37). Нарушает F-08-050 («правятся дата, склад, товары, количество,
цены, комментарий» — время меняться не должно, если поле не трогали).

## Замечание (major, UX) — сообщение об ошибке перемещения не называет причину

Перемещение с неверно выбранным складом-источником (товара там нет) даёт тост **«Не удалось сохранить
перемещение»** без объяснения — снимок `move2/…m1-42-move-result.png`. При верном складе-источнике то же
действие проходит успешно (снимок `move3/…m1-92-move-result2.png`), так что механика (F-08-059) работает —
проблема только в тексте ошибки: по правилу 0 «понятные слова» и «отклик на каждое действие» пользователь
должен понимать, **почему** не получилось («На складе «Расходники» нет товара «Гель-лак «Бордо»»), а не
получать общее «не удалось». Также: форма перемещения по умолчанию подставляет в «Со склада» первый склад
списка («Расходники»), а не склад, где реально лежит товар, который потом выбирают в «Товары» — это провоцирует
именно эту ошибку у обычного пользователя, если он не поменяет склад-источник вручную.

## Методическая заметка (важно для будущих измерителей раздела `stock`)

Первые попытки этого прогона (сценарии `b02-m1-recheck-list.json`, `b02-m1-writeoff-check.json`, `b02-m1-move.json`,
`b02-m1-move2.json`) использовали `{"goto": "…"}` для перехода между экранами внутри сценария. Это воспроизвело
уже описанный в `qa/requests/stock.md` артефакт: полная навигация браузера (`goto`/`reload`) натыкается на
`[mock-db] QuotaExceededError` в localStorage (фундамент `src/mock/db.ts`, не мой путь) и теряет только что
сделанную запись — список «не видит» новую операцию, остаток «не меняется». **Это не баг экранов `stock`.**
При переходе кликом по пункту бокового меню (SPA-навигация, без полной перезагрузки) — те же действия дают
верный результат (список видит операцию, остаток пересчитан). **Рекомендация:** сценарии на этот раздел, где
важна проверка «после сохранения», не должны использовать `goto`/`reload` между шагом сохранения и шагом
проверки — только клики по меню/ссылкам, как реальный пользователь. Отдельно фиксировать не стал — тот же
корень уже открыт в `qa/requests/stock.md` (block по `F-08-007`/`F-08-049`), просто подтверждаю, что вывод
верен и распространяется также на F-08-058 и F-08-059 (я по ошибке чуть не завёл на них дубли того же
артефакта).
