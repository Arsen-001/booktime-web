## 🔴 Главные находки

### ПОДТВЕРЖДЕНО действием — фикс прав для персоны `master` работает по-настоящему, не только визуально

fix2 заявил `<fieldset disabled={!canManage}>` + подсказку. Проверил не только глазами (скриншот), но
**действием**: сценарий `b03m2-master-click-blocked.json` — персона `master`, клик по радиокнопке
«Дата поступления средств на счёт» — Playwright **не смог кликнуть, `locator.click: Timeout 8000ms
exceeded`** (элемент не interactable — честно задизейблен, а не просто визуально приглушён CSS).
Плюс подсказка «Только просмотр — изменить настройки может тот, у кого есть право «Зарплата:
управление»» видна над формой и на телефоне, и на десктопе (`qa/shots/payroll-b03m2/permission/…`).
Это закрывает найденный в b03-m1 дефект «мастер может пощёлкать настройки без единого признака
«только просмотр»» — теперь ✅ подтверждено действием, не только чтением кода.

### НЕ ПОДТВЕРЖДЕНО — F-09-008 «настройка переживает перезагрузку» ПО-ПРЕЖНЕМУ ❌, fix2 сам это признал

fix2 прямо написал, что чинил не саму запись на диск (не свой путь, `src/mock/db.ts` — фундамент), а
только видимость в рамках одной вкладки. Перепроверил действием заново (`b03m2-reload-persistence.json`):
владелец включает тумблер «Доплачивать за ассистирование», жмёт «Сохранить» → тост «Настройки
сохранены», в той же вкладке тумблер включён (`…after-save-same-tab.png`) — но следующий **настоящий**
`page.goto` на тот же адрес (эквивалент F5) откатывает тумблер обратно на выключенный
(`…after-full-reload.png`, оба снимка есть в `qa/shots/payroll-b03m2/reload/`). Корневая причина видна
и в консоли этого же прогона: `[mock-db] не удалось сохранить в localStorage QuotaExceededError:
… exceeded the quota` (тот же warning всплыл и в отдельном прогоне `master-click-blocked`, то есть
это не разовый флейк, а стабильно исчерпанная квота). Итог: пункт «Готово, когда» для F-09-008,
требующий сохранения настройки, остаётся ❌ — фикс закрыл только половину дефекта (права), не саму
персистентность.

### ЧАСТИЧНО ПОДТВЕРЖДЕНО — F-09-028/029/030 (групповые события): чекбоксы и подписи на месте, живое число не свёл

На `/dev/ext/staffCard/payroll` (владелец, свежая загрузка страницы — именно так, как их увидит
реальный пользователь после перезахода) чекбокс «Оплата за групповые события» раскрывает ровно тот
набор, что в ТЗ: «Минимальная выплата (никто не пришёл)», «Выплата, если пришёл хотя бы один клиент»,
три радиокнопки правила доплаты («Не доплачивать…» / «Доплата за каждого пришедшего клиента» /
«Доплата за каждого пришедшего сверх порога») — подписи дословно совпадают с F-09-028/029/030
(`qa/shots/payroll-b03m2/extgroup2/…group-enabled.png`). Это подтверждено **действием на свежей
загрузке страницы**, без сохранённого состояния из предыдущей сессии — сильнее, чем находка m1. Однако
довести до конкретного числа (например «0 участников, минимум 5% от 1000 → 50») в этом заходе не успел
— сценарий с кликом по чекбоксу «Минимальная выплата» и вводом суммы упал по таймауту селектора (моя
техническая недоработка сценария, не проверка продукта), пересобрать не хватило бюджета пачки.

### НЕ ПОДТВЕРЖДЕНО — F-09-047 (пример ассистентов 300/100/100 из fix2) недостижим со свежей страницы

fix2 заявил живой пример «Мастер: 300 · Ассистент 1: 100 · Ассистент 2: 100», но прямо написал, что
проверял его **в рамках одной вкладки без полной перезагрузки** — то есть при уже включённом в памяти
(не на диске) `assistCompensationEnabled`. Открыл `/dev/ext/staffCard/payroll` свежей загрузкой (как
одна из первых точек входа реального пользователя после переоткрытия вкладки) — блока «три ставки»
(без ассистента / с ассистентом / как ассистент, F-09-015/047) на экране просто нет, потому что
`assistCompensationEnabled` на уровне бизнеса на свежей загрузке снова `false` (та же причина, что и
в находке про F-09-008 выше — квота `localStorage`). Значит пример из fix2 воспроизводим только
внутри одной живой вкладки сборщика, а не при обычном заходе — тот же корневой блокер, что в m1,
просто иначе задет. Не мой путь чинить (`src/mock/db.ts`), фиксирую для протокола.

  заблокирован, не просто визуально), reload-persistence для F-09-008 (повторно подтверждён как ❌),

  визуально, и физически (Playwright не может кликнуть) недоступны, с понятной подсказкой
- **Осталось ⚠ без изменений с m0/m1** (не входило в целевой объём m2): 015 (оба пункта), 107 (3 из 4

## Сценарии

Новые в этом заходе — `qa/scenarios/payroll/b03m2-*.json` (8 файлов): `reload-persistence` (полная
перезагрузка после сохранения), `permission-master` (десктоп+телефон, визуальная проверка),

`assist-clientnav` (сохранение + клиентская навигация по меню), `ext-staffcard` (обзор вклада payroll
в карточку сотрудника), `ext-group` / `ext-group2` (раскрытие блока групповых событий). Снимки —
