# Заметки b01 — три грабли «всегда смонтированной» шторки/модалки

Для себя (следующие пачки b02…b05) и на случай, если пригодится соседям с той же формой CRUD (список +
шторка редактирования, шторка мономонтирована, `initial` приходит пропом).

## 1. `initial!.id` внутри `useApiMutation` — падает экран

React Compiler выносит `x!.y` из тела колбэка в область рендера (CONVENTIONS §18.5). Шторка
«Новая запись» рендерится с `initial === undefined`, и `initial!.id` падает ДО того, как функция вообще
вызвана. Чинится: `initial?.id ?? ''`.

**Как ловится:** `measure.mjs --area <id>` — «экран упал TypeError» в консоли. Проверять сразу после
первой сборки списочного экрана с шторкой правки, не дожидаясь сценария.

## 2. Форма правки открывается ПУСТОЙ

`Sheet`/`Modal` возвращают `null`, когда `open=false`, — но КОМПОНЕНТ-ОБЁРТКА (`AccountFormSheet` и т. п.)
не размонтируется, если родитель держит его в дереве постоянно (а конвенция требует именно этого —
«оверлеи смонтированы закрытыми», §0.3). Поэтому `useState(initial?.name ?? '')` инициализируется ОДИН РАЗ,
когда `initial` был `undefined`, и не обновляется, когда пользователь позже кликает «править» на конкретной
записи (React не перевызывает инициализатор `useState` при смене пропов).

**Чинится:** `key={editing === 'new' || editing === null ? 'new' : editing.id}` на самом компоненте
шторки/модалки в экране-списке — React размонтирует/монтирует её заново под новый `initial`. Приём уже был
в `loyalty/AccountTypesScreen.tsx` и `schedule/TemplateFormModal.tsx` — не увидел его сразу, повторил
грабли. **Проверять сценарием**, не только снимком «форма открылась»: снимок пустой формы для НОВОЙ записи
выглядит так же, как разбитая форма правки (оба «пустые»), разница видна только если реально кликнуть
правку у записи с данными и прочитать значение поля.

## 3. Дефолт из ещё не загруженных данных, замороженный в `useState`

`useState(activeLocationIds[0] ?? locationIds[0] ?? '')` — на первом (закрытом) рендере шторки эти массивы
пустые (`useCurrent()` ещё не готов), значение замораживается как `''` навсегда для этого монтирования.
Результат — создаётся запись с пустым `locationId`, которая потом никогда не проходит фильтр по филиалу и
«пропадает» из списка, хотя в сторе она есть (это особенно коварно — ошибки в консоли нет, тулза
`fids.mjs`/`check-tokens.mjs` тоже молчат, только сценарий с реальным созданием ловит).

**Чинится:** не замораживать «умолчание из хука» в `useState`; держать только явный выбор пользователя
(`useState<string | null>(null)`) и считать эффективное значение в теле рендера каждый раз:
`const locationId = override ?? activeLocationIds[0] ?? locationIds[0] ?? '';`.

## Общий урок

Для КАЖДОГО списка с шторкой/модалкой правки — сценарий должен: 1) создать запись, проверить, что она
появилась в списке (а не просто «тост показался»), 2) кликнуть правку у СУЩЕСТВУЮЩЕЙ (не только что
созданной) записи и проверить, что поле формы РЕАЛЬНО содержит её значение (`inputValue()`, а не снимок
на глаз — оба состояния визуально похожи), 3) перезагрузить страницу и проверить, что созданное осталось.
Просто открыть форму и сделать скриншот — недостаточно, все три бага прошли бы этот минимальный набор
незамеченными.
