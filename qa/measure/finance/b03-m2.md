Сценарий `qa/scenarios/finance/_persist_check.mjs`: на `/biz/finance/settlements` выписал премию 77 ֏
(«Проверка сохранения») → тост «Начисление добавлено», строка появилась, баланс вырос — всё верно **в

считает `console.error`):

```
[mock-db] не удалось сохранить в localStorage QuotaExceededError: Failed to execute 'setItem' on 'Storage':
Setting the value of 'bp-mock-db' exceeded the quota.
```

`Object.keys(localStorage)` — **пусто** и сразу после сохранения (спустя 3000 мс, дебаунс — 400 мс), и после
`page.reload()`. Тело страницы после reload: `Пока нет начислений`, баланс — `0`. Тот же прогон с полным
циклом премия+штраф (`after-premium-and-penalty.png` → баланс 20, обе строки видны) → `page.goto` на тот же
URL (`after-reload.png`) → баланс снова `0`, список снова пуст.

**Новое по сравнению с b03-m1:** это не только «квота переполнена у уже большого стора» — сама
дебаунс-запись (`src/mock/db.ts`, `debouncedLocalStorage()`) **не срабатывает вообще ни разу за сессию** в
моих прогонах, ни через 400 мс, ни через 3000 мс без действий — значит `pending`/`timer` либо переполнение
происходит на **первой же** попытке записи (весь снапшот `bp-mock-db` уже больше лимита ДО моего действия, из
сидовых данных), и любая новая мутация просто не может записаться поверх уже нерабочего ключа. Это
согласуется с тем, что `localStorage.keys()` пуст даже до всякого моего действия — ключ `bp-mock-db` не
создаётся вовсе, а не «создаётся один раз и потом не обновляется».


отображаемой строке способа оплаты в чеке должна быть **фактически заплаченная сумма** (5000), а не полная
цена. Похоже, что тестовые сидовые данные для этого визита содержат платёж на 8000, а не на 5000 (расхождение
между тем, что видит `ClientCard` — вычисляет из `bookingPayments`/визитов — и тем, что видит чек — тоже из
`bookingPayments` для того же `bookingId`), т.е. вероятно это два РАЗНЫХ источника чисел для одного визита с
несовпадающими данными в сиде, а не ошибка формулы. Это блокирует проверку «Готово, когда» для F-07-148
буквально (чек не совпадает с реальной задолженностью клиента) — оцениваю как **major**, т.к. выданный
клиенту чек на полную сумму при фактическом долге — прямой риск для бизнеса (не только UI-баг).
