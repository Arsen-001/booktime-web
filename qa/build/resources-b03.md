## Готово по каждому пункту «Готово, когда»

- **F-16-064**: `repeatEvent` создаёт N событий по шаблону/периодичности; шаблон сохраняется и выбирается в
  другом событии (`listEventTemplates`/`saveEventTemplate`, проверено: сценарий «выбрать сохранённый →
  периодичность подставляется»). «С клиентами» копирует активных участников в каждое новое событие.
- **F-16-065**: событие с `seriesId` не показывает форму «Повтор» (только заметку со ссылкой на «Расписание»).
- **F-16-067**: `createEventSeries` — расписание «Пн 18:00–19:00 и Чт 19:00–20:30 до даты» создаёт события
  обоих дней с их СВОИМИ временем/длительностью/ресурсами; исходное событие не дублируется на свою дату.
- **F-16-069**: создание серии/повтора не вызывает ни одной функции уведомлений (`sendEventJoinNotifications`
  вызывается только явной кнопкой «Отправить», отдельно от создания); проверка графика сотрудника нигде не
  вызывается — событие создаётся в любой день.
- **F-16-070**: `SeriesManagePanel` рендерит кнопки правки только при `!isPast` (событие, открытое из прошлого,
  их не показывает); прошедшие события серии никогда не попадают в выборки `futureSeriesEventsOnWeekdays`/
  `datePart(e.start) >= today()` у extend/remove/edit-функций — их не тронет даже прямой вызов API.
- **F-16-071**: `extendOrShortenSeries` продлевает (создаёт недостающие) и сокращает (отменяет лишние,
  прошедшие не трогает); дата раньше сегодня — `ApiError('invalid_end_date')`, поймано формой.
- **F-16-072**: `addSeriesWeekday`/`removeSeriesWeekday` — добавленный день создаёт события до конца серии,
  удалённый отменяет все БУДУЩИЕ события этого дня.
- **F-16-073**: `editSeriesDayRule` физически не принимает `serviceId` в патче — сменить услугу массовой
  правкой невозможно на уровне типа.
- **F-16-074**: `uniqueEventIds` в `EventSeriesDef`; `editSeriesDayRule(..., applyToUnique)` пропускает
  уникальные события, если галочка не отмечена.
- **F-16-075**: `saveEventParams`/`updateSeriesEvent`/удаление одного события меняют/отменяют ТОЛЬКО это
  событие (по `eventId`), остальные события серии не задеты; событие помечается уникальным.
- **F-16-076**: `deleteSeries` отменяет все будущие события серии, прошедшие остаются (видны в отчётах как
  обычные `groupEvents`).
- **F-16-077**: значок серии — в шапке `EventWindowScreen`, в списке `GroupsListScreen`; в журнале уже
  показывал `GroupEventBlock.tsx` (чужой, не мой путь, проверил — работает как есть); события «Повтора» без
  `seriesId` значка не имеют (структурно — `repeatEvent` его не ставит).
- **F-16-078**: `createVisitSchedule`/автосоздание при «Добавить клиентов из текущего события» — клиент
  попадает во все будущие события серии на отмеченные дни; каждая такая запись — обычная `Booking`, значит
  видна в истории визитов клиента без отдельной работы.
- **F-16-079**: снятие дня в `VisitScheduleSheet` → `updateVisitSchedule` снимает клиента только с БУДУЩИХ
  событий этого дня (`futureSeriesEventsOnWeekdays`), прошедшие визиты (уже созданные брони с датой в прошлом)
  не трогает; «Удалить» — `deleteVisitSchedule`, тот же принцип.
- **F-16-080**: кнопка «Расписание посещений» скрыта, если у брони участника мест > 1, и API дополнительно
  бросает `ApiError('multi_seat_no_schedule')`; кнопка также скрыта на прошедшем событии (из прошедшего в
  расписание не добавить); изменённая цена участника не копируется в новые брони — `addParticipant` всегда
  создаёт бронь с ценой по умолчанию (в наш `createVisitSchedule`/`updateVisitSchedule` цена не передаётся).
- **F-16-081**: `saveEventJoin` пишет `url`+`instructions` (и зеркалит `url` в `GroupEvent.onlineUrl` ядра для
  совместимости с F-00-081); поля сохраняются и подгружаются при повторном открытии вкладки.
- **F-16-082**: «Отправить»/«Отправить повторно» доступны из вкладки «Уведомления»; каждый вызов добавляет
  метку времени в журнал отправок, показанный тут же.
- **F-16-095**: `EventCreateScreen` (та же форма и на 390px) — сотрудник/дата/время/услуга (одна)/мест/
  длительность/ресурсы (через занятость F-16-011..013 из b01) — уже создаёт событие; отмечено F-16-095.
- **F-16-096**: перенос времени/сотрудника/длительности события в `EventWindowScreen` теперь переносит и
  бронь каждого активного участника (`saveEventParams`) — раньше (b01/b02) переезжало только событие.
- **F-16-097**: «Добавить клиента» (`AddParticipantSheet`) уже поддерживает телефон/имя + «посетитель на имя
  клиента» (`visitorName`) — ребёнок под тем же номером; отмечено F-16-097.
- **F-16-098**: `EditParticipantSheet` меняет ТОЛЬКО цену и комментарий брони участника — не услугу, не
  сотрудника, не ресурсы, не дату/время (нет таких полей в форме и в вызове `updateBooking`).
- **F-16-099**: интерфейс оплаты — статусы «Оплачено/Не оплачено/Без предоплаты» видны у каждого участника
  (наше решение — деньги не принимаем, только фиксируем статус, F-00-126/194, черновик, было уже в b01).
- **F-16-100**: кнопки «Позвонить» (`tel:`), WhatsApp (`wa.me`, с готовым приветствием) и переход в карточку
  клиента (`/biz/clients/[id]`) — в развёрнутой строке участника.
- **F-16-101**: «Повтор» события — тот же `RepeatPanel`, что и на десктопе (390px тот же экран); отмечено
  F-16-101 вместе с F-16-064/065.
- **F-16-034**: `EmptyStateHint` группового списка получил 6 шагов из блока ТЗ (тип журнала → сотрудники →
  групповые услуги → назначить сотрудников → график → расписание событий).
- **F-16-170**: `ServiceCard.tsx` (мой вклад в карточку услуги) показывает предупреждение с числом будущих
  событий у групповой услуги — САМО удаление и окно подтверждения строит `services` (не мой путь, заявка в
  `qa/requests/resources.md`), поэтому «услуга удаляется только после явного подтверждения» и «пропадает из
  поля Услуги ресурсов» — на стороне services (второе, впрочем, уже верно структурно: `Resource.serviceIds` не
  хранит невалидных id сам по себе только если services явно вызовет отвязку при удалении — тоже в заявке).

- **F-16-083** — канал «только email» у Altegio сознательно не повторяем (ТЗ прямо помечает это нашим ⭐
  расхождением: пуш вместо email, F-00-120); отдельного тумблера «Общие настройки → канал уведомлений» не

## Assumed (додумано)

- Даты `repeatDates`/`seriesOccurrences` — реализация «Недель: N» как множитель 7×N дней от `startDate`, без
  ловушки Altegio «Недель: 1 = раз в две недели» (F-01-102 «наша подпись без ловушки», F-16-064 явно ссылается
  на F-00-064) — у нас «раз в 1 неделю» значит буквально каждую неделю.
- `createEventSeries`: если у исходного события уже есть `seriesId`, повторная попытка создать расписание
  бросает `ApiError('already_series')` (в ТЗ явно не описано, вывод по аналогии с «нельзя переоткрыть уже
  открытое»).
- Расписание посещений клиента (`VisitScheduleEntry.weekdays`) при автосоздании через «Добавить клиентов из
  текущего события» получает ВСЕ дни серии (не только день исходного события) — трактовка фразы ТЗ «клиенты
  события попадают во все события серии» (1388) как «и в расписание посещений на все дни».
- «Уникальное» событие — храню список `uniqueEventIds` в СВОЁМ срезе (`EventSeriesDef`), а не полем на самом
  `GroupEvent` (ядро) — GroupEvent не трогаю без запроса; если позже понадобится видеть флаг «уникальное» вне
  resources (например, в журнале) — нужен отдельный запрос на поле ядра, пока не заводил (пока это видно
  только на моих экранах).
- `extendOrShortenSeries`: «нельзя сократить серию раньше уже созданных событий» (F-16-071, ❓ в самом ТЗ)
  реализовано как «нельзя раньше сегодня» — конфликт внутри самого ТЗ (прошедшие остаются или нет) решён так
  же, как F-16-070/072: прошедшие не трогаем никогда, будущие после новой даты — отменяются.
- Изменение `Booking.services[0].price` в `EditParticipantSheet` пересчитывает `total` по всем строкам
  (`price × qty`), хотя у групповых событий обычно одна строка — общий путь на случай, если позже появятся
  расходники/доп. товары в этой же брони (F-16-098 упоминает их как отдельную область не в этом списке).
