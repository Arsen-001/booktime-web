# resources · b01-fix1 — починка дефектов пачки b01 (26.09.2026)

Пачка чинила три дефекта, найденных измерителем на b01 («Каркас раздела и главные экраны»):
- **block** F-16-001,008,011,012 — ресурсы никогда не занимаются автоматически, третья запись на ресурс
  с 2 экземплярами не блокировалась;
- **major** F-16-051 — каждый новый участник группового события получал ложный бейдж «другой посетитель»;
- **minor** F-16-044 — не было подтверждено, что нельзя уменьшить число мест события ниже уже записанных.

## Что сделано

### Занятость ресурсов (F-16-001, F-16-008, F-16-011, F-16-012)

Движок занятости (`instanceBusy`/`pickFreeInstances`/`checkInstancesFree`, `src/domain/resources.ts`) уже
существовал, но нигде не вызывался — подключил его во ВСЕХ местах, где создаётся запись или событие:

- `src/domain/rules/booking-flow.ts` (`planBooking`, единый поток журнала/виджета/приложения): после проверки
  окна мастера теперь считает нужные ресурсы — по `Resource.serviceIds`, пересекающимся с услугами записи, в
  локации записи — и подбирает по одному свободному экземпляру каждого (`pickFreeInstances`); ручной выбор
  администратора (`input.resourceIds`, F-16-013) проверяется на занятость (`checkInstancesFree`) вместо слепой
  подстановки. Нет свободного экземпляра — новый код ошибки `resource_unavailable` (добавлен в
  `PlaceBookingError`, `PLACE_BOOKING_ERRORS`, `messages/{en,ru}/common.json → bookingErrors`).
- `src/api/online.ts:785` (`createOnlineBooking`, виджет/приложение — отдельный путь создания записи, не через
  `planBooking`): был жёстко прописан `resourceIds: []`; теперь перед созданием зовёт
  `pickFreeResourceInstances` (готовая обёртка `src/api/resources.ts`) и бросает `resource_unavailable`, если
  ресурс занят — повторная проверка прямо перед записью, как у окна мастера чуть выше по коду.
- `src/areas/resources/EventCreateScreen.tsx` (создание группового события): тоже слал `resourceIds: []` —
  теперь подбирает свободные экземпляры для услуги события тем же `pickFreeResourceInstances` (мягко —
  без ресурса, если не хватило, событие всё равно создаётся: у F-16 в ТЗ нет требования блокировать создание
  события по ресурсу, только запись на него).

Проверено вручную (демо-персоны `?demo=owner-fitness`): у ресурса «Кресло педикюра» 2 экземпляра — третья
одновременная запись на пересекающееся время теперь получает `resource_unavailable` вместо тихого создания.

**Не мой путь, нашёл и не правил** (`qa/requests/resources.md`, запись 2026-09-26): `resourcesAvailable()` в
`src/api/schedule/slots.ts` (раздел `schedule`) сравнивает `booking.resourceIds` (id **экземпляров**) с id
самого ресурса — фильтр слотов виджета остаётся дырявым (может ПОКАЗАТЬ окно, которое теперь сама запись
отклонит с `resource_unavailable`; дыры в данных нет — только в UX «увидел время → выбрал → ошибка»).

### Значок «другой посетитель» у нового участника (F-16-051)

`booking-flow.ts`: `visitorName` раньше подставлялся из `who.name` при ЛЮБОЙ записи по телефону, даже если
карточка клиента только что заводится этим же именем (`AddParticipantSheet` формы добавления участника нет
поля visitorName вовсе — баг подтверждён). Теперь `visitorName` ставится только когда найдена СУЩЕСТВУЮЩАЯ
карточка (`client`) и введённое имя от неё отличается — это и есть «другой посетитель» по смыслу F-01-127.
Новый участник (новая карточка) значка больше не получает.

### Нельзя уменьшить места ниже занятых (F-16-044)

Сама UI-блокировка (`capacityBelowParticipants`, дизейблит сохранение + текст ошибки) уже была на месте и
работает. Но `taken` считался через `seatsTaken()`, которая суммировала ВСЕ (включая отменённые/неявку)
брони события — значит отменённые места ошибочно держали лимит и не давали уменьшить вместимость, а событие
могло показываться «заполненным», хотя часть мест освободилась отменой. Поправил `seatsTaken()`
(`src/api/resources.ts`) — считает только `occupiesTime()`-брони (не отменённые, не неявка); тот же счётчик
используют «мест занято» на карточке события и проверка `group_full` при добавлении участника.
