## assumed (додумано)

- Слово подтверждения увольнения — `DISMISS`, удаления — `DELETE` (по справке Altegio, F-10-155); проверка
  делается на клиенте (как и раньше было с вводом имени), без учёта регистра.
- Роль-шаблон хранится в своём срезе (`staff.access[staffId].roleTemplateId`), core `StaffRole`
  (`owner`/`admin`/`master`) не менялся — трогать core.ts не стал без просьбы; 8 шаблонов — «надстройка» с
  описаниями, привязанная к одному из трёх базовых уровней.
- «Будущие записи» в окне увольнения считаю напрямую по `core.bookings` (staffId + дата ≥ сегодня + статус не
  отменён/неявка) — отдельного счётчика зарплаты (F-10-042 п. 2, «не выплачена — предупреждение») не строил:
  payroll ещё не даёт API для этого в срезе staff; оставил только пункт про записи.
- Восстановление (F-10-044): «24 часа» считаю по дате увольнения/удаления (только день, без времени —
  `today()`), поэтому в демо-данных окно «сразу» действует буквально в день события, а не 24 полных часа —
  для мока это ближе к «в тот же день» и достаточно, чтобы показать правило и оба состояния (сразу / заблокировано).
- Кандидаты для «Перенести доступ» (F-10-045) — сотрудники со статусом отличным от `active` (кроме владельца);
  точного признака «доступ выключен» на уровне списка (без отдельного запроса на сервер по каждому) не было,
  использовал статус как прокси.
- «Настроить права доступа» и выбор роли в форме добавления — не блокируют сохранение сотрудника, если роль
  не выбрана явно: по умолчанию «Специалист» (мастер) / «Администратор» (админ), как в ТЗ.
- Приглашение с email на уже существующий аккаунт (F-10-020, «подключить к локации, а не создать бизнес») —
  не смоделировано (у нас нет отдельной сущности «аккаунт человека» вне Staff); оставлено как есть до появления
  этой сущности.
