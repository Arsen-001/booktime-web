## Готово (`done`)

Все пункты «Готово, когда» выполнены и проверены на моковых данных (issue→список→reload сохраняет
состояние — проверено сценарием Playwright, скрин `qa/shots/scenarios/…after-reload.png`):

  (окно записи использует тот же хост `clientCard`, не отдельный экран — см. ТЗ «Где»). Форма
  показывается, только если у бизнеса есть хоть один тип карты; список типов на форме исключает уже

- **F-06-052** — номер карты: пустое поле генерирует уникальный 16-значный номер; повтор уже
  занятого номера отклоняется (`ApiError('validation')` → тост «номер уже есть»).
- **F-06-053** — вкладка «Лояльность»: карты клиента с плитками Кэшбэк/Макс.%/Макс.фикс.; отдельно
  сертификаты и абонементы (эти блоки уже были построены в b01–b03).
- **F-06-054** — «Развернуть» у карты: история операций (переиспользован `getCard`) + акции карты +
  подсказка сгорания бонусов (из `burnDays` типа карты).
- **F-06-055** — ручное начисление/списание: две иконки на карте открывают модалку суммы; баланс
  меняется, в истории — «Ручное пополнение»/«Ручное списание» (типы `manualTopup`/`manualCharge` уже
  были в домене, использованы как есть).
- **F-06-056** — удаление карты: подтверждение через `useConfirm()`, карта пропадает из вкладки.
- **F-06-060** — «Лояльность» в карточке клиента сети: компонент не фильтрует по локации (только по
  `businessId`), поэтому владелец сети видит карты/сертификаты/абонементы клиента по всем филиалам в
  одной карточке без доп. работы.
- **F-06-061 / F-06-193** — блок «Лояльность» в окне записи (`bookingWindow:loyalty`, раньше был
  заглушкой): карты с балансом, активные абонементы (остаток визитов) и сертификаты клиента —
  ВСЕГДА клиента-владельца номера (`draft.clientId`), что по ТЗ верно и для визита «за другого
  посетителя» (F-06-193, бонус пачки). Без клиента в записи блок не рендерится (компонент отдельно
  проверяет F-06-066 «без клиента лояльности нет»).
- **F-06-070** — начисление кэшбэка после оплаты: `accrueCashbackForBooking` вызывается шагом
  «после сохранения» (`registerAfterSave`) при статусе записи «Клиент пришёл» с ненулевой суммой;
  идемпотентно по `bookingId` (повторное сохранение не задваивает начисление — проверено логикой, поле
  `bookingId` добавлено в `LoyaltyTransaction`); результат виден в развёрнутой карте (транзакция
  «Начисление по программам лояльности», помечено тем же data-f).
- **F-06-095 / F-06-197** — продажа сертификата: модалка «Продать сертификат» на `/biz/loyalty/certificates`
  — тип, клиент по телефону (поиск `findClientByPhone`), код (вручную или кнопкой генерации, обязателен
  кроме именного типа — `allowNoCode`), цена/скидка/продавец (`soldPrice`/`discountPercent`/`sellerId`
  добавлены в `Certificate`). Именной без кода требует клиента. Пустое состояние «Создайте первый
  сертификат» при нуле типов.
- **F-06-099** — правка баланса/срока сертификата: уже была в b03 (`adjustCertificate` в карточке
  клиента), в этой пачке только добавлен `data-f`.
- **F-06-122 / F-06-197** — продажа абонемента: аналогичная модалка на `/biz/loyalty/memberships`,
  клиент обязателен (абонемент всегда именной), код обязателен кроме типов с «продажа без кода»; статус
  сразу «Активен» при `activationMode='onSale'`, иначе «Выдан»; те же поля цены/скидки/продавца
  (`Membership.soldPrice/discountPercent/sellerId`); пустое состояние «Создайте первый абонемент».

## Додумано (`assumed`)

- Номер карты при генерации: 16 цифр, первые 7 — детерминированный хеш `businessId` (условная
  имитация «номера сети» из спецификации), остальные 9 — случайные; коллизии проверяются и
  перегенерируются.
- «Макс. % скидки»/«Макс. фикс. скидка» новой карты — вычисляются как наибольшее значение среди акций,
  уже привязанных к её типу карты (в ТЗ это не описано явно, только показано как готовое поле в
  снимках).
- Продавец (`sellerId`) в продаже сертификата/абонемента — необязательное поле, `listStaffBrief`
  используется для выбора (в проекте нет отдельного «окна продажи товара», поэтому список сотрудников
  и склад — не выбираются полноценной панелью, а простым select).
- Локация продажи (`locationId`) в модалках продажи — берётся автоматически из текущей активной
  локации персоны (`activeLocationIds[0]`), без отдельного выбора склада/локации в форме (в проекте нет
  отдельного «окна продажи товара» — F-06-197 полностью, со шапкой даты/времени/склада, не строился;
  сделана упрощённая, но рабочая продажа).
- Начисление кэшбэка (F-06-070) — берёт первую подходящую акцию `kind.startsWith('cashback')` с
  `valueType='percent'` для каждой карты клиента; таблицы порогов накопительных акций не учтены (в этой
  пачке накопительная логика не пересчитывалась, только плоский % от суммы визита).
- F-06-197 «продажа записывается на выбранного сотрудника и видна в его статистике» — сотрудник
  сохраняется в `sellerId`, но отчёты/статистика по сотрудникам (раздел «Зарплата»/«Отчёты») не мои
  пути и не проверялись/не дополнялись.
