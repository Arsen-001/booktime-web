## Что исправлено

### F-00-064 · Повторяющиеся записи — block + major

**Было:** создание серии («каждые N дней» и «по дню недели») иногда падало необработанным
`ApiError('slot_taken')`: тост «Не удалось сохранить запись», модалка не закрывалась и оставалась с
введёнными данными, часть occurrences всё же успевала создаться до сбоя. Плюс предупреждения
`[mock-db] обращение к базе вне request()` из `resolveOccurrence()`.

**Корень (проверено кодом и живым прогоном, не гипотеза):**
1. `NewSeriesModal.save()` всегда слал `durationMin: 30` в `createSeries`, вместо настоящей длительности
   выбранной услуги. Наша собственная предварительная проверка занятости (`resolveOccurrence`) считала
   окно по этой выдуманной длительности, а настоящая проверка при создании (`placeBooking` → `planBooking`)
   берёт длительность из карточки услуги (`linesDuration`) — если услуга длиннее 30 мин, «свободно» по
   нашей прикидке расходилось с «занято» у настоящей проверки → `ApiError('slot_taken')` наружу без обработки.
2. `resolveOccurrence()` считал занятость своим упрощённым сравнением интервалов (`overlapsBooking`, без
   технологического запаса `bufferAfterMin`), а настоящая проверка (`checkSlot`) запас учитывает — второе
   расхождение той же природы.
3. Сама проверка (`readCore()`) читалась в обход `request()` — отсюда предупреждения `[mock-db]`.

**Правка (`src/api/schedule.ts`, `src/areas/schedule/series/SeriesScreen.tsx`):**
- `resolveOccurrence()` теперь вызывает ТУ ЖЕ функцию `checkSlot()` (`@/domain/rules/busy`), с тем же
  `bufferAfterMin` (взят из карточки услуги) и тем же режимом («journal»: без проверки часов/прошлого,
  как и в настоящем `placeBooking`) — предварительная проверка и настоящая теперь совпадают по построению,
  а не «похожи». Читается через `request()` — предупреждение `[mock-db]` для этого места ушло.
- `NewSeriesModal.save()` берёт `durationMin` из выбранной услуги (`servicesQuery.data`), а не хардкодит 30.
- На случай остаточной гонки (кто-то другой создал запись на то же время между проверкой и записью,
  возможно в другой вкладке) `generateOccurrences`/`resolveAndCreateOccurrence` ловит `ApiError` от
  `createQuickBooking` и, вместо падения всей серии, едет на следующий день (как «попало на занятое —
  ближайшее свободное» из «Готово, когда» этой функции), и только исчерпав горизонт сдвига
  (`SERIES_MAX_SHIFT_DAYS`) — пропускает эту одну дату, не всю серию.
- Заодно убрал предупреждения `[mock-db]` у соседних общих хелперов этого же файла — `setCells`,
  `restoreCells`, `writeScheduleOverrides`, `copySchedule` (один снимок базы на всю пачку через `request()`
  вместо `readCore()` на каждого сотрудника вне запроса; `writeScheduleOverrides` принимает уже найденный
  `existing` параметром вместо повторного чтения внутри). Экономия: раньше `setCells` читал базу N раз (по
  сотруднику) вне `request()`, теперь — один раз, так дешевле, а не дороже.

**Проверено живьём:** headless-прогон через `/biz/schedule/series` (master/nails/ru/desktop): «По дню
недели» — создаётся и закрывается модалка за ~6–7 с, 0 ошибок консоли; «Каждые N дней» (стресс: персона
`master` с плотным календарём) — создаётся без падения и без ошибок консоли, но на этой конкретной
плотной демо-персоне может занимать долго (см. «Что не доделано»). tsc/eslint по `src/api/schedule.ts` и
`SeriesScreen.tsx` — чисто.

### F-02-020 · «Убрать из графика» — major

**Было:** после подтверждения и тоста об успехе карточка сотрудника продолжала показывать старую дату
конца графика и кнопку «Убрать из графика», как будто ничего не изменилось.

**Корень:** `removeStaffFromSchedule()` закрывал дни (тип «Нерабочий день»), но не трогал поле
`WorkSchedule.openUntil`, а именно его читает `getScheduleEnd()` — отсюда старая дата не исчезала.

**Правка (`src/api/schedule.ts`):** после `deleteCells` дополнительно чистит `openUntil` во всех
расписаниях этого сотрудника (`coreUpdate('schedules', id, { openUntil: undefined })`).

**Проверено живьём:** `/dev/ext/staffCard/schedule` (owner/nails/ru/desktop) — до: «График есть до
2026-10-25»; после подтверждения диалога «Убрать из графика?» → «Всё равно убрать»: тост «Сотрудник снят
с графика», блок мгновенно показывает «Графика нет» (см. скриншот `/tmp/scn-staffcard3` в этой сессии).
0 ошибок консоли.

### F-00-055 · Напоминание «откройте окна на неделю» — minor

**Было:** баннер показывался всегда при «занято + пустая неделя», без привязки к дню недели «воскресенье»
из ТЗ.

**Правка (`src/api/schedule.ts`, `hasEmptyNextWeek`):** добавлено условие `weekdayIndex(from) === 6`
(воскресенье, по принятой в проекте нумерации 0=понедельник…6=воскресенье) — баннер теперь показывается
только по воскресеньям, как в «Готово, когда» ТЗ.

**Не проверено живым скриншотом:** сегодня в системе пятница (25.09.2026), а в проекте нет способа
подменить «сегодня» для демо (проверено — нет `?demo=`-параметра и API для фейковой даты). Проверено
чтением кода и логики (`weekdayIndex` = 0 пн…6 вс, подтверждено `src/lib/date.ts`), но не скриншотом в
реальное воскресенье. См. `assumed`.

## Что НЕ доделано (partial)

- **F-00-064, скорость.** На демо-персоне `master` (плотный, почти полностью занятый календарь) серия
  «каждые 3 дня» на горизонте 6 недель (14 повторов) может создаваться десятки секунд (замерено:
  6.6 с у «по дню недели» с ~6 повторами, но 20–50 с у «каждые N дней» с частыми конфликтами на этой
  плотной персоне) — это не крах и не ошибка (0 ошибок консоли, тост в итоге показывает успех), а
  следствие того, что каждый повтор при конфликте честно перепроверяет свободное время по-настоящему
  (`checkSlot`) на плотном календаре. Находка про скорость не входила в список дефектов и `speed-*`
  замеры вне обязательного списка правил раздела — не трогал специально, но фиксирую как источник для
  будущего `ux-best`/`speed` замера: имеет смысл либо не звать реальный `checkSlot` при явно свободных
  дальних датах (быстрый локальный предфильтр + редкая точная проверка), либо распараллелить создание
  occurrences, если движок это позволит.
- **F-02-016 (`/biz/schedule/print`), F-02-030/F-02-065 (`/biz/schedule/settings`), F-00-062
  (`/biz/schedule/new`)** — эти маршруты из плана b03 отвечают 404 (страниц ещё нет в `src/app/biz/schedule/`).
  Это не входило в 4 присланных дефекта и не было сломано этой правкой — экраны, судя по всему, ещё не
  строились. Не трогал в рамках этой починки (задача — 4 конкретных дефекта), но раз пачка называет их
  b03 — оставляю как открытый пробел на следующую сборку.
