## F-14-009 (major) — «Мои мастера» может раскрывать CRM-запись

**Код уже верен.** `listBookedMasters()` в `src/api/client.ts:221-240` фильтрует по
`SELF_BOOKED_SOURCES = ['app', 'link', 'widget']` — запись, заведённая администратором вручную
(`source: 'journal'`/`'phone'`), в выборку попасть не может. Более того, в сидах `Booking.appUserId`
в принципе не проставляется, если `source !== 'app'` (`src/mock/seed/bookings.ts` → `place()`).
Правило соблюдается по конструкции.

**Почему измеритель всё равно прав считать это дефектом.** Скриншот (`home__client-nails-ru-light-phone.png`,
персона client/nails) показывает среди 4 карточек «Мои мастера» двоих из Atam Dental — Карен
Мелконян и Седа Адамян. Проверил сид: у демо-клиента (`appUserId: 'au_01'`) в `demoPlan`
(`src/mock/seed/bookings.ts:397-426`) это **настоящие** self-booked записи (`source: 'app'`) —
демосценарий специально возит клиента через 4 сферы. Так что на этом конкретном экране показанное
верно. Но в сиде **нет ни одной** контрпримерной CRM-записи (`source: 'journal'`/`'phone'`, без
`appUserId`) на другого мастера того же бизнеса — а значит, ни замер, ни человек глазами не могут
отличить «правило соблюдается» от «правило совпало с данными случайно». Дефект в доказуемости, не
в поведении.

**Что сделал.** Точка проверки (`src/api/client.ts`) — в моих путях и уже правильная, менять
нечего. Контрпример нужно завести в `src/mock/seed/bookings.ts` — это фундамент
(`src/mock/seed/**`, вне `src/areas/client/**`, см. `CONVENTIONS.md` §1), сам не трогаю. Записал
точную просьбу в `qa/requests/client.md`: добавить в Atam Dental запись клиента `au_01` у другого
мастера бизнеса (`ST.atamAshot`) с `source: 'journal'`, без `appUserId` — после этого замер сможет
проверить, что Ашот Торосян в «Моих мастерах» не появляется, хотя его бизнес знает номер клиента.

## «multiple» (minor) — низкий охват `data-f` в пачке b01

Перепроверил все 28 F-id пачки b01 через `node scripts/fids.mjs --area client`:
`F-00-001, 002, 003, 005, 008, 010, 031, 032, 036, 104, 105, 106, 108, 109, 110, 111, 112, 117, 123,
172, 175` и `F-14-006, 007, 008, 009, 010, 028, 030`.

Не размечен только один — **F-00-036** («Один вход для клиента и мастера — не решено»). Это не
экранная функция: по ТЗ (`00-our-decisions.md`, F-00-036) «Готово, когда» = «решение принято и
записано», а «У нас: наше решение — ждёт» — сам пункт спецификации говорит, что решения ещё нет.
Ставить `data-f` на переключатель «Я клиент / Мой бизнес», которого по спецификации не должно быть,
пока продуктовое решение не зафиксировано, значило бы подделать замер — не стал.

Остальные 27 из 28 пунктов пачки уже помечены (например `F-00-003`/`F-00-005` —
`src/app/(client)/layout.tsx:8`, `F-00-010` — в составе `data-f` секции «Мои мастера» в
`HomeScreen.tsx:84`) — видимо, предыдущий проход по этой же пачке уже это закрыл. Общая цифра
13.4% (33 из 246), которую называет дефект, — это охват **всего** раздела client (246 F-id из всех
подпакетов, включая не разобранные b02+), а не конкретно пачки b01; чинить её целиком вне этого
прохода не пытался, чтобы не выдавать чужие несделанные пачки за сделанные.
