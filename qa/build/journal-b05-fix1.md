# Журнал — пачка b05, починка дефектов (fix1)

Починка 12 дефектов из замера `qa/measure/journal/b05-…md` (пакет «Права, настройки «Цифрового
журнала», телефонные сценарии и редкое»): 3 block/major по правам и данным клиента, 1 major по
несуществующей точке входа F-01-036, 2 major по ложным data-f мобильного приложения, 5 minor.

## Что сделано

### Block

- **F-01-168 / F-01-178 / F-01-179 — доступ к `/biz/journal/settings`.** Раньше страница не проверяла
  роль вовсе (единственная защита — скрытый пункт меню); прямым переходом мастер видел и мог менять
  «Права доступа» любого сотрудника. Теперь `JournalSettingsScreen` проверяет `useCan('settings.manage')`
  (то же грубое право, которым владеет владелец/сеть/индивидуал — F-01-168 «Роль: владелец
  настраивает») и рендерит `EmptyState` «Нет доступа» вместо формы. Проверено `measure.mjs`: у
  master/admin страница — 3 узла (замок), у owner/individual — полная форма, на всех устройствах.

### Major

- **F-01-219 (частично — см. partial).**
- **F-01-036 — запись от бота/CRM.** Была только колонка «источник» в отчёте и тип `'external'` в
  ядре — ни одной реальной точки входа. Добавлена `createExternalBooking()`
  (`src/api/journal.ts`) поверх фундаментного `placeBooking()` (единый поток создания записи,
  `rules/booking-flow`): валидирует телефон и имя ДО вызова (`ApiError('phone_required'|'name_required')`),
  сама подбирает «любого свободного» мастера по занятости, если `staffId` не передан. Демо-кнопка
  «Запись от бота (демо)» на `/biz/journal/records` (data-f="F-01-036") показывает форму (имя,
  телефон, услуга, мастер/«любой свободный», дата, время) и реально создаёт запись — проверено
  сценарием: без телефона — ошибка «Без телефона бот запись создать не может» прямо под полем; с
  телефоном — запись создаётся, открывается в журнале, неотличима от ручной (тот же клиент найден по
  номеру, тот же UI окна записи), источник виден в «Записях». Интеграций в разделе «Интеграции»
  по-прежнему нет (не наш раздел) — это ожидаемо и не входит в F-01-036.
- **F-01-184 / F-01-185 — ложный data-f мобильного приложения.** Сняты с корневого `<div>`
  `JournalScreen.tsx` (весь экран был помечен функциями мобильного приложения Altegio, которого в
  проекте нет вовсе — Next.js веб-платформа). Наше решение (assumed, ниже): те же create/edit
  работают отзывчиво на телефоне 390×844 через общий стор — теги перенесены на реальные точки: кнопку
  «+ запись» (F-01-184) и Sheet окна записи в `BookingWindow.tsx` (F-01-185, там же уже работают
  статус/состав услуг/товаров/оплата/удаление, подтверждено предыдущими пачками).

### Minor

- **F-01-165 — ссылка на чат.** Всплывашка была голым текстом. Теперь показывает текст + ссылку
  «Открыть чат» (Next `Link`, ведёт на карточку клиента `?tab=calls`, если автосохранение лидов
  включено и клиент создан демо-функцией; иначе на список клиентов). Проверено сценарием — ссылка
  видна и кликабельна.
- **F-01-171 — вторая строка вместо телефона.** У визита «Записывает другого посетителя» без своей
  карточки клиента (`client` не найден, есть только `booking.visitorName`) `phoneLine` был `undefined`
  — в режиме «первая строка — телефон» первая строка молча пустела, а имя посетителя всплывало в
  «дополнительной» строке ниже. Добавлен `phoneOrVisitorFallback` (телефон, а когда его нет у
  посетителя — имя вместо пустоты) в первую строку; дополнительная строка больше не дублирует то же
  самое имя под пустой первой строкой.
- **F-01-172 — зона нажатия 20px.** Безлейбловый `Radio` (кастомный интервал минут) получил
  `className="min-w-11"` — зона нажатия `<label>` расширена до ≥44px по обеим осям, сам Radio-компонент
  (фундамент, `src/ui/Radio.tsx`) не тронут.
- **F-01-178 / F-01-180 — ограничение истории раньше гасило только Save/Delete.** Теперь при
  `isEdit && beyondHistory` тело окна записи (Tabs + три зоны) подменяется на замок с текстом
  «Запись вне разрешённого периода» — запись действительно не открывается, а не просто недоступна для
  сохранения. Footer (Cancel/Save) не трогали — Save и так был задизейблен через `canEditNow`.

## partial

- **F-01-219 — вкладка «Клиент» пустая у записи удалённого клиента.** Красные строки в «Записях»,
  «Всего визитов 0», незатронутая выручка — уже работали (пред. пачки, не трогал). Сама пустая вкладка
  «Клиент» в окне записи — вклад раздела **clients** в хост `bookingWindow`
  (`src/areas/clients/extensions/BookingWindow.tsx`, `if (rowQ.isError || !rowQ.data) return null;`),
  журналу этот файл не принадлежит (CONVENTIONS §1 — вклад в чужой хост принадлежит контрибьютору).
  Просьба с точным местом и что нужно поправить — `qa/requests/journal.md` (запись от 2026-09-25,
  «F-01-219: вкладка «Клиент»…»). Третий пункт «Готово, когда» (новый клиент с тем же номером получает
  прежнюю историю) не проверен в этой пачке вовсе — нужен отдельный прогон.
- **F-01-168 / F-01-178 / F-01-179 — остальные пункты.** Гейт доступа (сам block-дефект) закрыт и
  проверен. Не переприверял в этой пачке: «сотрудник с правом «только свои» видит только свою
  колонку», «без права телефонов — маска в окне записи» (оба — код прошлых пачек, не менял),
  «ограничение истории «7 дней»» проверено только логикой (нет сид-данных со старыми записями для
  живого прогона — то же ограничение, что отмечал прошлый цикл).
- **F-01-172 — сама механика склейки визитов.** «Готово, когда» этой функции — про поведение
  (разрыв 10 мин у клиента = один визит, 20 мин = два), не про UI; я поправил только зону нажатия
  (дефект измерителя), логику склейки в этой пачке не проверял.

## assumed

- F-01-184/185: в проекте нет отдельного мобильного приложения (не наш и не чей-либо ещё раздел его
  не строит — вся платформа веб-first). Решение: считать «то же самое, отзывчиво на телефоне»
  эквивалентом функций мобильного приложения Altegio, а не строить фиктивное отдельное приложение.
  Если владелец захочет иначе — это решение можно пересмотреть, вопрос не настолько денежный/спорный,
  чтобы копить в `qa/questions/`.
- F-01-165: ссылка ведёт на карточку клиента только когда есть реальный `clientId` (демо создало лид
  через «Сохранять новых клиентов из чата»); без него — на список клиентов (чат как отдельный экран у
  нас не строится, «Интеграции» не наш раздел).
- F-01-036: «любой свободный» мастер подбирается по занятости среди `service.staffIds`; рабочие часы
  не проверяются (как и в остальной части журнала при создании из сетки — двойная запись невозможна,
  но вне часов создать можно, F-01-215).
