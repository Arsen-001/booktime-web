# Раздел loyalty — починка дефектов пачки b02 (второй заход), 25.09.2026

Пачка измерителя: b02 «Формы: тип карты и мастер акции» — F-06-021…028, 030, 032…048, 050, 082.
Задача: починить два найденных дефекта (F-06-050 major, F-06-041 minor).

## Что исправлено

### F-06-050 (major) · Заблокированные поля в правке акции

Было: секции «1. Название и тип» и «2. Вид» в `/biz/loyalty/promotions/[id]` были полностью
кликабельны — ТЗ требует «заблокированные поля видны как недоступные», а какие именно поля
блокируются — не сказано в справке (❓ в ТЗ).

Решение (assumed, т.к. справка не перечисляет): заблокировали именно **тип акции** (скидка/бонус) и
**вид** (какой из 4+4 вариантов) — это структурные поля, от которых зависит вся логика расчёта в
шаге 3 («Способ расчёта»); менять их после того, как по акции уже могли начаться начисления,
семантически ломает историю. Название, правила, область действия и график остаются полностью
редактируемыми.

- `Section1NameType` и `Section2Kind` (`src/areas/loyalty/promotions/PromotionFormSections.tsx`)
  получили проп `locked?: boolean`:
  - выбранный вариант остаётся виден и отмечен, недоступен для переключения (`ChoiceOption.disabled`
    на всех вариантах, кроме уже выбранного — сам выбранный тоже не даёт переключиться, `onValueChange`
    игнорирует клик при `locked`);
  - под полем — пояснение почему («Нельзя изменить после создания акции — начисления уже считаются
    по этому типу/виду»), новые ключи `familyLockedHint` / `kindLockedHint` в `messages/{ru,en}/loyalty.json`.
- `PromotionEditScreen.tsx` передаёt `locked` в обе секции; мастер создания (`PromotionWizardScreen.tsx`)
  использует те же секции без `locked` — там поля обычные.
- Живой снимок `/biz/loyalty/promotions/[id]`: «Тип акции» и «Вид» показывают выбранный вариант с
  галочкой в рамке primary, второй вариант — серый, `disabled`, курсор `not-allowed`.

### F-06-041 (minor) · Продано/Оплачено не расходились в демо-данных

Было: формула в `getCardSoldPaid` (`src/api/loyalty.ts:143-159`) верна, но конкретная проверенная
карта (№1074) показывала Продано = Оплачено = 36 500 — списывающая транзакция (`promoDiscount`)
создавалась только для клиентов, чей хеш id делился на 5, поэтому расхождение было не гарантировано
и не нашлось за отведённое время.

Решение — `src/mock/slices/loyalty.ts`: карты и так выдаются только клиентам с чётным хешем (более
ранний фильтр `h % 2 !== 0` → return), поэтому условие `if (h % 5 === 0)` заменено на безусловный блок
— теперь **у каждой выданной карты** есть списывающая транзакция `promoDiscount`, и её сумма гарантированно
не нулевая (`-(((h % 8) + 1) * 300)` вместо `-((h % 8) * 300)`, где `(h % 8)` мог быть 0).

- Живой снимок карты № 1074 (та самая, что не удалось увидеть в первом заходе): «Продано 36 500 ֏» /
  «Оплачено 36 200 ֏» — расхождение видно на экране, без чтения кода.
