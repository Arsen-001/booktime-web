# online · g2-2-fix2 · починка дефектов после измерения g2-2-2

Роль — сборщик раздела `online`. Измеритель прислал 2 дефекта после проверки доделки g2-2
(F-03-103, F-03-106, F-00-067, F-00-068, F-00-077, F-03-068, F-03-128, F-03-131) — чинил оба.

## Дефект 1 — F-00-067 (major): клиент не получает решение мастера без ручной перезагрузки

**Причина (нашёл, не было в отчёте измерителя):** предыдущая правка (fix1) опрашивала `q.refetch()`
раз в 15 с, но моковая база — `zustand`-стор со `skipHydration: true` (`src/mock/db.ts`, общий файл):
читается из `localStorage` ОДИН РАЗ при загрузке вкладки, дальше живёт только в памяти этой вкладки.
Вкладка мастера (кабинет бизнеса), подтверждая заявку, пишет в СВОЙ стор — вкладка клиента об этом не
узнаёт: `refetch()` просто перечитывал тот же устаревший fetcher. Единственное, что реально обновляло
статус, — полная перезагрузка страницы, ровно то, что подтвердил проверяющий.

Правка через ре-гидратацию чужого стора (`useDb.persist.rehydrate()`) технически работает, но требует
`import { useDb } from '@/mock/db'` — это запрещено ESLint'ом (`no-restricted-imports`, `NO_DIRECT_DB`
в `eslint.config.mjs`) для ЛЮБОГО файла `src/areas/**`/`src/api/**`, кроме `core.ts`/`area.ts`/
`request.ts`. Не мой файл, не обхожу линтер — вместо этого:

**Фикс (только мои файлы):** `respondToRequest` (`src/api/online.ts`) уже знает новый статус в момент
решения мастера — рассылаю его остальным вкладкам через `BroadcastChannel` (стандартный Web API между
вкладками одного источника, без бэкенда). Клиентские экраны (`BookingConfirmedScreen.tsx`,
`CabinetScreen.tsx`) слушают через новый `src/areas/online/lib/bookingDecisionChannel.ts` и мержат
статус ПРЯМО в кэш react-query (`queryClient.setQueriesData`), не пытаясь перечитать базу (это и была
причина, почему `refetch()` не помогал). Опрос раз в 15 с оставлен резервом (браузеры без
`BroadcastChannel`). Подробный докстринг — в самом файле канала и в `qa/requests/online.md`
(запись 2026-09-25 g2-2-fix2).

Файлы: `src/api/online.ts` (`respondToRequest`), `src/areas/online/lib/bookingDecisionChannel.ts`
(новый), `src/areas/online/booking/BookingConfirmedScreen.tsx`,
`src/areas/online/public/CabinetScreen.tsx`.

## Дефект 2 — F-03-106 (minor): промоблок открывает ссылку напрямую, окна с описанием нет

Спецификация (`03-online-booking.md`, «Логика»): «Только заголовок → некликабельный баннер; заголовок +
описание + картинка → кликабельный, открывает окно с описанием и кнопкой». В коде карточка сама не была
кликабельна — кликабельна только вложенная `<a target="_blank">`.

**Фикс:** `PublicBusinessPage.tsx` — карточка промоблока теперь сама кликабельна (как `<button>`), когда
есть `description` И `imageUrl`; клик открывает наш `Modal` (`@/ui/Modal`) с картинкой, описанием и
кнопкой-ссылкой (клик по кнопке в окне по-прежнему шлёт `clicked_promo_link`). Если картинки/описания
нет — карточка остаётся статичным баннером (как раньше), с прежней инлайн-ссылкой, если у блока есть
`buttonLink` без картинки.

Попутно заметил: сидовый (единственный `approved`) промоблок в демо-данных не имел ни `imageUrl`, ни
`buttonLink` — то есть кликабельное состояние физически не было демонстрируемо ни при каком прогоне.
Добавил оба поля в сид (`src/mock/slices/online.ts`, мой файл — `src/mock/slices/<area>.ts` по
`AREAS.md`): `imageUrl` — уже сгенерированное фото интерьера бизнеса (`firstBusiness.photos[0]`, без
новых сетевых образов), `buttonLink` — на публичную страницу самого бизнеса (`/b/<slug>`). Это не меняет
форму `PromoBlock` (поля и так были опциональны в типе) — только значения сида.

Файлы: `src/areas/online/public/PublicBusinessPage.tsx`, `src/mock/slices/online.ts`.

## Честная граница — прогон измерителя не переигран живьём до конца

tsc/eslint — чисто (ниже). Логику проверил вручную: собрал двухвкладочный прогон
`qa/scenarios/online/g2-2-fix2-crosstab.mjs` (вкладка A держит открытой `/b/<slug>/booking/<id>` БЕЗ
перезагрузки, вкладка B подтверждает ИМЕННО эту заявку на `/biz/online/requests`) — на нём же поймал и
починил баг в СВОЁМ тестовом скрипте (параметр демо-персоны в адресе — `?demo=…`, а не `?persona=…`,
`src/demo/settings.ts`), и подтвердил, что клик находит правильную карточку заявки по имени клиента
(`confirm button found: 1`, совпадение по конкретной заявке, не «первая попавшаяся»).

Довести этот прогон до финального зелёного результата (статус на вкладке A меняется без перезагрузки) не
успел: последние ~15 минут сборки `:3710` — общий дев-сервер держит `Build Error` из чужого файла
(`src/areas/client/book/BookScreen.tsx`, экспорт `consumeMembershipVisit` не найден в `@/lib/date`) — это
раздел `client`, не мой путь, не трогал и не обязан чинить (CONVENTIONS §0.1: «сломанная сборка роняет
дев-сервер ВСЕМ»); ошибка не проходила даже до `localStorage`-гидратации, поэтому ни `measure.mjs`, ни мой
сценарий не смогли отработать до конца ни разу за это время. Механизм проверен по коду и частично живым
действием (targeting, компиляция, tsc/eslint) — но финального скриншота «статус сменился без
перезагрузки» получить не успел из-за внешнего блокера. Если раздел будет перепроверяться и `:3710` к тому
моменту жив — `node qa/scenarios/online/g2-2-fix2-crosstab.mjs` даёт финальный ответ за один прогон.

## assumed

- «Кликабельно» для промоблока = есть `description` И `imageUrl` (буквально по «Логике» F-03-106: «заголовок
  + описание + картинка → кликабельный»); только заголовок+кнопка без картинки — остаётся некликабельным
  баннером с прежней инлайн-ссылкой.
- Канал `BroadcastChannel` шлёт только `{bookingId, status}` — минимально достаточно для того, чтобы
  клиентский экран сам домержил в уже загруженный им кэш; полный объект брони не гоняю между вкладками.
- Не трогал `getBookingStatusLog`/историю статуса на клиентском экране — BroadcastChannel патчит только
  поле `status`, история по-прежнему появится только при следующем реальном чтении (не блокер этого
  дефекта — измеритель жаловался на статус, не на историю).
