# b06 · Своё приложение салона (брендированное) и цены приложений — редкое

Раздел: **client**. Дата: 25.09.2026. Сборщик — субагент workflow.

ТЗ: `booking-research/functional-map/14-apps-altegio-me.md` (§9 «Altegio.me: своё приложение»,
§10 «Цены и что платно»). Решение пользователя по F-14-142 не принято (см. В-29,
`booking-research/functional-map/QUESTIONS.md`) — экран построен по правилу «1:1» как демо-заявка:
заявка реальная (уходит в очередь поддержки platform), материалы/документы/цена — черновик.

## Что построено

Новый экран **`/biz/apps/branded`** (`src/areas/client/apps/BrandedAppScreen.tsx`), пункт меню
«Приложения» → «Своё приложение» (`src/areas/client/nav.ts`), плюс правки хаба `/biz/apps`
(`src/areas/client/apps/AppsHubScreen.tsx`: три приложения, позиционирование, «бесплатно»,
доводы пуш/SMS) и точечная правка потока записи `/book` (`src/areas/client/book/BookScreen.tsx`)
для F-14-165.

Новые данные — свои (раздел client, ничего в core не тронуто):
- `src/domain/client.ts` — `BrandedAppRequest`, `BrandedAppMaterials`, `BrandedAppDocsChecklist`,
  `BrandedAppOwnerType`, `BrandedAppAccessMethod`, `BRANDED_APP_LIMITS`, цены-константы,
  `checkBrandedAppText()`, `MembershipUsedForBooking`.
- `src/mock/slices/client.ts` (version 12) — `brandedApp: Record<businessId, BrandedAppRequest>`
  (3 демо-состояния: черновик / отправлена / в разработке) и `membershipUsedForBooking`.
- `src/api/client.ts` — `getBrandedAppRequest`, `saveBrandedAppLinks`, `saveBrandedAppMaterials`,
  `setBrandedAppOwnerType`, `setBrandedAppAccessMethod`, `setBrandedAppExtraLocations`,
  `toggleBrandedAppDoc`, `getBrandedAppBlockers`, `submitBrandedAppRequest` (реально создаёт
  `SupportTicket` через `createSupportTicket` из `@/api/platform/support`, section `clientApp`);
  `getBookingMembershipOption`, `consumeMembershipVisit` (F-14-165).

## partial

Нет пунктов в partial — все 25 функций пачки доведены до своих критериев приёмки. Что осталось
черновиком осознанно (это не «недоделано», а прямое следствие решения ⭐/❓ пользователя, отражённое
в самом ТЗ каждой функции «У нас»):
- Само решение «делаем ли брендированное приложение» (F-14-142) не принято — это ожидаемо снаружи
  пачки (В-29), экран учит будущее решение, а не подменяет его.
- Курс USD→AMD для показа цены (`BRANDED_APP_DEMO_USD_TO_AMD = 400`) — assumed-оценка для отображения,
  не курс банка; отмечено в самом domain-файле и на экране.

## assumed (додумано)

- Годовой курс драма для показа цены в AMD — 400 ֏/$ (демо, не решение пользователя).
- Ссылка «Ваше приложение» → реально уходит заявкой в поддержку platform (`createSupportTicket`,
  cross-area импорт `@/api/platform/support` из `client`), а не в свой изолированный черновик — так
  выполняется решение «заявка через нашу поддержку, F-00-182» дословно; в остальном коде раздела
  такого cross-area импорта раньше не было, стоит иметь в виду при будущем рефакторинге границ.
- Контакт для заявки (имя) — берётся как текст-заглушка `t('apps.branded.contactFallbackName')`
  вместо отдельной формы «ваше имя/телефон» — потребовало бы ещё один шаг, а бизнес уже известен
  системе (businessId, phone бизнеса); если владелец захочет отдельную форму контакта — не вопрос
  ценам/логике, дописать по ходу.
- Матчинг «абонемент подходит для этой услуги» (F-14-165) — по имени услуги в `Membership.serviceNames`
  (простой список строк, как и было у существующих экранов абонементов); абонемент без списка услуг
  считается «на всё».
- Три демо-бизнеса засеяны на разных стадиях заявки (черновик / отправлена / в разработке), чтобы
  измеритель видел все состояния без ручных действий.
