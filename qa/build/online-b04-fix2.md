### F-03-116 · Плавающая гидратация на /biz/online/settings — minor → исследовано, дефекта в своих файлах не нашёл

Измеритель поймал `Hydration failed` + предупреждение о `setState` на несмонтированном компоненте 1 раз из
48 прогонов (owner/ru/phone), самовосстанавливается, воспроизвести стабильно не смог сам измеритель.

Проверил `SettingsScreen.tsx`: все 4 запроса (`staffQ`/`rulesQ`/`businessRulesQ`/`clientFieldsQ`) идут через
`enabled: ready && …`, до `ready` рисуется ОДИН И ТОТ ЖЕ `Skeleton` на сервере и на клиенте — ветвлений по
`typeof window`/`Math.random()`/`Date.now()` в рендере нет. `useCurrent()` (`src/demo/hooks.ts`) и
`useDb`/`useDbStatus` (`src/mock/db.ts`, оба не мои файлы) уже правильно устроены: `skipHydration: true`,
`ready` стартует `false` синхронно и на сервере, и на первом клиентском рендере. Ветвления, которое могло бы
разойтись между сервером и клиентом внутри `online`, не нашёл. Прогнал `measure.mjs` по `/biz/online/settings`
(owner/admin × ru × phone/desktop, 4 прохода) — 0 ошибок консоли на всех.

Записал наблюдение в `qa/requests/online.md` (не блокирую пачку, не мой код чинить) — гипотеза: гонка в
`@/api/request.ts` между несколькими одновременными `enabled`-запросами, которые все переключаются в момент,
когда `ready` становится `true`.

**Вывод:** дефекта в своих файлах не нашёл; экран уже SSR-безопасен по всем проверяемым признакам. Оставляю
как есть — минорный, самовосстанавливающийся, дев-режим, 1/48.

### F-03-102 · Гонка кадра у тумблера «Записаться ещё» — minor → исправлено

При двух быстрых кликах подряд (~300мс) `Switch` в `GroupBookingSection` (`LinkSettingsScreen.tsx`, секция
«Групповая запись», `data-f="F-03-102"`) читал `checked` прямо из кэша запроса (`rulesQ.data`), который
обновлялся только после ответа мока (400–1200мс задержка) — на кадр между кликами Switch мог показать
старое значение, пока зависимое поле уже успело отрисоваться по новому. Реальное состояние в базе было
верным всегда — гонка была только в кадре рендера.

Починил стандартным для проекта способом (`optimistic()` из `@/api/request.ts`, тот же паттерн, что уже
использует `platform/ads/AdDetailSheet.tsx`): `useApiMutation` для `updateGroupBookingRules` получил
`optimistic: optimistic<GroupBookingRules, …>(['online-group-rules', linkId], (old, patch) => ({...old,
...patch}))` — кэш запроса обновляется СРАЗУ по клику, `Switch` и зависимое поле читают один и тот же кэш,
поэтому больше не могут разойтись между собой. Дополнительно оба `Switch` (extraSeats/allowMultiEvent)
получили `disabled={saveMutation.isPending}` — второй клик не стартует, пока первый не долетел, что убирает
саму возможность гонки двух одновременных мутаций.

Файлы: `src/areas/online/links/LinkSettingsScreen.tsx` (`GroupBookingSection`), импорт `optimistic` из
`@/api/request`, тип `GroupBookingRules` из `@/domain/online`.

Проверено: tsc/eslint по файлу — чисто; `measure.mjs` по `/biz/online` и `/biz/online/settings` (owner/admin
× ru × phone/desktop) — 0 ошибок консоли; сценарий с переходом на `/biz/online/links/[id]` — `data-f`
включает `F-03-102`, `F-03-076`, страница открывается без ошибок.
