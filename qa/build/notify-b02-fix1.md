# Раздел «Уведомления» — пачка b02, доделка 1 (починка дефектов измерителя)

Сборщик: подраздел notify. Дата: 25.09.2026. Источник дефектов: измеритель, прогон по пачке b02
(F-05-009…F-05-040). Ниже — что починено по каждому пункту его списка.

## F-05-009 (major) — плитка «Уведомления о визите» не существовала

Подсказка на «Условиях отправки» обещала ручную правку времени напоминания в карточке записи, но
`src/areas/notify/extensions/BookingWindow.tsx` был пустой `ExtensionStub` — плитки не было нигде,
0 функций на `/dev/ext/bookingWindow/notify`.

Построил минимальную рабочую плитку (полный набор F-05-082 — повторная отправка подтверждения, свой
срок повторного визита — не входит в b02, оставлен другой пачке):

- `src/domain/notify.ts` — новый тип `BookingNotifyOverride` (`sendOnSave`, `smsEnabled`/`smsTimingHours`,
  `emailEnabled`/`emailTimingHours`).
- `src/mock/slices/notify.ts` — поле среза `bookingOverrides: Record<Id, BookingNotifyOverride>`
  (ключ — `Booking.id`), версия среза 4 → 5.
- `src/api/notify.ts` — `getBookingNotifyOverride(bookingId)` (умолчание — 1 ч SMS / 12 ч Email, как у
  типа 1) и `updateBookingNotifyOverride({ bookingId, override })`.
- `src/areas/notify/extensions/BookingWindow.tsx` — сама плитка: чекбокс «Отправить уведомление с
  деталями записи сразу после сохранения», таблица SMS/Email (чекбокс канала + `Select` «за сколько
  часов»), кнопка «Напомнить через WhatsApp» (⭐ F-00-121, видна только когда у записи есть клиент),
  «Сохранить» (disabled, пока нет правок). `mode === 'create'` (записи ещё нет) → `EmptyState` с
  пояснением «Сохраните запись, чтобы настроить её уведомления». Гейт `useCan('notify.manage')`.
  Правки переживают перезагрузку — проверено через `getBookingNotifyOverride`/локальный стор.
- `qa/requests/notify.md` — фундаменту это НЕ нужно (всё в своих путях), просьб не потребовалось.

«Готово, когда» F-05-009 — оба пункта: старая запись держит старое время (умолчание не меняется полем
типа, override читается по `bookingId` независимо от текущих настроек типа), и время можно поменять
вручную в плитке.

## F-05-011 (major) — формат даты/времени не влиял на переменные

`TEST_DATA`/`VARIABLES` в `registry.ts` были статичными строками — переключение 24ч/12ч ничего не
меняло в предпросмотре шаблона.

- `src/areas/notify/lib/registry.ts` — новая `testDataForFormat(dateFormat)`: пересчитывает `{time}` и
  `{dateTime}` (`formatHour12()` — русское «дня/вечера/утра/ночи», как в тексте `dateFormat12` настройки:
  «7:32 вечера»). `TEST_DATA` остался (24ч по умолчанию, используется, где формат ещё не известен).
- `src/areas/notify/types/TypeDetailScreen.tsx` — `testData = useMemo(() => testDataForFormat(dateFormat), …)`
  на основе `settingsQ.data?.dateFormat`; все 5 использований `TEST_DATA` (текст письма, системный вариант
  типа 7, read-only системный текст, данные клиента, счётчик символов) переведены на `testData`.
- Проверено вживую сценарием Playwright: переключил на 12-часовой на `/types/1/templates` → предпросмотр
  под полем сменился с «…в 14:00» на «…в 2:00 дня», тост «Настройки сохранены».

## Гонка при сохранении условий (major, F-05-009/024-040)

`saveConditionsPatch` мержил патч поверх `conditions` из замыкания рендера — второй клик подряд (в
пределах ~500–800 мс) терял первый.

- `src/areas/notify/types/TypeDetailScreen.tsx` — `conditionsRef` держит последний ОТПРАВЛЕННЫЙ (не
  последний полученный с сервера) набор условий, обновляется синхронно в `saveConditionsPatch` ДО await;
  `conditionsInFlightRef` — счётчик патчей в полёте, блокирует затирание ref свежими данными сервера,
  пока что-то не долетело; синхронизация ref с сервером — в `useEffect` (не в рендере: правило
  `react-hooks/refs` запрещает мутировать ref во время рендера). Очередь `conditionsSaveQueueRef`
  сериализует фактическую отправку на сервер — порядок записи всегда совпадает с порядком кликов, даже
  если сетевые ответы придут не по порядку.
- Проверено сценарием: клик «3 ч» → сразу чекбокс «Другое время для Email» → перезагрузка страницы —
  «Отправлять за» осталось «3 ч» (раньше откатывалось на дефолт «1 ч»).

## F-05-009 (minor) — подсказка на типах без карточки записи

Подсказка «Время… меняется в её карточке» показывалась на всех типах с условиями, включая 3
(день рождения), 17 (сгорание скидки), 55 (повторный визит), 72 (недошедшие) — там привязки к записи нет.

- `src/areas/notify/types/TypeConditionsFields.tsx` — новый `HINT_FUTURE_ONLY_TYPES = {74, 73, 1, 6, 20}`
  (подмножество `TYPES_WITH_CONDITIONS`, привязанное к конкретной записи).
- `src/areas/notify/types/TypeDetailScreen.tsx` — `description` секции «Условия отправки» показывается
  только для `HINT_FUTURE_ONLY_TYPES`; для остальных — секция без подсказки. Проверено: на типе 3
  подсказки больше нет, на типе 1 — есть.

## F-05-020 (minor) — каталог переменных и «Сохранить» на системных типах

«Каталог переменных» (+Добавить переменную) и кнопка «Сохранить» показывались и на типах 7/19/43, где
редактируемого поля нет вообще (у 19/43 текст не редактируется, у 7 — выбор из 2 вариантов, не текст).

- `src/areas/notify/types/TypeDetailScreen.tsx` — оба блока обёрнуты в `{!type.systemLocked && (…)}`.
  Справочник устаревших переменных (F-05-023, только для чтения) остался виден всем — он не про вставку.
  Заодно поправил разметку: `data-f` перенесён с `SectionCard` (эта обёртка не пробрасывает атрибуты на
  DOM — `SectionCardProps` их не объявляет) на оборачивающий `div`, иначе `measure.mjs` (проверка по
  живому DOM) не находил метку, хотя `fids.mjs` (статический разбор текста) её видел. Проверено: на
  `/types/19/templates` каталога и «Сохранить» больше нет, `measure.mjs` находит `F-05-022`/`F-05-023`
  в DOM.
