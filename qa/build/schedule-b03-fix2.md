# schedule — b03-fix2: почин находок (Действия мастера, повторы, права, редкое)

Чиню находки измерителя по пачке b03. Три находки, все проверены действием на живом сервере
(`scripts/measure.mjs` со сценариями кликов, скриншоты в `qa/shots/schedule-b03fix2*/`).

## F-00-059 · «Задерживаюсь» — не следующему клиенту (major) → **частично, честно**

Находка верна: `sendDelayNotice()` пишет уведомление ТОЛЬКО в свой срез
(`readArea('schedule').delayNotices[bookingId]`), следующий клиент его не видит.

Разобралась, почему это не чинится в одном файле: чтобы клиент реально увидел уведомление, оно должно
попасть в его ленту (`listNotifications` в `src/api/client.ts`, закрытый union `NotificationKind` в
`src/domain/client.ts`) — это чужой раздел (`client`), не мой путь. Общего шлюза «положить уведомление
клиенту из чужого раздела» в фундаменте нет (проверила — ни шины событий, ни публичной функции).

Что сделано:
- логика поиска «следующего клиента» (`getNextBookingForDelay`) и запись самого уведомления с
  `nextBookingId`/`minutes`/`sentAt` — верны и не тронуты, работают как задокументировано;
- заявка на недостающий кусок (новый `NotificationKind: 'master_delay'` + публичная функция в
  `src/api/client.ts`, которую сможет звать другой раздел) — в `qa/requests/schedule.md`
  (`## 2026-09-25 · b03-fix2: F-00-059 …`).

**Остаётся partial** — мастер видит бейдж у себя (единственное подтверждённое «Готово, когда» без правки
чужого раздела), клиент — нет, пока не появится п.1–2 из заявки.

## F-00-064 · Повторяющиеся записи — «зависает» без обратной связи (major) → **done**

Два независимых улучшения:

1. **Меньше сетевых вызовов на повтор.** `resolveOccurrence` (`src/api/schedule.ts`) раньше делала
   ОТДЕЛЬНЫЙ `request()` на часы дня (`getDayHours`) и ОТДЕЛЬНЫЙ на `checkSlot` — на каждую кандидат-дату.
   Объединила в один `request()` (чтение часов + проверка занятости внутри одной «сетевой» операции) —
   вдвое меньше вызовов на повтор без изменения логики (тот же `checkSlot`, тот же порядок проверок, тот
   же комментарий-предупреждение про гонки оставлен).
2. **Видимый прогресс вместо голого спиннера.** `createSeries`/`generateOccurrences` теперь принимают
   необязательный `onProgress(done, total)`, `SeriesScreen.tsx` показывает «Создаём записи: N из M» в
   футере модалки, пока идёт сохранение (кнопка «Отмена» заблокирована на это время).

Проверено действием (`qa/shots/schedule-b03fix2-seriescreate*/`): создала серию «по дню недели», прогресс
реально идёт кадр за кадром («1 из 6» → «3 из 6» → «4 из 6»), без ошибок консоли, без «сырых» ключей.

Копнула, почему один повтор всё равно занимает ~1.5–2.5 с при базовой задержке `request()` 150–400 мс
(`api: 'normal'`, не `'slow'`) — причина в фундаменте: `request()` (`src/api/request.ts`) делает
`snapshotDb()` (клон ВСЕЙ моковой базы) на каждый вызов, это не мой путь и не только моя проблема
(касается всех разделов). Заявка с предложением — `qa/requests/schedule.md`
(`## 2026-09-25 · b03-fix2: F-00-064 — остаточная медленность серии не в моём коде`).

Итог: «зависла» находка была верной по факту (спинер без индикатора), причина устранена в части, которая
мне принадлежит (меньше вызовов + видимый прогресс) — кнопка больше не выглядит зависшей, per CONVENTIONS
§0 «отклик на каждое действие». Остаточная длительность — стоимость фундамента, не моя.

## F-02-020 · «Убрать из графика» — confirm вместо 5-секундной отмены (minor) → **done**

Находка справедливо отметила: это не провал «Готово, когда» (сам вопрос помечен ❓ в 00-our-decisions.md),
но с 25.09 он уже решён «по описанию» в `functional-map/QUESTIONS.md` («Решили сами по описанию»,
F-02-020): **при будущих записях — окно подтверждения со списком/числом записей; без записей — «Отменить»
на 5 секунд**. Реализовала ровно это в `src/areas/schedule/extensions/StaffCard.tsx`:

- `handleRemoveClick` сначала зовёт `previewRemoveFromSchedule` (уже было);
- есть будущие записи → как раньше, `ConfirmDialog` с точным числом и кнопкой «Всё равно убрать»
  (необратимое действие — окно остаётся, это подтвердил и сам вопрос-по-умолчанию);
- нет будущих записей → `removeWithUndo()`: снимает с графика сразу, показывает toast с «Отменить» на
  5000 мс (тот же паттерн, что уже есть в `SchedulePanel.tsx` этого раздела — `snapshotCells`/
  `restoreCells`). Добавила `snapshotBeforeRemoveFromSchedule`/`restoreAfterRemoveFromSchedule` в
  `src/api/schedule.ts` (снимок ячеек графика + `openUntil`, откат обоих).

Проверено действием на двух сотрудниках:
- `st_nuri_ani` (23 будущие записи, `/dev/ext/staffCard/schedule`) → диалог подтверждения с «23» —
