найденных измерителем на доделке g3-1. До начала — прочитал `qa/measure/journal/` (кроме `b*-m*`/

попутно (ux-r5 №3, строка «Записей» не открывалась) — см. ниже.

## done (все пункты «Готово, когда» выполнены)

- **F-01-006** — переключатель локаций: `JournalScreen.tsx` считал `staff`/`bookings` по одному
  `businessId` (первому филиалу) даже когда выбрано «Все филиалы». Завёл `activeBusinessIds`
  (`'all'` → `businessIds` из `useCurrent()`, иначе один) и передаю его в оба запроса + `listBookings`
  теперь зовётся с `businessIds` (ядро уже поддерживало). Проверено снимком: сеть по умолчанию видит
  мастеров и записи всех филиалов.
- **F-01-181** (minor у измерителя) — фильтр «Отменённые» в `RecordsScreen.tsx` включал не только
  `deletedAt`, но и статусные отмены («не пришёл», «отменил клиент/мастер») — развёл: «Отменённые» =
  только удалённые (мягкое удаление), статусные остаются в «Не отменённые», как требует ТЗ.
- **F-01-121** — восстановления удалённой записи по справке Altegio нет (1310), но их же скрин
  намекает на «Восстановить»; вопрос записан в `qa/questions/journal.md` с решением по умолчанию.
  Реализовал: у удалённой строки в «Записях» карандаш/клик по карточке создаёт НОВУЮ запись с тем же
  клиентом/мастером/услугами/временем (снимок уже был в `extras[bookingId].deletion.restore` для
  5-секундного «Отменить» — тут просто читаю `Booking` напрямую), тост объясняет почему.
- **F-01-126** (своя половина) — «Отменить рабочий день»/«Удалить рабочие дни» с записями раньше
  ПОДТВЕРЖДАЛИ удаление (`force: true` после простого «ок») — записи оставались, день реально удалялся,
  вопреки «нельзя удалить рабочий день с записями, не переназначив их». Теперь это настоящий блок:
  диалог только объясняет и закрывается, ничего не удаляется (`DayGrid.handleCancelDay`,
  `WorkingDaysRangeModal`). Вторая половина (предупреждение при увольнении мастера) — раздел `staff`,
  не наш путь, см. **partial**.
- **F-01-146** — снимок политики оплаты: новый `PaymentPolicyBlock.tsx` в центре окна визита (под
  статусами) — сумма депозита, дедлайн бесплатной отмены (календарь зелёный/красный, точная дата по
  наведению), статус (ждёт/оплачена/удержана как штраф/прощена). Снимок читает сохранённый `booking`,
  не черновик — не пересчитывается при правке визита, как требует ТЗ.
- **F-01-116** — поздний перенос записи с внесённой предоплатой: `BookingWindow.handleSave` перед
  сохранением проверяет `freeCancelUntil()` (ядровое правило `domain/rules/booking-policy.ts`, дедлайн
  от ИСХОДНОГО времени) и спрашивает диалогом «удержать/простить», если время реально меняется и срок
  уже прошёл.
- **F-01-124** — «Не пришёл» с предоплатой: `BookingWindow.handleStatusChange` спрашивает тем же
  диалогом; по умолчанию (диалог закрыт без явного «Простить») — штраф считается удержанным, как
  требует ТЗ («не решил до полуночи — штраф применяется сам»; настоящего таймера до полуночи нет —
  бэкенда нет, дефолт срабатывает сразу при закрытии диалога, а не в полночь — см. assumed).
  Решение по обоим пишется в `extras[bookingId].prepaymentDecision` (`api/journal.ts:decidePrepayment`),
  реальными деньгами не двигает (F-00-126: только записываем).

## Заодно (§0.1, из ux-r5.md №3, не было отмечено)

Строка отчёта «Записи» не открывалась (`Table` без `onRowClick`) — единственное, зачем на этот экран
заходят. Добавил `onRowClick` (открывает запись / создаёт заново у удалённых, тем же путём, что и
карандаш; карандаш — `stopPropagation`, чтобы не дублировать переход). Это вскрыло невалидный HTML —
мобильная карточка `Table` оборачивает содержимое в `<button>`, когда есть `onRowClick`, а столбец
«карандаш» без явной `mobile`-роли попадал внутрь как ещё один `<button>` («cannot contain a nested
button», консоль/React hydration) — поставил `mobile: "hidden"` этому столбцу (на телефоне вся карточка
и так кликабельна). Остальные пункты ux-r5 №3 (поиск, период, пагинация, статус-бейджи, `extrasQuery`
по одному запросу на строку) — редизайн экрана целиком, отметил `⏳ позже` в файле, не влезает в бюджет
этой пачки.
