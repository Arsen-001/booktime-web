# client · b02 · fix1 — правка дефектов измерителя

Пачка b02 («Запись клиентом и «Мои записи»»). Ниже — что было не так и что сделано, по каждому найденному дефекту.

## F-00-092 (major) — «Ближайшие окна» считались по фиксированным 30 мин, а не по длительности услуги

**Было:** и в каталоге (`listCatalog`), и на карточке мастера (`MasterCardScreen`) ближайшие свободные окна
считались с `durationMin: 30` (константа `CATALOG_DEFAULT_DURATION`), а не длительностью реальной услуги.
Окно, показанное свободным, при попытке записаться отклонялось как «уже заняли» — потому что
`bookAppointment()` проверяет `stillFree` уже с реальной длительностью выбранной услуги.

**Правка:**
- `src/api/client.ts` — `listCatalog()`: окна теперь считаются с длительностью **самой долгой** из
  бронируемых услуг мастера (а не фиксированной), так что показанное окно годится для любой его услуги.
- `src/areas/client/masters/MasterCardScreen.tsx` — блок «Ближайшие окна» (`getNearestSlots`) считает так же:
  максимум длительности среди бронируемых услуг мастера, а не константу `30`.
- Заодно (F-00-004 «клик по окну сразу к подтверждению»): если у мастера **ровно одна** бронируемая
  услуга — ссылка на окно теперь несёт и `service=`, и поток `/book` пропускает шаг выбора услуги
  (существующая логика `BookScreen` это уже умела — не хватало только передачи параметра). Если услуг
  несколько — шаг выбора услуги остаётся (иначе непонятно, на какую услугу считать), но время, уже выбранное
  по окну, при этом гарантированно вмещает любую из них.

**Проверено:** сценарий `qa/scenarios/client-b02-fix1-nearest.json` — клик по ближайшему окну на карточке
мастера с 6 услугами (`st_nuri_ani`, максимум 120 мин) → выбор любой услуги → «Подтвердить запись» →
«Запись создана», без «окно уже заняли» (0 ошибок консоли, все 12 шагов сценария прошли).

## F-00-097 (major) — TypeError при прямом открытии записи с предоплатой

**Было:** `releaseExpiredPrepayments()` читала `readArea('client').prepaymentDeadline` и вызывалась
**синхронно**, до `request()` — то есть до того, как база вообще поднялась из localStorage (`dbReady()`).
При прямом заходе на `/bookings/[id]` (первая загрузка вкладки) срез `areas.client` ещё был пуст,
`prepaymentDeadline` — `undefined`, и `Object.entries(undefined)` падал `TypeError` прямо в
`getBooking()`/`listMyBookings()`. Это и объясняет воспроизведённую «аномально долгую загрузку» (16–34 с) —
на самом деле экран падал и Next пере-монтировал дерево, а не «висел».

**Правка:** `src/api/client.ts` — `releaseExpiredPrepayments()` теперь `async` и завёрнута в `request()`
(та же обёртка, что у всех остальных функций api-фасада) — она сама ждёт `dbReady()` до выполнения; `?? {}`
на чтении `prepaymentDeadline` вдобавок защищает от старой сохранённой версии среза без этого поля.
Оба вызывающих места (`listMyBookings`, `getBooking`) теперь `await` её перед своим собственным `request()`.

**Проверено:** `node scripts/measure.mjs --routes "/bookings/bk_0081,/bookings/bk_0083" --persona client
--lang ru,en,hy --device phone,desktop` — 12 страниц, **0 ошибок консоли**, 0 «висит загрузка». (Время
загрузки первой страницы каждого маршрута в dev всё ещё 6–30 с — это holodный компиль Turbopack самого
маршрута при первом обращении, не наш код: второй и следующий заход на тот же маршрут — единицы секунд;
воспроизведено на всех 12 комбинациях без единой ошибки.)

## F-14-011 (minor) — ссылка на компанию в карточке записи меньше 44px

**Было:** `Link` на `business.name` внутри `BookingDetailScreen` — инлайновый текст без `min-height`,
фактическая высота нажимаемой зоны 19px.

**Правка:** `src/areas/client/bookings/BookingDetailScreen.tsx` — добавлены `inline-flex min-h-11
items-center` (+ небольшой `px-1 -ml-1`, чтобы не сдвигать текст визуально). Зона нажатия теперь ≥ 44px,
подтверждено на снимках `qa/shots/client-b02-fix1/`.

## F-14-029 (minor, по сути расширено до полноценного фикса) — «Записаться» с карточки места вело к одной категории вместо общей формы

**Было:** кнопка «Записаться» на `PlaceCardScreen` брала «первого попавшегося» мастера места
(`primaryStaff`) и вела прямо в `/book?staff=<id>` — то есть на список услуг **этого одного мастера**, а
не «любую услугу компании», как требует ТЗ (F-14-029 «Готово, когда: открывает запись к этому бизнесу на
любую его услугу»).

**Правка:** добавлен режим `/book?business=<id>` (без `staff`):
- `src/app/(client)/book/page.tsx` — читает `?business=` и передаёт в `BookScreen`.
- `src/areas/client/book/BookScreen.tsx` — новый компонент `BusinessBookPicker`: если `staffId` не задан,
  но есть `businessId` — сначала список **всех** бронируемых услуг компании (все категории, как на
  карточке места), затем — мастер, который эту услугу делает (если он один — шаг пропускается
  автоматически), и переход на уже знакомый `/book?staff=&service=` поток.
- `src/areas/client/places/PlaceCardScreen.tsx` — кнопка «Записаться» ведёт на `/book?business=<id>`
  вместо `primaryStaff`.
- Локализация: добавлены ключи `book.masterTitle` / `book.masterTitleHint` в `messages/ru/client.json` и
  `messages/en/client.json` (перевод для `hy` не добавлен — см. «Замечено вне списка» ниже).

**Проверено:** сценарий `qa/scenarios/client-b02-fix1-placebook.json` на `biz_nuri` (7 услуг, несколько
мастеров-маникюрщиц) — «Записаться» → список услуг по категориям → выбор «Маникюр классический» → список
из 3 мастеров, которые её делают. 0 ошибок консоли на повторном прогоне (первый прогон словил чужую
500-ошибку из `journal/components/BookingWindow.tsx` — не мой файл, воспроизведена и на уже существующих
сценариях `client-b02-waitlist-place`/`client-book-guest`/`client-book-logged-in`, тоже ушла на повторном
прогоне — фон параллельной правки другого раздела, не связан с этой правкой).
