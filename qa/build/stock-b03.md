## Что построено

**Модель данных** (`src/domain/stock.ts`, `src/mock/slices/stock.ts`, version 4→5):
- `TechCard`/`TechCardLine` — техкарта (услуга × мастер, у каждого мастера своя), сид: 1-2 услуги на бизнес,
  до 3 мастеров каждая.
- `OperationDoc` расширен необязательными полями: `paymentMethod`, `extraLines` (абонементы/сертификаты в
  продаже), `autoWriteoff` (флаг автосписания), `cancelledAt` (отменённая продажа) — обратная совместимость
  сохранена (нет поля = старое поведение).
- `StockSettings` (`costMethod`, `forbidOnShortage` — задел под b04, `expiryWarningDays`).

**API** (`src/api/stock.ts`, +~650 строк):
- Техкарты: `listTechCards`, `listTechCardsForService`, `getTechCard`, `saveTechCard` (upsert по паре
  услуга+мастер), `deleteTechCard`, `getPackageTechCardLines` (F-08-040 — сумма техкарт входящих услуг).
- Автосписание: `ensureAutoWriteoffs` (идемпотентная синхронизация — у записи «пришёл» ровно один документ
  списания по техкартам, у прочих статусов документа нет; откат при смене статуса/удалении записи —
  F-08-042), `getBookingConsumables`, `getBookingConsumablesByService` (расходники по КАЖДОЙ строке визита
  отдельно, F-08-044), `addBookingConsumableLine`/`removeBookingConsumableLine` (ручная правка).
- Продажа: `createSaleOperation`, `updateSaleOperation`, `cancelSaleOperation` (возврат на склад отдельным
  документом прихода), `getReceiptData`.
- Настройки: `getStockSettings`/`updateStockSettings`; себестоимость: `createIncomeOperation` теперь считает
  либо «последняя цена», либо средневзвешенную (по настройке), `costPriceAt`/`getCostPriceAt` (себестоимость
  на дату операции, F-08-098).

**Экраны:**

## partial

- **F-08-071 (оплата лояльностью)** — выбор способа «Лояльность» в окне оплаты пишется в
  `paymentMethod`, но реального списания с депозита/баланса клиента не делает — в `loyalty` пока нет api
  «списать с депозита» (просьба №5 в `qa/plan/stock.md` уже сформулирована предыдущим планировщиком,
  повторно не пишу). Деньги в этом разделе и так только запись (⭐ F-00-126), поэтому это не блокирует
  «Готово, когда» продажи как документа, но сама сумма депозита клиента не уменьшается.
- **F-08-073 (отмена продажи с абонементом/сертификатом)** — возврат ТОВАРНЫХ строк на склад работает
  полностью (создаёт документ прихода). Абонемент/сертификат, проданные в той же продаже, отдельно не
  отзываются автоматически — `loyalty` не даёт api «отменить проданный абонемент/сертификат» вызовом извне;
  предупреждение об этом показано в тексте подтверждения отмены («абонементы и сертификаты этой продажи
  придётся снять отдельно в разделе «Лояльность»»).
- **F-08-097/F-08-098 (себестоимость)** — реализованы два метода (последняя цена / средневзвешенная) и
  функция себестоимости «на дату», но это приближение: при вводе прихода «задним числом» после более
  поздних приходов средневзвешенная не пересчитывается ретроспективно (документировано как assumed в коде).

## assumed

- Формат кода абонемента/сертификата — свободная строка, кнопка «Сгенерировать» даёт 6 символов
  `[A-Z0-9]` (`Math.random().toString(36)`), не привязан к формату loyalty (там UI сам решает валидность).
- Автосписание при статусе «пришёл» агрегирует расход одного товара по всем строкам визита в ОДНУ строку
  документа (для верного остатка), а «разными строками» (F-08-044) показывается отдельно, вычислением
  напрямую из техкарт по каждой строке визита (`getBookingConsumablesByService`) — не из хранимого документа.
- Возврат склада при отмене продажи не проверяет наличие места на складе (всегда можно вернуть) — это приход,
  ограничений по приходу в ТЗ нет.
- Оплата продажи (F-08-070) — свой шаг поверх api finance пока не подключён (просьба №4 из плана уже
  открыта предыдущим планировщиком): способ оплаты сохраняется в документе, финансовая операция отдельно не
  создаётся.
- `costMethod: 'average'` — средневзвешенная считается по остатку СКЛАДА В ЦЕЛОМ по бизнесу (все склады
  суммарно через `computeLevels`), не по конкретному складу прихода — упрощение, задокументировано в коде.
