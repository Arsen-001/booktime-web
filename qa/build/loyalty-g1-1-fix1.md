# loyalty · починка g1-1-fix1 (25.09.2026)

Чинил дефекты измерителя по доделке g1-1 (F-06-175/176/177/151/149/024…047/070/078…080/183/002/004/030/057/130/191/145/180).

## Исправлено (block/major)

- **F-06-057** (major) — повторная загрузка Excel с «-100» обнуляла баланс вместо уменьшения на 100.
  Причина: колонка читалась как абсолютное целевое значение всегда. Починка: значение с ведущим «-» —
  относительная дельта (`-100` → минус 100 к текущему балансу), без знака — как раньше, абсолютная цель.
  `src/areas/loyalty/CardsScreen.tsx`. Проверено живым сценарием: 4000 ֏ → загрузка «-100» → 3900 ֏.

- **F-06-130** (major) — `BulkImportModal` не был атомарен: одна ошибочная строка не откатывала уже
  импортированные валидные. Добавлен необязательный проп `onValidateRow` — все строки проверяются БЕЗ
  побочных эффектов первым проходом; при любой ошибке не импортируется ни одна строка. Подключено во
  все 4 места `BulkImportModal` в разделе (cards/memberships/certificates/deposits), не только
  memberships, где нашёл измеритель — общий компонент, общий дефект. Проверено сценарием: файл из 2
  строк (валидная + ошибка в типе) → «0 успешно, 2 с ошибкой», счётчик абонементов не изменился.

- **F-06-183** (major) — «акцию можно ограничить датами действия» было НЕ реализовано (было только
  повторяющееся расписание по дням недели/часам). Добавлены `Promotion.validFrom`/`validTo` (ISODate,
  включительно, `src/domain/loyalty.ts`), функции `isPromotionWithinDateRange`/`isPromotionActiveNow`
  (сочетают дату И расписание), новая секция «Период действия» на шаге 5 мастера акции (два `DatePicker`
  с перекрёстными `min`/`max`), поле в `PromotionInput`/`createPromotion`. Подключено в
  `listApplicablePromotions` (панель оплаты лояльностью на окне записи) — акция вне периода/расписания
  не предлагается как способ оплаты. **Не подключено** (assumed, вне бюджета) в начисление кэшбэка
  (`accrueCashbackForBooking`) — тот путь по-прежнему не гейтит по датам/расписанию; если понадобится —
  тот же `isPromotionActiveNow`.

- **[major, новая находка из `recheck-c3.md`] Двойное создание акции** — кнопка «Добавить акцию» не
  блокировалась на время сохранения: `mutation.isPending` гасло ДО завершения `router.push`, и второй
  клик в этом окне успевал создать вторую такую же акцию. Добавлен локальный флаг `submitted` (не
  гаснет обратно при успехе). Проверено сценарием: двойной клик подряд → в списке ровно одна акция.

- **[major, из `recheck-c3.md`] F-06-004** — по прямому адресу `/biz/loyalty/promotions/new` мастер
  открывался и позволял создать акцию с `cardTypeIds: []`, даже когда у бизнеса вообще нет ни одного
  типа карты (акция создавалась, но её никогда не было видно — список закрыт EmptyState'ом). Починка:
  `/promotions/new` сам читает типы карт и при нуле показывает тот же EmptyState «Добавить тип карты»,
  что список. Кнопку «Добавить акцию» на шаге 5 НЕ блокировал при `cardTypeIds.length === 0` — это
  законный путь для акции, заводимой только для рефералки (F-06-082, `showReferralWarning`), блокировка
  сломала бы этот случай.

## Предположения (assumed)

- `isPromotionActiveNow` подключил только к `listApplicablePromotions` (способ оплаты на панели
  лояльности), не к начислению кэшбэка — по ощущению, оплата (где клиент реально видит акцию и решает
  ей воспользоваться) важнее для проверки измерителем, чем фоновое начисление; если нужно и там —
  добавить один вызов в `accrueCashbackForBooking`.
- Формат дат в Excel-импорте (F-06-057) не менял — только знак «-» перед числом читается как дельта;
  число без знака остаётся абсолютной целью, как до починки (это НЕ противоречит «Готово, когда»,
  которое требует только «-100» → уменьшение на 100).
- `BulkImportModal.onValidateRow` — необязательный проп, чтобы не ломать другие возможные будущие
  использования компонента без валидации; для 4 текущих экранов раздела передан везде.
