# notify — g1-2-fix1: починка дефектов измерителя

Дата: 25.09.2026. Вход — 6 дефектов измерителя после доделки g1-2 (F-05-029…138): 4 major, 1 minor
(в F-05-132 два замечания), плюс отдельный major на F-05-029.

## Починено

### F-05-043 (major → починено полностью)

Претензия «нет vitest» была ошибочной: раздел (как и весь проект — `src/domain/rules/tests/**`) не
использует vitest, а работает через `node:test` + свой раннер `src/areas/notify/lib/run-tests.mjs`
(так уже было до этой пачки, `package.json` без vitest — общий проектный выбор, не notify). Прогнал
`node src/areas/notify/lib/run-tests.mjs` — 16/16 тестов зелёные, включая три новых (см. ниже).

Реальный пропуск был другим: два случая из «что если» F-05-029 (проверка 2) не имели ни правила, ни
теста. Добавил в `src/areas/notify/lib/liveLog.ts` (функция `timeBasedBookingEntries`) и покрыл тремя
тестами в `liveLog.test.ts`:

- **запись создана позже момента напоминания** — по аналогии с типом 73 в том же сводном списке:
  если `booking.createdAt` уже позже расчётного момента напоминания, напоминание не создаётся вовсе
  (а не «досылается» задним числом при следующей проверке).
- **перенос визита после того, как напоминание уже «запланировано»** — движок notify стейтless: время
  напоминания каждый раз считается заново от актуального `booking.start`, отдельной сущности
  «запланированного» напоминания нет. Поэтому перенос автоматически сдвигает напоминание на новое
  время, клиент его не теряет. Решение отражено в assumed (ТЗ помечал это как ⚠ открытый вопрос).

### F-05-132 (major + minor → major починен, minor остаётся assumed/не строим)

- Три бейджа связи с поддержкой на вкладке «Новости сервиса» (`InboxScreen.tsx`) были некликабельным
  `<Badge>` (span без onClick/href). Теперь:
  - Telegram и WhatsApp — настоящие ссылки (`<a target="_blank">`) на `https://t.me/<handle>` и
    `waLink()` (демо-контакты, см. assumed);
  - «Чат с поддержкой» открывает новую модалку `src/areas/notify/components/SupportChatModal.tsx` —
    текстовое поле → `createSupportTicket()` (`@/api/platform/support`, `channel: 'app'`), тот же
    паттерн, что уже использует `LoyaltyHubScreen` для «Помогите настроить». Toast на успех/ошибку.
  - Проверено сценарием (`qa/shots/scenarios/biz-notifications-inbox__…__support-chat-sent.png`):
    открытие модалки, ввод текста, отправка, тост «Сообщение отправлено», модалка показывает
    подтверждение — все 10 шагов сценария прошли.
- Пункт про персонального менеджера (minor) НЕ построен намеренно: ни поля вроде
  `Business.personalManager` в ядре, ни отдельного окна «?» в шапке кабинета не существует (шапка —
  `src/shell/**`, чужой путь). Строить точечно только текст без данных и без места показа значило бы
  выдумать факт — оставил как assumed/не построено, а не «починил вполсилы».

### F-05-058 (major → частично: своя часть построена, колокольчик снова блокирован)

`NotificationsBell.tsx` — чужой файл фундамента (`src/shell/workspace/**`, не наш путь по
CONVENTIONS.md §1), сам его не правлю — это ПЯТАЯ по счёту просьба хранителю `src/shell` без ответа
(см. `qa/requests/notify.md`, записи b01-fix2 → g1-1-fix1 → g1-1-fix2 → сейчас). Наша сторона
(`countUnreadInbox`, `listInboxPreview` в `src/api/notify.ts`) готова и не менялась.

Что ДЕЙСТВИТЕЛЬНО было в нашей власти и было дефектом — почищено: страница `/biz/notifications/inbox`
раньше игнорировала галочку «Операции с записями» (`WebPopupSettings.bookingOps`,
`/biz/notifications/channels`) — список событий показывался всегда, независимо от тумблера. Теперь
`InboxScreen` читает `getWebPopupSettings(businessId)` и при выключенной галочке список пуст с
EmptyState «Уведомления о записях выключены» + кнопкой «Открыть каналы». Проверено сценарием
(`…__bookingops-off.png` / `…__bookingops-on.png`, оба скриншота).

## Не починено (осталось в partial)

- **F-05-118, пункт «оплата сетевой рассылки списывается с баланса главной локации»** — в проекте
  нигде нет баланса уведомлений (`grep -rn "notifyBalance\|smsBalance" src` — пусто); F-05-115
  (баланс, «Биллинг») — чужой раздел settings и там тоже не построен. Цена SMS — фиксированная строка
  для всех локаций (не по бизнесу), поэтому «тариф с главной локации» физически нечем отличать от
  общего тарифа, пока нет per-location цены. Подсказка (`newMailing.audience.networkSmsRateHint`)
  остаётся текстовой, фейковую цифру баланса не рисовал. Запрос settings обновлён.

## Побочный эффект, который проверил и не подтвердил

При одном из первых прогонов `measure.mjs --area notify` (после первой правки badges) один снимок
`/biz/notifications/inbox` (desktop) показал `Hydration failed`. Перепроверил 11 раз подряд (5× тот же
один маршрут изолированно, 3× вся область, плюс повторные прогоны) — 0 повторов. Похоже на разовый
артефакт первой компиляции роута в dev-режиме сразу после правки файла (Turbopack), а не
детерминированный баг в JSX (структура `<a>`/`<button>` вокруг `<Badge>` — валидная вложенность,
никакого `Date.now()`/`typeof window` в новом коде нет). Финальные прогоны (после всех правок,
несколько раз подряд) — 0 ошибок консоли на всех 16 страницах раздела. Если проверяющий увидит это
снова — стоит для начала повторить прогон, прежде чем считать регрессией.
