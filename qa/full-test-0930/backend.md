## Что проверено и прошло

- **Вход и сессии.** Гость, код, неверный код (`wrong_code`), повторный запрос кода раньше 60 с (`code_resend_wait`), вход, список сессий, выход. Плохой телефон, канал, JSON или формат кода дают 400 `validation`. После 5 неверных попыток верный код тоже не принимается.
- **Лимиты.** `/auth/code`: 31-й запрос с одного IP → 429 `rate_limited` + `Retry-After`. `/auth/verify`: 41-й → 429.
- **Владелец.** PATCH мастера (предоплата процентом, `percent: 130` → 400, чужая версия в If-Match → 409). Создание записи (`place`), пересечение по времени → 409 `slot_taken`. Перенос через PATCH `start`, устаревшая версия → 409. Статусы, `awaiting_prepayment` от бизнеса запрещён. Отмена, удаление, восстановление.
- **Онлайн-запись по ссылке с предоплатой 30 %.**
  - Запись на 6 000 ֏: предоплата 1 800 ֏. С `payInFull`: 6 000 ֏ и `full: true`.
  - Неверный код → 4xx. Двойная запись на одно время → `slot_taken`.
  - Запись по хэшу; неверный хэш → 404.
  - «Я оплатил» по ссылке, затем «Предоплата получена» у владельца → `scheduled`, `paid`.
- **Отмена клиентом** (срок мастера 48 ч):
  - до срока → `refundDue` = вся предоплата;
  - после срока → предоплата остаётся мастеру, `cancelledLate`, +1 неявка;
  - повторная отмена → `not_active`;
  - `refund-done` у владельца работает.
  - `cancel-window` совпадает с тем, что происходит при самой отмене.
- **Приложение клиента** (`/v1/me/bookings`): `payInFull`, `/paid` снимает срок, владелец подтверждает предоплату. Перенос оплаченной записи → `prepaid_locked`. Отмена до срока → `refundDue` 6000.
- **Заявка без ответа мастера.** Режим ручного подтверждения; снятие по сроку через `releaseExpired` из свежей сборки. Результат: `cancelled_by_master`, в `alternativeStarts` 3 начала, не больше 2 в день. Их видно и по ссылке, и в кабинете. Запись на предложенное время проходит. Владелец подтверждает другую заявку → `scheduled`.
- **Журнал, «оплатить всю сумму».** Строка `prepayment` 1800 сохраняется, наличными добавляется остаток 4200, `paidAmount` 6000.
- **Telegram (заглушка без токена).**
  - `telegram-link` по хэшу даёт ссылку `t.me/…?start=`; без хэша → 404; повторный запрос → `linked: true`.
  - `/start <код>` создаёт привязку; код одноразовый.
  - Кнопки из чужого чата ничего не меняют. «Приду» → `client_confirmed`; «Да, отменить» → `cancelled_by_client`.
  - Мусор в вебхуке не даёт 500. `/stop` ставит `blockedAt`.
  - `/v1/me/telegram-link` с сессией работает, без сессии → 401.
- **Права мастера** (Ани, 10 прав). Нельзя: переносить запись другого мастера, создавать ему записи, править чужой профиль. На кассы, журнал изменений компании, счета подписки, уволенных и журнал выгрузки клиентов → 403. Владельцу те же маршруты отвечают 200.

## Исправлено (booktime-backend, typecheck 0)

1. **«Я оплатил» по ссылке не останавливал таймер.** `markPrepaymentPaid` не снимал `holdUntil`, поэтому воркер через `timeoutMin` отменял уже оплаченную запись как `prepayment_expired` (воспроизведено) и освобождал окно для других. Общий шаг вынесен в `BookingsService.stopPrepaymentHold`, приложение и ссылка теперь используют его. `online.service.ts`, `bookings.service.ts`.
2. **Двойная «Предоплата получена»** добавляла вторую строку оплаты, и сумма удваивалась. Теперь строка `prepayment` добавляется один раз.
3. **`GET/POST /v1/public/bookings/:id…` без `?h=`** отвечали 500 (`hashOf(undefined)`). Теперь 404. Исправление в `findByHash` покрывает просмотр, `cancel-window`, отмену, «я оплатил» и `telegram-link`.
4. **Лимиты: одна корзина с разными окнами.** `public-booking-hash` делили GET (60 за минуту) и POST (20 за час). После одной отмены просмотры записи по ссылке запирались на час, а 21 просмотр блокировал отмену (воспроизведено). У POST теперь своя корзина `public-booking-hash-write` (в том числе у `telegram-link`).
5. **Бронь в чужой филиал.** `place()` не проверял, что `locationId` принадлежит бизнесу: Hayk создал запись в `loc_nuri` (воспроизведено). PATCH записи принимал чужие `staffId` и `locationId`, то есть можно было занять время чужого мастера. Теперь в обоих случаях 404.
6. **IDOR в переводах.** `GET/PUT /biz/:b/translations/override` не проверяли владельца текста: Hayk писал и читал перевод услуги Nuri (воспроизведено). Добавлен `assertOwned` (business, staff, service своего бизнеса), параметры запроса проверяются схемой (раньше `ZodError` давал 500).
7. **`cancel-window` расходился с самой отменой.** Окно смотрело только правила мастера: не видело правил бизнеса и `allowCancel`/`allowCancelPrepaid`, часы округляло. Клиенту показывали «отмена бесплатна», а отмена отвечала отказом. Теперь окно берёт те же действующие правила и тот же `clientCancelOutcome` (`clientCancelPreview` дополнительно отдаёт `rules`).
8. **`POST /bookings/external` без проверки тела:** без `phone` падал 500. Подключена уже существующая, но неиспользуемая `externalBody`.
9. **`PATCH /clients/:id/note` без проверки тела:** `note: 5` давал 500. Теперь Zod-пайп.
10. **Несуществующая дата в правильном формате** (`2026-02-30T10:00`) давала 500 через `RangeError` в `localToUtc`. Добавлен `InvalidLocalTime`; фильтр ошибок отдаёт 400 `validation`. Работает для всех маршрутов сразу. Туда же добавлен `ZodError` → 400.
11. **`GET /biz/:b/news/suggestions` падал 500 всегда:** `deletedAt` у Service нет. Заменено на `active: true`.
12. **Обязательные параметры запроса без проверки давали 500:**
    - `stock/to-order/whatsapp-text` (`phone`);
    - `me/favorites/check`;
    - `me/loyalty`, `me/loyalty/buyable` (`businessId`);
    - `app-staff/z-report` (`date`);
    - `app-staff/:id/payroll-calculation|payroll-payouts` (`from`/`to`);
    - `reports/client-visits`, `reports/stock-write-off`, `reports/stock-turnover` (`from`/`to`).

    Теперь это 400: даты проверяются строго через `isLocalDate`.
13. **Вебхук Telegram без секрета принимал поддельные обновления.** Поддельный `contact` с `user_id = from.id` привязывает чат к любому номеру и даёт кнопки отмены чужих записей (в дев-режиме воспроизведено). В `NODE_ENV=production` вебхук без `TELEGRAM_WEBHOOK_SECRET` теперь отвечает 403.

14. **Отзыв по записи без проверки цели.** `POST /v1/public/bookings/:id/reviews` принимал любой `targetId`: по id записи можно было поставить звезду чужому мастеру или бизнесу. Теперь `targetId` должен совпадать с `businessId`/`staffId` самой записи, иначе 400. Экран шлёт `business.id`, совместимо. Проверено на :4011.

## Открытые вопросы (не правил)

1. **API и воркер на :4010 работают на коде от 28.09** (`dist/` от 28.09 09:37). В них нет предоплаты процентом и `payInFull`, Telegram-модуля, `alternativeStarts` в `releaseExpired` и сегодняшних правок. Воркер :4010 уже снимает просроченные заявки в дев-базе старым кодом, то есть без 3 окон. Нужны `npm run build` и перезапуск обоих процессов (сам не трогал: процесс занят).
2. **`openapi/openapi.json` в репозитории устарел** (нет `prepayment.percent`, тела `bookings/external`). Сгенерировал свежий в скретчпаде (1034 пути), но в репозиторий не клал. `npm run openapi` пересобирает `dist`, поэтому запускать его стоит вместе с перезапуском.
3. **Отзыв и «уже оценено» по ссылке работают без хэша** (`POST /v1/public/bookings/:id/reviews`, `GET …/reviews/:target`). Цель я проверил (исправление 14), но хэш по-прежнему не требуется: фронт (`src/api/online.server.ts:287`) не шлёт `?h=`. Воспроизведение: `POST /v1/public/bookings/<чужой id записи>/reviews {"target":"business","targetId":"<её бизнес>","clientId":"x"}` без `h` → 200, звезда засчитана. Нужна правка фронта (передавать `h`), затем на сервере — `findByHash`.
4. **Мастер видит в CRM всех клиентов бизнеса** (телефоны маскированы) и запись другого мастера (GET 200): у Ани `clients.view` и `journal.view`. Если «мастер видит только своих» — это настройка `calendarVisibility`/шаблона роли, а не сервер.
5. **Много `@Query()` без Zod по всему коду.** Всё, что давало 500, закрыто. Остальные маршруты на мусоре отвечают 200 с пустым ответом, 400 или 404, но форматы не проверяют (например, отчёты принимают `from=x`). Системно — завести общий `qDate` и использовать его во всех схемах запросов.
