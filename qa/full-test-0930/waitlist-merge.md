# Один лист ожидания — слияние двух реализаций (30.09–01.10.2026)

Решение владельца: у бизнеса ОДИН лист ожидания. Экран /biz/waitlist — его полный вид, панель «Лист ожидания» в
журнале — компактный вид тех же данных.

## Как сделано и почему так
Взята рекомендованная схема. Хозяин сущности — раздел resources (так записано в core-rules). Его форма данных богаче:
желания с интервалами, теги, история отметок «Уведомлён».
- **Один тип** `WaitlistEntry` в `src/domain/resources.ts`. `WaitlistWish.date` стал необязательным: так хранится
  «любой день, но с 10 до 12» — это умела только панель журнала, теперь ничего не теряется. Тип журнала
  (`slots`, `bookingId`) удалён из `src/domain/journal.ts`.
- **Общие правила — чистые функции в домене:** `filterWaitlist` (статус, «на выбранную дату / сегодня / все», поиск,
  сортировка — раньше у каждого экрана была своя копия), `waitlistWantsDay`, `waitlistWantsSlot` (кому дойдёт
  «Предложить окно»), `pickWaitlistSlot`, `wishesToDrafts` / `draftsToWishes` (форма), `waitlistFromLegacyJournal`
  (перенос старых заявок).
- **Одно хранилище:** срез `resources.waitlist`. Одна функция чтения и один ключ: `useWaitlist` →
  `['resources','waitlist',businessId]`. Её читают экран, панель журнала и счётчик в «Требует внимания», поэтому заявка,
  созданная в одном месте, сразу видна в другом.
- **Один API** в `src/api/resources.ts`: `addToWaitlist`, `updateWaitlistEntry`, `closeWaitlistEntry`,
  `removeWaitlistEntry`, `notifyWaitlistForFreedSlot`, `getWaitlistNotifications`, `waitlistEntriesSync`
  (для «Предложить окно»), `suggestWaitlistSlot`. Функции листа ожидания из `api/journal.ts` и `journal.server.ts`
  удалены. В `api/journal.ts` осталось только состояние панели (открыта/закрыта).
- **«Найти окно» / «Свободно сегодня» → «Предложить»** (`journal-offers.ts`): берёт одного получателя из общего листа
  и ставит отметку «Уведомлён» (`resources.waitlistNotified`) любой заявке, откуда бы она ни пришла. Раньше заявки
  журнала отметку не получали. Панель журнала теперь показывает строку «Уведомлён · последний раз …», как и экран.
  Списки «сообщить об окне» из приложения и виджета остались отдельными, как и договаривались.
- **«Записать»** работает одинаково на экране и в панели:
  - клиент заявки берётся по карточке; если карточки нет — подставляются имя и телефон из заявки;
  - подставляется услуга и мастер, который её делает;
  - время — ближайшее свободное окно, которое ждёт заявка (`suggestWaitlistSlot` → `getFreeSlots`/`getNearestSlots`).
    Раньше при «Любое время» ставилось 10:00 даже на занятое, и сохранение падало (замечание из journal-2 F-01-159).
  После сохранения заявка становится «Закрытая» (панель — `closeWaitlistEntry` в onSaved, экран — `?waitlist=` в
  JournalScreen). У закрытой заявки есть кнопка «Открыть запись» (`/biz/journal?booking=…`) — и на экране, и в панели.
- Дополнительно по замечаниям journal-2:
  - на кнопке было «+ + Создать» — «+» убран из текста (ru/en/hy);
  - в форме панели и экрана остались только мастера, которые есть в журнале (`isScheduleStaff`, без
    `hiddenInJournal`); в панели ещё и только те, кто делает выбранные услуги;
  - в hy добавлен ключ `journal.board.attention.pendingHintOverdue`, в ru/en/hy — ключи
    `journal.waitlist.card.openFull/openBooking/anyDay/notifiedAt`, `resources.waitlist.anyDay/openBooking`.
  - В панели появилась ссылка «Весь лист ожидания» → /biz/waitlist (видна тем, у кого есть `resources.manage`).
    Фильтр панели «На выбранную дату» теперь берёт день сетки журнала (раньше всегда брал «сегодня»).

## Перенос данных
**Мок (localStorage).** Версии срезов не поднимал: подъём пересеял бы весь срез journal или resources и стёр бы
остальные данные пользователя. Вместо этого:
- `waitlistEntriesSync` читает `resources.waitlist` и заодно старые `journal.waitlistEntries`, переводя их через
  `waitlistFromLegacyJournal`. Битые записи (без id, бизнеса или имени, `null`) пропускаются — старая база не падает.
- Первая запись в лист (создать, изменить, закрыть, удалить, «Уведомить») сначала вызывает `absorbLegacyWaitlist`:
  старые заявки переезжают в `resources.waitlist` с теми же id, а поле `journal.waitlistEntries` удаляется.
- Демо-заявку «по одной на бизнес» теперь засевает срез resources (раньше это делал journal) — только тем бизнесам,
  у которых нет своих примеров.

**Бэкенд** — `prisma/migrations/20260930120000_one_waitlist/migration.sql`. Канонической осталась `waitlist_entries`:
на неё уже ссылаются FreedSlot.waitlist_ids, приложение клиента, склейка клиентов и обезличивание.
1. Добавлены `wishes`, `tags`, `notified_times`.
2. `slots` переведены в `wishes` SQL-ом через JSON_TABLE. Прошлый `notified_at` стал первой отметкой в истории.
3. Колонка `slots` удалена.
4. Строки `resources_waitlist_entries` вставлены с теми же id. При совпадении id добавляется суффикс `_rw`.
   `client_id` подбирается по телефону, `notified_at` — последняя отметка из истории.
5. `wishes` и `tags` стали NOT NULL, таблица `resources_waitlist_entries` удалена.

Код бэкенда:
- `schema.prisma`: модель `ResourcesWaitlistEntry` удалена, `WaitlistEntry` получила `wishes`, `tags`,
  `notifiedTimes`.
- `resources-events.service/schemas/controller`: `/v1/biz/{b}/resources/waitlist` — теперь единственный адрес листа,
  работает над `waitlist_entries`. Создание подбирает `clientId`. `createdAt` и отметки отдаются местным временем.
  Желание без даты разрешено, `locationId` может быть пустым.
- Правило «Проверить лист» сведено к фронтовому: только этот день. Раньше срабатывало на любое будущее желание.
- Маршруты `/v1/biz/{b}/waitlist` журнала и `WaitlistInput`/схемы удалены (`journal.controller/service/schemas`).
- `bookings.service.freeSlot` (раздача окна В-18) читает `wishes` и дописывает историю отметок.
- `me.service.addWaitlist` (приложение клиента) пишет `wishes`.
- В `ids.ts` снят `resourcesWaitlistEntry`.

Проверка миграции — только на временных базах в docker-MySQL, не на dev-базе:
- `booktime_wltest`: старые таблицы + строки с разными слотами, дубль id, null-даты. Миграция прошла, результат
  совпал с ожидаемым.
- `prisma migrate diff --from-migrations … --to-schema …` на временной shadow-базе: пустой diff, миграции совпадают
  со схемой.
- Временные базы удалены. `prisma generate` выполнен, `npm run typecheck` в бэкенде зелёный. API на :4010 не
  перезапускал, `dist` не пересобирал.

## Открытые вопросы
- **Порядок выката бэкенда:** миграцию надо применить (`migrate deploy`) до запуска нового кода. Старый код на новой
  базе и новый код на старой базе падают на листе ожидания.
- `openapi/openapi.json` не пересобран: для этого нужен `npm run build`, а он перезаписывает `dist`. В нём ещё лежат
  `/v1/biz/{b}/waitlist*` — пересобрать при следующей сборке.
- Режим api для «Предложить окно» по-прежнему только мок: эндпоинта нет, это было и до слияния.
- Дев-сервер какое-то время отдавал устаревшие `messages/*/journal.json` (новые ключи других тестеров тоже были
  «missing»). После перезапуска сервера кем-то из команды всё подтянулось. Это не код, а залипший кеш turbopack.
- Во время работы сборка на минуту ломалась: AttentionPanel ещё импортировал удалённый `listWaitlistEntries`.
  Исправлено сразу же — импорты переключены.
