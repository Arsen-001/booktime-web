# Вопросы владельцу — раздел stock

По каждой ❓-ситуации из `functional-map/08-stock.md` F-08-147 (пограничные ситуации склада)
принято решение по умолчанию — общий принцип: **не удалять то, у чего есть остаток или ссылки,
объяснить, что именно мешает**; необратимое — только явным подтверждением. Если хозяин выберет
другой вариант, правка — в `src/api/stock.ts`, функции указаны при каждом пункте.

### Удалить склад с остатком, операциями, в техкартах или в правах сотрудника (F-08-008)

- а) запрет, если на складе есть остаток (qty ≠ 0 хотя бы по одному товару), с текстом «На складе
  остались товары — сначала переместите или спишите их» (что сделано по умолчанию —
  `deleteWarehouse`, `ApiError('warehouse_has_stock')`);
- б) как (а), но дополнительно запрещать удаление, если склад упомянут в правах сотрудника
  (`StockStaffPermissions.warehouseIds`) или в техкарте — не реализовано отдельно, т.к. права и
  техкарты ссылаются на склад только как «где списывать», без остатка это не опасно;
- в) разрешить всегда, молча отвязывая ссылки.

**Что сделано по умолчанию:** (а). Довод для (б): пункт остаётся открытым, если хозяин захочет
более строгую проверку — правка в `deleteWarehouse`.

### Сменить тип склада, на котором уже лежит товар (F-08-009, справка 1329)

- а) разрешить всегда — тип склада влияет только на то, какие операции с него доступны дальше
  (продажа/списание/перемещение), не на остаток; остаток при смене типа не трогается (что сделано
  по умолчанию);
- б) предупреждать тостом «Остаток есть — операции, недоступные новому типу, останутся
  заблокированы», без запрета.

**Что сделано по умолчанию:** (а) — форма склада (`WarehouseForm`) меняет тип свободно, правило
типа (`assertWarehouseTypeAllows`, `src/domain/stock.ts`) проверяется на каждой операции заново,
а не один раз при смене типа — то есть даже без предупреждения несовместимая операция всё равно
не пройдёт.

### Удалить товар из техкарты, с остатком, служебный товар абонемента (F-08-030)

- а) товар, использованный хоть в одной техкарте — не удаляется совсем, только архивируется, с
  текстом «Товар входит в техкарту «…» — удалить нельзя, можно архивировать» (что сделано по
  умолчанию — `deleteGood`, `ApiError('good_in_use')`);
- б) удалять, снимая товар из техкарты автоматически.

**Что сделано по умолчанию:** (а). Товар с остатком не удаляется тоже — архивация не требует
нулевого остатка (соответствует Altegio, 1375), удаление — да.

### Что станет с прошлыми количествами, если у товара с операциями вручную сменить единицы (справка 1415)

- а) прошлые документы хранят количество в той единице, что была на момент операции (снимок в
  строке документа), пересчёт истории при смене единицы не делается — только новые операции
  используют новую единицу (что сделано по умолчанию: `StockOperationLine` хранит `unit` построчно,
  не ссылку на текущую единицу товара);
- б) пересчитывать всю историю по коэффициенту — рискованно и не по Altegio (баг 08-020/056 —
  именно неявный пересчёт при смене единицы — прямо описан как то, что мы НЕ повторяем).

**Что сделано по умолчанию:** (а).

### Два товара с одинаковым штрихкодом (F-08-019)

- а) запрет сохранения — «Такой штрихкод уже используется у «Название»» (что сделано по умолчанию
  — валидация в `GoodForm`/`createGood`/`updateGood`, штрихкод уникален в пределах `businessId`);
- б) разрешить, сканер берёт первый найденный.

**Что сделано по умолчанию:** (а) — безопаснее для поиска по скану в продаже и приходе.

### Сменить мастера в визите — какая техкарта (F-08-039, добавлено проверкой 1)

- а) подставляется техкарта нового мастера для той же услуги, если она у него есть; если нет —
  списания по этой услуге не создаются, тост предупреждает (что сделано по умолчанию);
- б) сохранить техкарту старого мастера.

**Что сделано по умолчанию:** (а) — техкарта привязана к паре «услуга + мастер»
(`TechCard.staffId`), смена мастера ищет техкарту заново тем же ключом.

### Перенести визит после «Пришёл» — дата списания (F-08-041)

- а) дата списания не переезжает вместе с визитом — операция уже создана на момент, когда статус
  стал «Пришёл», перенос времени/даты визита её не трогает (что сделано по умолчанию, совпадает с
  тем, что «Изменения данных» у Altegio пишут реальное время действия, не дату операции);
- б) пересчитывать дату списания на новую дату визита.

**Что сделано по умолчанию:** (а).

### Вернуть «Пришёл» → «Ожидание» (F-08-042)

- а) как «Не пришёл» — автосозданные списания расходников по техкарте отменяются (возврат на
  склад), ручные строки товара/абонемента остаются как были (что сделано по умолчанию, по
  аналогии с уже описанным поведением «Не пришёл»);
- б) списания остаются, статус просто меняется.

**Что сделано по умолчанию:** (а) — иначе повторное «Пришёл» задвоило бы списание.

### Автосписание при нехватке и включённом запрете (F-08-099)

- а) статус «Пришёл» не блокируется — списание просто пропускается по недостающим строкам, тост
  «Не хватает 2 позиций — списано частично, доспишите вручную» (что сделано по умолчанию —
  запрет операций при нехватке относится к ручным документам, не к автосписанию визита, иначе
  мастер не смог бы закрыть визит вовсе);
- б) блокировать «Пришёл» целиком, пока не спишешь вручную.

**Что сделано по умолчанию:** (а) — согласуется с F-00-061 «Отменить 5 секунд» и с тем, что визит
важнее строгости склада.

### Вернётся ли на склад товар, проданный в визите, если визит удалить/«Не пришёл» (F-08-147)

- а) да, как и расходники — продажа товара в визите создаёт операцию списания, отмена визита
  создаёт обратную операцию (что сделано по умолчанию — общий код возврата не различает
  расходник/товар);
- б) только расходники по техкарте, проданный товар — нет (это была бы отдельная бизнес-логика
  «продажа состоялась»).

**Что сделано по умолчанию:** (а) — проще и безопаснее для остатка; если хозяин хочет наоборот,
это отдельная ветка в обработчике удаления/«Не пришёл» визита (не в путях stock).

### Перемещение со склада на тот же склад (F-08-059)

- а) запрет в форме — «Выберите разные склады» (что сделано по умолчанию, валидация в форме
  перемещения);
- б) разрешить как «пустую» операцию без эффекта.

**Что сделано по умолчанию:** (а).

### Удалить контрагента, по которому были приходы

Сейчас «Контрагент» в документе прихода — свободное текстовое поле (сущности «Контрагент» со своим
списком/карточкой в разделе пока нет), поэтому удалять физически нечего — вопрос неприменим, пока
не появится отдельный справочник контрагентов. Заранее решаю на будущее:

- а) когда справочник появится — контрагент не удаляется, если на него есть хоть один документ
  прихода, только «Архивировать» (что решено по умолчанию для будущей реализации);
- б) удалять, документы остаются с текстовым именем без ссылки.

**Что сделано по умолчанию:** (а) как решение на будущее; сейчас поле текстовое, удалять нечего.

### Прошлые списания по удалённой техкарте (F-08-038)

- а) остаются в журнале операций как есть, привязка к техкарте — тоже как была (сохраняем `id`
  строкой без разрешения ссылки) — само удаление техкарты не трогает прошлые документы (что
  сделано по умолчанию — см. комментарий у `deleteTechCard`);
- б) стирать ссылку, оставляя только название текстом.

**Что сделано по умолчанию:** (а).

### Правка цены старого прихода — пересчитается ли себестоимость уже проданного

- а) нет — себестоимость товара берётся на дату конкретной операции (F-08-098, справка 1416),
  правка цены задним числом меняет её отчёт с этой даты, но не переписывает уже посчитанные
  прошлые продажи (что сделано по умолчанию — отчёты читают снимок себестоимости на момент
  операции, не текущую цену товара);
- б) пересчитывать всё исторически.

**Что сделано по умолчанию:** (а) — иначе правка одного прихода задним числом каждый раз меняла
бы прибыль всех прошлых месяцев.

### Оплатить позже неоплаченный приход (F-08-057)

- а) документ прихода можно оставить неоплаченным при создании и оплатить позже отдельной
  кнопкой «Оплатить» в документе — остаток на складе уже увеличился в момент прихода, оплата —
  только финансовая операция вдогонку (что сделано по умолчанию);
- б) приход обязателен к оплате сразу.

**Что сделано по умолчанию:** (а) — соответствует тому, что склад и касса у нас разделены (деньги
только фиксируем, F-00-126).

### Что происходит с датой финансовой операции при смене даты продажи/прихода

- а) финансовая операция создаётся один раз на дату оплаты и дальше не переезжает при правке даты
  продажи/прихода — только явная правка самой финансовой операции (в разделе finance, не stock)
  меняет её дату (что сделано по умолчанию — в stock мы просто не трогаем `financeOp.date` при
  правке `StockOperation.date`);
- б) синхронизировать даты автоматически.

**Что сделано по умолчанию:** (а) — синхронизация была бы записью в чужой домен (`finance`), не в
моих путях.

### Расходники в групповом событии — списываются ли по техкарте

- а) да, так же, как в обычном визите — участник группового события считается визитом одной
  услуги, техкарта ищется тем же ключом «услуга + мастер» (что сделано по умолчанию, отдельной
  ветки для группового события в коде склада нет — общий обработчик визита не различает тип
  события);
- б) не списывать для групповых событий вовсе, пока не решено явно.

**Что сделано по умолчанию:** (а) — по умолчанию безопаснее списывать (иначе расходники группы
молча теряются из учёта), а не пропускать списание тихо.

### Наше: мастер со своим складом уходит из салона — чей остаток (F-08-005, F-00-044)

- а) остаток остаётся у салона (склад мастера превращается в архивный склад салона, данные не
  теряются) — по аналогии с F-00-044 «записи, деньги и клиенты — салону» (что сделано по
  умолчанию: `Warehouse.staffId` — только метка «чей», данные и так лежат по `businessId +
  locationId`, уход мастера их не переносит);
- б) остаток уходит вместе с мастером (нелогично — товар физически остался в салоне).

**Что сделано по умолчанию:** (а) — согласуется с уже принятым решением F-00-044.

### Наше: индивидуал со своим складом переходит в салон (F-00-043)

- а) склад индивидуала не переносится автоматически — при переходе в салон у него появляется
  доступ к складу салона (по правам сотрудника), а личный склад остаётся отдельным до тех пор,
  пока хозяин вручную не перенесёт остатки операцией «Перемещение» (что сделано по умолчанию —
  нет автоматической миграции данных между `businessId`);
- б) склад индивидуала автоматически становится складом салона.

**Что сделано по умолчанию:** (а) — автоматическое слияние данных двух разных `businessId` — это
операция фундамента (переход аккаунта), не разовая функция склада; ручной перенос явной операцией
безопаснее и виден в истории.

### Наше: мастер одновременно в салоне и сам по себе (F-00-045) — сколько складов

- а) два раздельных склада, каждый со своим `businessId` (у каждого салона всё раздельно, F-00-050
  — это касается и «личного салона» индивидуала); материалы домашнего визита списываются со
  склада того контекста, в котором создана запись (визит в личном кабинете индивидуала → его
  склад, визит в салоне → склад салона) (что сделано по умолчанию — ключ остатка всегда
  `businessId + locationId` без исключений);
- б) один общий склад на человека.

**Что сделано по умолчанию:** (а) — совпадает с общим правилом F-00-050 «свой склад у каждого
салона», без специального случая для одного и того же человека.
