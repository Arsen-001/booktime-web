## 2. Точечное перечитывание — как устроено

```
 ЧТЕНИЕ                                                   ЗАПИСЬ
 useApiQuery(key, fetcher)                                useApiMutation(fn) / любой вызов api
   └ queryFn → runQuery: контекст чтения ctx                └ request(fn) → set() в zustand
       └ fetcher() → request(fn) запоминает ctx               └ useDb.subscribe: сравнение ссылок до/после
           СИНХРОННО, в момент вызова                              core.<коллекция>, areas.<раздел>.<поле>, access
       └ после задержки fn() под runTracked(ctx):             └ метки копятся до конца микрозадачи → onDbChange
           useDb.getState() отдаёт «наблюдаемый вид»        handleDbChange: запросы, чьи метки пересекаются
           → чтение core.bookings / areas.clients.rows        с изменёнными → invalidateQueries (активные
             / access пишет метку в ctx.deps                  перечитываются в фоне, неактивные — помечаются)
   └ удачно: deps запроса = ровно прочитанное
```

- **Метки (`DbTag`)**: `core.bookings` … (13 коллекций ядра), `areas.<раздел>.<поле среза>` (например
  `areas.clients.autoSaveChatLeads`), `areas.<раздел>` (набор полей среза — меняется, когда поле появилось/исчезло), `access`.
- **Поля среза, а не срез целиком.** `mutateArea` клонирует срез целиком, поэтому `setArea` пропускает результат через
  `replaceEqualDeep`: неизменённые поля сохраняют ссылки, и переключатель в настройках раздела не будит список клиентов
  (замер: `clients-switch` — 13 перечитываний → 1).
- **Вид вместо Proxy.** Наблюдаемый вид — объект с геттерами: его можно отдать в `structuredClone`, JSON, спред (они читают
  все поля — и все они честно становятся зависимостями). Писать в вид нельзя (геттер без сеттера) — писать только через
  `mutateArea`/функции ядра, как и раньше.
- **Контекст после `await`.** Синхронно захваченный контекст знает, чей это `request()`. Чтение без контекста
  (продолжение после `await` внутри функции чтения, `for (…) await getDayHours()` подряд, api без `request()`)
  засчитывается **всем идущим сейчас чтениям**: лишний раз перечитать можно, пропустить изменение — нельзя. Вид, полученный
  до `await`, помнит свой запрос и после него.
- **Запись во время чтения.** Чтение уже прочитало изменённую коллекцию, но ещё не вернулось — его результат устарел:
  оно тоже инвалидируется (TanStack отменяет и начинает заново). Прочитать ещё не успело — прочитает свежее.
- **`meta.rev`** по-прежнему растёт на каждую запись, но на него никто не подписан.

### Транзакция `request()`

Функция `request(fn)` — транзакция мока: перед `fn` берётся снимок `core/areas/access` (ссылки — O(1)), `fn` упала
посередине — всё, что она успела записать, откатывается (`restoreDb`). Работает для синхронной `fn` (одна операция = один
синхронный `request()` со `coreTx.*` внутри — ARCHITECTURE §4); в async-функции между `await` пишут другие запросы, её не
откатить. В деве чтение базы **вне** `request()` пишет в консоль `[mock-db] обращение к базе вне request()` со стеком (одно
предупреждение на место): такое чтение до подъёма базы видит пустые данные, и у бэкенда его не будет.

`request(fn, { permission: 'clients.export' })` — «сервер» проверяет право (`assertCan` ядра) до `fn`: нет — `ApiError('forbidden')`.

## 3. API для разделов (`@/api/request`)

```ts
useApiQuery(key, fetcher, { enabled?, keepPrevious? })
  → { data, isLoading, isFetching, isError, error, isPlaceholderData, refetch }
useApiMutation(fn, { optimistic?, invalidates? })
  → { mutate, isPending, error, reset }          // mutate бросает — try/catch + toast
patchInList(keyPrefix, (args) => ({ id, patch }))   // готовая оптимистичная правка: поле элемента по id
removeFromList(keyPrefix, (args) => id)              // убрать элемент по id
optimistic<T, A>(keyPrefix, (old: T, args: A) => T)  // своя правка
prefetchApiQuery(key, fetcher)                       // заранее в кэш (соседний день, следующий шаг)
request(fn, { permission? }), ApiError, getQueryClient()
```

Публичный контракт прежний (разделы не правились): `useApiQuery(key, fetcher, { enabled })`, `useApiMutation(fn)`,
`request(fn)`, `ApiError`. Отличия, которые стоит знать:

- `data` при `enabled: false` — `undefined` (как раньше), даже если в кэше что-то есть.
- Функция чтения законно может вернуть `undefined` («черновика нет») — TanStack так не умеет, в кэше хранится знак
  «ничего», наружу выходит снова `undefined`.
- `isLoading` — только первая загрузка ключа; при `keepPrevious` смена ключа показывает прежние данные с
  `isPlaceholderData: true` и `isFetching: true` — приглушайте список, а не прячьте его.
- `refetch()` присоединяется к уже идущему чтению (`cancelRefetch: false`), а не начинает второе.

### Оптимистичные правки

```ts
const setStatus = useApiMutation(
  ({ id, status }: { id: Id; status: BookingStatus }) => changeBookingStatus(id, status),
  { optimistic: patchInList(['journal', 'bookings'], ({ id, status }) => ({ id, patch: { status } })) },
);
```

Механизм: `onMutate` отменяет идущие чтения этих ключей (иначе ответ «до записи» затёр бы правку), запоминает прежние
данные всех запросов с этим **началом** ключа и кладёт правку (`setQueryData`); ошибка — прежние данные на место; после
завершения — сверка с базой (перечитывание; совпало — перерисовки нет). Пока правка в полёте, автоматическое
перечитывание этих запросов откладывается до её завершения — чужая запись посередине не «мигнёт» старым значением.
Проверено на временной странице: правка видна через 40 мс, откат при `ApiError` возвращает прежний статус.

### `keepPrevious` — когда прежние данные остаются

По умолчанию — если в ключе поменялись только параметры вида: дата `YYYY-MM-DD`, число, объект фильтров, строка поиска
(с пробелом или не латиницей), `true/false`, пустая строка. Сменился id (`bk_…`, `cl_…`) или имя ресурса — **нет**:
прежние данные чужой сущности показывать нельзя (форма, которая «подхватывает» данные по id, подхватила бы чужие).
Явное `keepPrevious: true | false` важнее правила.

## 4. Настройки кэша и почему

| Настройка | Значение | Почему |
|---|---|---|
| `staleTime` | 60 с | перечитывание по записи точечное, данные в кэше и так свежие; минута — запас для того, что зависит от времени («свободно сейчас»): повторный заход через минуту перечитает в фоне |
| `gcTime` | 5 мин | ушли с экрана и вернулись — данные сразу |
| `refetchOnWindowFocus` / `OnReconnect` | нет | база в браузере, от фокуса и сети не меняется |
| `networkMode` | `always` | иначе при `navigator.onLine === false` TanStack ставит запросы на паузу |
| `retry` | 1 раз, кроме `ApiError` и режима `?api=error` | `ApiError` — ответ «сервера» (демо-ошибка, `not_found`), повтор не поможет, ErrorState — сразу |
| `structuralSharing` | да (по умолчанию) | неизменившиеся объекты — прежние ссылки |
| Ошибка запроса | `console.warn('[api] запрос не удался', key, error)` | как было |
| Смена режима в демо-панели (normal/slow/error) | `resetQueries()` | сразу видно скелетоны или ErrorState |
| Смена персоны или сферы | `resetQueries()` | другой «пользователь»; часть ключей ещё без `businessId` (arch-a1 S6) |

Демо `?api=slow` и `?api=error` проверены на 7 экранах: скелетоны через 1,2 с → содержимое; ошибки → ErrorState с «Повторить».

Панель запросов (только дев): `localStorage.setItem('bp-devtools', '1')` в консоли и обновить страницу — кнопка слева внизу.
По умолчанию выключена, чтобы не попадать на снимки замеров.

Проверено: компилируется большинство компонентов (журнал, сетка, клиенты, каталог, UI-кит — в чанках есть кэш
`react/compiler-runtime`); компоненты с неподдерживаемым кодом компилятор пропускает сам (`BookingWindow`,

Линт уже строгий по правилам компилятора (`set-state-in-effect`, `refs`, `purity`): по `src/**` — 0 нарушений.
react-hook-form в проекте нет (формы на useState) — известной несовместимости `watch()`/`formState` нет.

Проверка под компилятором (25.09): обход всех 118 адресов `/dev/routes` — одна ошибка (вклад online, ниже); сценарии форм
`measure.mjs --scenario`: `clients-b02-create` 27/27 шагов (ошибки «Укажите имя», «Укажите полный номер телефона» видны,
клиент создаётся и находится поиском), `client-book-logged-in` 8/8, `online-ux-r1-create` 16/16, `schedule-set-cell` 7/7,
`platform-sphere-request-create` 17/17. Три сценария упали не из-за компилятора — устарели после правок разделов:
`journal-create` (телефон клиента переехал во вкладку «Клиент»), `clients-ux-r2-form` («Добавить поле» теперь в свёрнутых
«Дополнительных параметрах»), `platform-ads-create` (второе поле стало загрузкой файла).

**Единственная найденная опасность — `x!.y` внутри функции, переданной в хук или в проп JSX.** Компилятор считает такую
функцию «может быть вызвана в рендере» и выносит её обращения к полям в рендер для сравнения кэша. Было:

```tsx
const linkQ = useApiQuery(['online-booking-link', metaQ.data?.linkId], () => getLink(metaQ.data!.linkId!), {
  enabled: Boolean(metaQ.data?.linkId),
});
// скомпилировалось в: if ($[8] !== metaQ.data.linkId) { … }  — в РЕНДЕРЕ, при data === undefined падает
```

Исправление — посчитать значение в рендере через `?.` и взять его в функции:

```tsx
const linkId = metaQ.data?.linkId;
const linkQ = useApiQuery(['online', 'booking-link', linkId], () => getLink(linkId ?? ''), { enabled: Boolean(linkId) });
```

Поиск таких мест: `node scripts/renders.mjs --check-compiler` (на 25.09 — 16 мест в 7 файлах journal, online, client,
schedule; замечания разделам — `qa/measure/<id>/state-s1.md`). Сейчас падало одно (вклад online в окно записи, ловит `ExtensionSlot`),
остальные при обходе не падали (компилятор эти компоненты пока пропускает или значение есть уже к первому рендеру), но
упадут при первом же сочетании «компилируется + значения ещё нет». Раздел
`platform` такую же ошибку уже исправил сам (`BusinessesScreen`, комментарий в коде). Крайняя мера для одного
компонента — `'use no memo'` первой строкой функции (с комментарием почему).

Почему не выключили: выигрыш измерен (§7: ещё −28…−71 % перерисовок сверх того, что дал слой запросов, на семи действиях
из восьми), а опасность одного вида,
находится скриптом и чинится одной строкой. Передать компилятору `enableTreatFunctionDepsAsConditional` (отключает
вынос) через `next.config` нельзя — Next перезаписывает `environment` компилятора целиком.

## 7. Замер: до / после

`node scripts/renders.mjs --label <имя>`; сравнение — `--compare before,after`. Chromium без троттлинга, дев-сервер,
3 прогона на действие (медиана), прогоны с Fast Refresh от чужих правок повторялись. Отчёты: `qa/speed/renders-before.json`,
`renders-after-state.json` (слой запросов без компилятора), `renders-after.json` (итог: слой + компилятор).

- **renders** — сколько раз отрендерились компоненты за действие (монтирование тоже считается); **queries** — сколько
  запросов перечитано; **requests** — вызовов моковой базы; **result** — мс до видимого результата; **settled** — мс до
  последнего коммита. Задержка мока — случайные 150–400 мс на запрос, поэтому разница `result` в пределах ±150 мс — шум.

  не запросы; замечание clients.

| S5 оболочка читает стор | ✅ (сделал дизайн, r3) |
| S6 ключи без `businessId` | ✅ смягчено: смена персоны/сферы сбрасывает кэш; ключи чинят разделы |
| S7 ключи-склейки | не мешает: перечитывание не по ключам, а по прочитанному; массивы в ключах — всё равно правило §18 |
| S8 `?api=flaky` | не сделано: режим живёт в `src/demo/settings.ts` и демо-панели (не мои файлы); откат по снимку — сделан (№1) |
| №1 флаг «внутри запроса» + откат | ✅ `markRequest`, предупреждение о чтении вне `request()`, откат синхронной `fn` по снимку |
| №8 `request(fn, { permission })` | ✅ через `assertCan` ядра |

## 10. Ограничения (честно)

- Точность — по коллекции ядра и полю среза, не по записи: смена статуса одной записи будит все запросы, читавшие
  `core.bookings` (журнал дня, история клиента, окна). Их данные перечитываются, но неизменившиеся объекты не
  перерисовываются (structuralSharing + компилятор).
- `Object.keys(readArea('x'))` без чтения значений не делает зависимостей от полей — только от набора полей.
- Откат по снимку — только для синхронной функции `request()`.
- Время ответа в демо — это задержка мока (150–400 мс); ускорить его «по-настоящему» можно только оптимистичными правками
  и `prefetchApiQuery` в разделах.
