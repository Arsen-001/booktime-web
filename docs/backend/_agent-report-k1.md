**Главные выводы:**
1. **Человек один, ролей несколько.** Клиент, мастер салона и индивидуал — одна учётная запись с несколькими ролями в разных бизнесах. Только так запись в салоне закроет время дома (F-00-045), а администратор увидит «занято дома» без имени клиента (F-00-046). В моке это невозможно: у мастера в двух бизнесах два разных идентификатора.
2. **Двойную запись должна запрещать сама база.** Нужна отдельная таблица занятости человека, где база не даёт двум записям пересечься по времени. Сейчас проверка идёт в браузере и работает только внутри одной вкладки: два клиента с двух телефонов оба запишутся в одно окно.
3. **CRM клиенту не видна, потому что так устроен сервер, а не вёрстка.** Клиентские вызовы вообще не читают таблицы CRM. Клиент получает только список свободных окон, а не календарь. Телефоны маскируются в каждом ответе. Сейчас база всех салонов лежит в браузере у любого посетителя — это самый опасный пункт.
4. **Мок уже расходится с решениями ТЗ.** Это ошибки, а не просто «нет сервера»:
   - поздняя отмена ставит «не пришёл» ещё до визита;
   - счётчик неявок нигде не растёт, у всех клиентов 0;
   - запись из приложения всегда «ждёт подтверждения», даже у мастера с «записываю сразу»;
   - длительность «от–до» бронирует нижнюю границу;
   - выезд не требует подтверждения;
   - чёрный список не мешает записаться онлайн;
   - запас после услуги в виджете не учитывается;
   - монеты при отказе на проверке «возвращаются», но баланса монет нет вовсе.

   Список с файлами — в `07`, разделы 2–4. Задание разрешало писать только в `docs/backend/`, поэтому в `qa/measure/*` я эти замечания не заносил. Их стоит передать сборщикам разделов client, online и platform.
5. **В 12 разделах из 18 данных нет совсем:** notify, loyalty, finance, stock, payroll, staff, network, reports, integrations, settings, resources, services. Для них модель и API взяты из ТЗ Altegio один в один.
6. **Стек не выбран.** Я предлагаю свой сервер на PostgreSQL: продукт по сути связанные таблицы (записи, мастера, ресурсы, клиенты, деньги), и главный риск закрывается одним правилом базы. Firebase быстрее на старте и сам обновляет данные у всех в реальном времени, но защиту от двойной записи и отчёты там придётся строить вручную.
