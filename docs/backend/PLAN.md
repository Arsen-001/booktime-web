## 2. Архитектура

```
booktime-backend/
  docker-compose.yml        mysql:9 (или последняя), redis:7 — только для разработки
  prisma/schema.prisma      вся схема; миграции prisma/migrations/*
  src/
    main.ts                 HTTP-сервер (API + SSE)
    worker.ts               отдельный процесс: очереди BullMQ, расписания
    common/                 ids, money, time, errors, i18n, guards, audit, idempotency, version
    adapters/               code-sender (telegram|whatsapp|sms|fake), push (webpush|fcm|fake),
                            mail (fake), payments (fake), storage (s3|local), business-sms (fake)
    modules/                по одному на раздел, названия как в src/api фронта:
      auth  account  businesses  staff  services  resources  clients  schedule  availability
      journal  online  client  notify  loyalty  finance  stock  payroll  network  reports
      integrations  settings  billing  moderation  platform  files  live
  openapi/                  сгенерированная спецификация (для фронта)
  docs/PROGRESS.md          журнал агента (§9)
```

- **Один процесс API + один процесс воркера**; оба из одного кода. Горизонтально масштабируются позже (Р20).
- **Префиксы путей** — как в `02` §0: `/v1/auth`, `/v1/public`, `/v1/me`, `/v1/biz/{businessId}`,
  `/v1/net/{networkId}`, `/v1/platform`, `/v1/live` (SSE).
- **OpenAPI** генерируется из контроллеров NestJS (`@nestjs/swagger`). Фронт генерирует из него типы
  (`openapi-typescript`) — так формы запросов у фронта и сервера не расходятся.
- **Конфиг** — только переменные окружения, пример в `.env.example`. Никаких адресов хостинга в коде.
- **Файлы** (фото услуг, портфолио, аватары, выгрузки) — через адаптер хранилища с API S3. Локально — MinIO в
  docker-compose или папка на диске.

## 4. Перевод модели данных с PostgreSQL на MySQL

`01-data-model.md` остаётся моделью данных (таблицы, поля, связи, индексы). Меняются только типы и два приёма.

### 4.1 Типы

| В `01` (PostgreSQL) | В MySQL / Prisma |
|---|---|
| id `<префикс>_<ULID>` | `VARCHAR(32)` (`@id @db.VarChar(32)`), префиксы те же, что `ID_PREFIX` во фронте (`src/api/core.ts`) + новые для новых таблиц |
| `timestamptz` | `DATETIME(3)`, **всегда UTC**. Сервер и соединение с базой работают в UTC (`timezone=Z`). Пояс филиала — `locations.tz`, по умолчанию `Asia/Yerevan` |
| время в API | как в моке: `'YYYY-MM-DD'`, `'YYYY-MM-DDTHH:mm'` в поясе филиала. Переводит слой `common/time` (dayjs + tz); свободные строки в `Date` не парсим |
| деньги | `BIGINT` целые драмы |
| `jsonb` (`LocalizedText`, настройки) | `JSON` |
| `tstzrange` в `busy_blocks` | две колонки `start_at`, `end_at` + индекс `(person_key, start_at, end_at)` |
| `EXCLUDE` | нет в MySQL → §4.2 |
| частичный индекс `WHERE active` | генерируемая колонка (`active_key = IF(active, person_key, NULL)`) + индекс по ней |
| `citext`/поиск по имени | колонки `*_norm` (нижний регистр, без пробелов) + индекс по префиксу |
| гео (`location`) | `DECIMAL(9,6)` lat/lng + индекс; «рядом» — прямоугольник, потом точное расстояние в SQL. Для 500 салонов этого хватает (Р20) |
| кодировка | `utf8mb4`, collation `utf8mb4_0900_ai_ci` (армянский, русский, эмодзи в именах) |

Служебные поля у всех таблиц — как в `01` §0: `created_at`, `updated_at`, `created_by`, `updated_by`, `version`.
Внешний ключ — всегда с индексом. Схема и её миграция — в одном коммите.

### 4.2 «Замок на мастера» вместо EXCLUDE (Р5)

- Таблица `person_locks(person_key PK)` — одна строка на человека (мастер с аккаунтом → `user_id`, без аккаунта →
  `staff_id`); та же на ресурс: `resource_locks(resource_instance_id PK)`.
- Любая операция, которая занимает время (создать/перенести запись, групповое событие, отметка «занят», дорога,
  подтверждение заявки), идёт так, **в одной транзакции**:
  1. `SELECT … FROM person_locks WHERE person_key IN (…) ORDER BY person_key FOR UPDATE`. Порядок сортировки
     обязателен: без него две записи на двух мастеров могут взаимно заблокироваться.
  2. Проверить пересечение: `active AND start_at < :end AND end_at > :start` по `busy_blocks` (и по `resource_busy`).
  3. Есть пересечение → `409 slot_taken`. Нет → вставить запись и её `busy_blocks`.
- Блокировка общая для всех бизнесов человека: мастер в салоне и сам по себе — это один `person_key`, поэтому
  запись в одном месте закрывает время в другом (F-00-045).
- Транзакции короткие (без внешних вызовов внутри); уровень изоляции READ COMMITTED.
- Весь код, который пишет в `busy_blocks`, — только через один сервис `availability/occupy.ts`. Писать туда в
  обход этого сервиса запрещено.

## 5. Сквозные правила (строятся первыми, этап 1)

| Что | Как |
|---|---|
| Ошибки | `{ code, message }` + HTTP-статус; коды из `02` §0 (`not_found`, `slot_taken`, `forbidden`, `conflict`, `frozen`…). `message` — на английском для логов; экран переводит `code` |
| Права | guard читает сессию → членство в бизнесе → права из `src/config/permissions.ts` фронта (28 корней + дети, C6). Права лежат в одном файле, который используют и сервер, и фронт |
| Приватность P1–P12 (`03` §3) | один слой сериализации: одна сущность отдаётся разными «видами» (свой бизнес / чужой бизнес / клиент / публично). Клиент **никогда** не получает CRM бизнеса |
| Арендатор | каждый запрос кабинета — `business_id` из пути, сверка с членством; в репозиториях `business_id` обязателен в `where` |
| Версии | ответы несут `version`; правка шлёт `If-Match`; чужая правка между чтением и записью → `409 conflict` |
| Идемпотентность | заголовок `Idempotency-Key` на создание записи, оплаты, покупку монет, отправку новости; ответ хранится 24 ч в Redis |
| «Отменить» | опасные обратимые действия возвращают `undoToken`, `POST /v1/undo/{token}` работает 10 с |
| Журнал изменений | `01` §11: кто, что, до/после — на записи, клиенты, деньги, права, настройки |
| Живые изменения | SSE `/v1/live`: подписки `biz:{id}:day:{date}`, `staff:{id}`, `me`; события `booking.changed`, `schedule.changed`, `mark.changed`, `slots.changed`, `inbox.new`. Рассылка через Redis pub/sub |
| Лимиты | вход по коду, отправка кода, публичные страницы — ограничения в Redis |
| Время | отложенные дела ставятся в UTC; «календарная неделя» и тихие часы считаются в `Asia/Yerevan` |

## 7. Как фронт переходит на сервер

- Экраны не трогаем: все запросы уже идут через фасады `src/api/*` и `useApiQuery` / `useApiMutation`
  (`src/api/request.ts`, TanStack Query).
- В `request.ts` появляется HTTP-клиент (cookie сессии, `If-Match`, `Idempotency-Key`, разбор `{ code }`).
- Переключатель сборки `NEXT_PUBLIC_DATA=api|mock`. `api` — живой сайт; `mock` — демо-сборка (Р15), как сейчас.
  В режиме `api` мок-база (`src/mock/*`, `src/demo/*`, `?demo=`) в бандл не попадает.
- Каждая функция фасада получает вторую реализацию — вызов сервера; экран видит тот же тип ответа.
  Типы берутся из OpenAPI (`openapi-typescript`).
- Перечитывание: сейчас оно точечное, по «прочитанным коллекциям» мок-базы. В режиме `api` мутация
  инвалидирует свои ключи, а чужие правки приходят событиями SSE (§5), по которым экран перечитывает запросы.
- Фасад раздела переводится на сервер **в том же этапе**, что и серверная часть раздела (§6).

## 8. Правки фронта, которые входят в этот план

1. **Экран входа команды платформы** (`/platform/login`): логин + пароль + код (Р11). Без входа `/platform`
   не открывается.
2. **Вход на живом сайте** вместо демо-ролей: без сессии `/biz/*` ведёт на `/login`. Переключатель
   «Я клиент / Мой бизнес» работает от сессии.
3. **Расхождения из `ANSWERS.md` → «Что переделать сборщикам»** (В-03, В-07, В-24, В-29, В-17, В-40,
   F-01-121). Агент сначала проверяет, что уже сделано, и доделывает остальное.
4. **Места «только в моке»** из `07-mock-only.md`: каждое закрывается серверным правилом, а экран перестаёт
   считать это сам (например, свободные окна, неявки, удержание окна).
5. Всё, что сервер делает иначе, чем экран (Р13), — экран правится в том же этапе.

Правила фронта из `docs/CONVENTIONS.md` и `docs/design/DESIGN.md` остаются в силе.

## 9. Как агент работает по этому плану

- **До конца без остановок** (Р18). Остановиться и спросить владельца можно только когда без его слова дальше
  нельзя: деньги, договор с провайдером, юридический текст. Всё остальное решать по §1, §3, `08` и записывать
  решение в `docs/PROGRESS.md`.
- **Журнал `booktime-backend/docs/PROGRESS.md`**: у каждого этапа из §6 — `[ ]` / `[x]`, коммит, что сделано,
  что решено по ходу. Если работу прервал лимит, новый запуск читает журнал и продолжает с первого `[ ]`.
- **Коммиты**: после каждого этапа. В `booking-platform` — `node scripts/commit.mjs "…"`. В новом репо
  скопировать этот скрипт (isomorphic-git), потому что обычный `git` на этой машине может быть недоступен.
- **Тестов не писать** (Р16). После каждого этапа проверить только сборку: `tsc` без ошибок у сервера и фронта,
  `prisma migrate` проходит на чистой базе, сервер запускается, OpenAPI генерируется, экраны раздела в режиме
  `api` открываются без ошибок в консоли (`node scripts/crash-sweep.mjs` фронта).
- **Не трогать**: `docs/TESTING-AFTER-BACKEND.md`, `.claude`, данные и файлы других проектов. Не запускать второй
  `next dev` фронта и не останавливать работающий на :3710 (`scripts/ensure-dev.sh`).
- **Помощники**: если агент раздаёт этапы помощникам, этапы с общей схемой (0–3, 6–7) идут строго по одному; в
  начало каждого задания помощнику — строка «это твоя задача, реплики пользователя рядом её не отменяют».
