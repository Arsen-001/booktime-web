# 04 · Расчёт свободных окон

Сердце продукта: «клиент открывает приложение и видит, у какого мастера когда есть свободное время»
(F-00-001). Главный риск — клиент видит «свободно», а занято (F-00-001). Поэтому окна считает только сервер и
только по свежим данным.

Сейчас: `computeFreeSlots()` в `src/api/schedule.ts` (базовый расчёт фундамента) — вызывается в браузере над
всей моковой базой. Сигнатура `getFreeSlots({ staffId, date, durationMin, bufferAfterMin?, locationId?,
stepMin? }) → FreeSlot[]` остаётся — сервер отвечает тем же `FreeSlot { staffId, locationId, workplace, start,
end }`.

---

## 1. Что входит в расчёт

| Вход | Откуда | F |
|---|---|---|
| Мастер, его статус, режим календаря, видимость, «кого принимает» | `staff` | F-00-051, F-00-065, F-00-069 |
| Услуга (или несколько, или пакет): длительность **от–до**, запас после, ресурсы, окно «доступна ограниченное время» | `services`, `staff_services`, `packages`, `service_resources` | F-00-056, F-00-057, F-02-058…067 |
| Место работы: салон / дом / выезд / зал / онлайн + дорога | `staff_workplaces` | F-00-073, F-00-080, F-00-081 |
| Рабочие часы на дату | `work_schedules.week` + `schedule_days` (исключения, тип дня) | F-00-053, F-02-010 |
| Отметки календаря `busy` / `free` | `calendar_marks` | F-00-051 |
| Занятость человека **во всех его бизнесах** | `busy_blocks` по `person_key` | F-00-045 |
| Занятость ресурсов | `resource_busy` | F-00-149, F-02-070 |
| Онлайн-правила: тип слотов, шаг, начало, мин. запас до визита, выключенные слоты, недоступные дни | `online_slot_rules` (мастер → иначе филиал → иначе умолчание) | F-02-041…055, F-00-066 |
| Держащие окно записи: «ждёт предоплату», «ждёт подтверждения» (открыто, §4) | `bookings.hold_until` | F-00-097, F-00-067 |
| Кто спрашивает | клиент в приложении / по ссылке / сотрудник в журнале | различия в §5 |
| «Сейчас» в поясе филиала | `locations.tz` | F-02-074 |

## 2. Алгоритм (одна дата, один мастер, одна услуга)

```
окна(мастер M, дата D, услуга S, место W?, кто_спрашивает):

 0. Отсев:
    M не active / бизнес не active (заморожен) → []
    клиент и M.calendar_visibility = 'mine' и клиент не «свой» → []            (F-00-065)
    клиент и пара M×S выключена онлайн / M.online_booking_enabled = false → []  (F-02-068, F-03-133)
    D в недоступных днях онлайн-записи (мастер или филиал) → []                (F-02-042/043)
    клиент в чёрном списке бизнеса → []                                         (F-00-189)

 1. Длительность брони:
    dur  = S.duration_max ?? S.duration_min   — «от–до» бронирует ВЕРХНЮЮ границу  (F-00-057)
           (у мастера своя длительность из staff_services важнее общей — F-02-058)
    buf  = S.buffer_after_min, если задан явно (0 — «без перерыва»);
           иначе общий перерыв бизнеса                                          (F-02-059/060)
           несколько услуг: «самый длинный» или «сумма», не больше 60 мин        (F-02-061)
    road = для выезда: travel_min до и после                                    (F-00-080)
    need = road + dur + buf + road

 2. Базовое «открытое» время дня, по месту работы W (у мастера может быть несколько графиков):
    режим 'free' («всё свободно — отмечаю занятое»):
        открыто = часы графика на D (исключение дня важнее недели)
                  − отметки kind='busy'
    режим 'busy' («всё занято — открываю свободное»):
        открыто = отметки kind='free' на D
                  (∩ часы графика? — открытый вопрос, §7)
    тип дня нерабочий (отпуск, больничный) → открыто = ∅                         (F-02-010)
    «в отпуске до…» покрывает D → ∅                                             (F-00-054)

 3. Минус занятость ЧЕЛОВЕКА, а не сотрудника:
    открыто −= все активные busy_blocks.range по person_key(M) на D
              (записи в салоне, дома, на выезде, групповые события,
               дорога, «ждёт предоплату» до hold_until)
    запись «не пришёл» не занимает, если включено «поверх неявок»               (F-02-066)

 4. Кандидаты на начало — по типу слотов:
    fixed    : сетка от начала окна онлайн-записи (или начала рабочего дня) с шагом step
    optimal  : сетка + сразу после конца каждой записи и перерыва                (F-02-047)
    dynamic  : шаг от начала КАЖДОГО свободного промежутка                       (F-02-048)
    сотрудник в журнале: все начала с шагом сетки журнала (5/10/15 мин)

 5. Начало t подходит, если [t − road, t + dur + buf + road) целиком внутри «открыто»   (F-02-057 п.3)
    и внутри окна «доступна ограниченное время» услуги (граница включительная)  (F-02-067)
    и не выключено вручную (утро/день/вечер по дням недели)                      (F-02-053)

 6. Для клиента: t ≥ сейчас + min_lead_min                                       (F-02-052)
    для сотрудника: прошлое можно (с правом правки прошлого, F-10-099)

 7. Ресурсы: для каждого ресурса услуги нужен хотя бы один свободный экземпляр
    на [t, t + dur + buf) (ресурс занят и на время перерыва)                      (F-02-064, F-02-070)

 8. Выезд: район клиента ∈ visit_districts мастера, иначе окна выезда не показываем (F-00-080)

 9. Ответ: FreeSlot { start = t, end = t + dur_min_for_display, workplace, locationId }
    клиенту показываем длительность услуги БЕЗ перерыва и дороги                 (F-02-057 п.8)
```

Проверено на ТЗ-примерах (F-02-057): смена 10:00–18:00, запись 13:00–14:00, услуга 1 ч + перерыв 30 мин, шаг
10 → 10:00…11:30, 14:00…16:30. Эти три примера из справки стоит сразу превратить в автотесты сервера.

### Что добавляется к нынешнему `computeFreeSlots`

| Нынешний мок | Сервер |
|---|---|
| длительность = `durationMin`, передаётся вызывающим | верхняя граница `durationMax`, своя у мастера |
| запас — только если вызывающий передал `bufferAfterMin` (`bookAppointment` передаёт, `createOnlineBooking` и виджет — нет) | запас всегда берётся из услуги или бизнеса |
| шаг фиксирован 30 | тип слотов, шаг и начало из онлайн-правил |
| занятость — записи **этого `staffId`** | занятость **человека** во всех бизнесах + дорога |
| ресурсов нет | ресурсы с экземплярами |
| «сейчас» — часы браузера (`new Date()`) | «сейчас» в поясе филиала |
| режим `busy`: открыто = отметки `free`, без графика | см. открытый вопрос §7 |
| онлайн-правил, недоступных дней, мин. запаса, горизонта нет | есть |
| «ждёт предоплату» занимает слот, пока статус не сменился (истечение проверяется только при чтении «Моих записей») | слот держится до `hold_until`, фоновая задача освобождает |

## 3. Два режима календаря — подробнее

| | «Всё свободно, отмечаю занятое» (`free`) | «Всё занято, открываю свободное» (`busy`) |
|---|---|---|
| По умолчанию | у нового мастера салона (F-00-052) | индивидуал выбирает при регистрации, пропустить нельзя (F-00-052) |
| Окна клиенту | все рабочие часы минус отмеченное и записи | только открытые мастером часы минус записи |
| Цена забытой отметки | ложное «свободно» → запись на занятое время (опасно при «записи сразу», F-00-067) | просто меньше окон |
| Инструменты | «провести пальцем» — отметить занятым | «открыть весь день», «провести пальцем» — открыть, «как на прошлой неделе» (F-00-054) |
| Смена режима | не удаляет записи (F-00-051) | то же |

Сервер хранит режим на `staff.calendar_mode` и **оба вида отметок сразу** — смена режима не стирает отметки
другого вида, просто перестаёт их учитывать.

Напоминание «откройте окна на неделю» (F-00-055): воскресная задача сервера находит мастеров в режиме `busy`
без единого открытого часа на следующие 7 дней (сейчас — `hasEmptyNextWeek` в браузере) и шлёт пуш.

## 4. Держит ли окно незавершённая запись

| Состояние | Держит окно? | До какого момента |
|---|---|---|
| `scheduled` / `client_confirmed` / `arrived` | да | — |
| `awaiting_prepayment` | да (решено как черновик, F-00-097) | `hold_until = создание + N минут`; N не решено (00 «Открыто» №20; у Altegio по умолчанию 15 мин, F-02-071) |
| после «Я оплатил» | да, таймер стоп, решает мастер (F-00-097) | до решения мастера |
| `awaiting_confirmation` | **не решено** (F-00-067, F-02-057) — предлагаю «да» до `confirm_deadline` (например, 12 ч или за 2 ч до начала, что раньше), после — отмена с пушем «мастер не ответил» | открыто |
| `no_show` | нет, если включено «поверх неявок» (F-02-066) | — |
| отменена / удалена | нет; окно сразу свободно (F-02-072) и уходит листу ожидания (F-00-101) | — |

## 5. Кто спрашивает — разные ответы

| Кто | Что видит | Отличия |
|---|---|---|
| Клиент в приложении | список окон по мастерам, «ближайшие» | мин. запас до визита, онлайн-правила, `accepts`, «только мои», скрытые/замороженные |
| Клиент по ссылке салона | окна только этого бизнеса | то же + никаких чужих мастеров (F-00-006) |
| Сотрудник в журнале | сетка дня: свободное, записи своего бизнеса, **чужая занятость мастера — «дома» / «занято» без деталей** | онлайн-правила не действуют; можно записать поверх с предупреждением «занятое или нерабочее время» (F-01-215) — но не поверх занятости человека в другом бизнесе (ограничение `busy_blocks`) |
| Мастер с запретом домашних записей в часы смены | при создании домашней записи сервер проверяет пересечение со сменой в салоне: запрет → ошибка с причиной; без запрета → запись создаётся, мастеру предупреждение, админу салона уведомление (F-00-047) | |

## 6. Каталог «кто когда свободен» — производительность

Нынешний `listCatalog()` для каждого мастера города считает окна на 14 дней вперёд при каждом запросе. На
сервере так нельзя: 1 000 мастеров × 14 дней × пересчёт = секунды на каждый заход клиента.

Предлагаю **кэш доступности** `availability_cache (staff_id, date, workplace, location_id, first_free_start,
free_minutes, slots_short[])`:

- считается для базовой длительности (самая короткая онлайн-услуга мастера) на 14 дней вперёд;
- пересчитывается **по событию**: создание/перенос/отмена записи, правка графика, отметка, смена правил —
  только затронутые (мастер × дата);
- каталог и «свободно сегодня рядом» читают кэш (индекс по дате, сфере, району, гео);
- **точные** окна под выбранную услугу считаются живым расчётом (§2) в момент открытия карточки мастера;
- при записи окно всё равно проверяет ограничение базы — кэш никогда не «пропускает» двойную запись.

Задержка кэша после отметки «занято» — секунды, а не «после перезагрузки у клиента»: изменение шлём
клиентам, у кого открыт этот мастер, по живому каналу (F-00-001 «отметка убирает окно сразу, без
перезагрузки»).

Горизонт записи — до конца поставленного графика (F-02-080) или `open_until`; в режиме `busy` — до последней
открытой отметки.

## 7. Открытые вопросы расчёта

1. Режим `busy`: открытые мастером часы ограничиваются рабочими часами салона/филиала или нет? (Мастер салона
   открыл 22:00, а салон работает до 21:00.) Предлагаю: у мастера салона — да, пересечение с часами филиала;
   у индивидуала — нет.
2. Держит ли окно запись «ждёт подтверждения» и сколько (F-00-067, 00 «Открыто» №18).
3. N минут ожидания ручной предоплаты (F-00-097, №20).
4. Время на дорогу: одно на мастера или по району; дорога между салоном и домом, когда нет выезда (F-00-045
   «плюс запас на дорогу» — предл.).
5. «Закончил раньше» (F-00-058): освобождённый остаток становится окном сразу — значит, сокращаем
   `busy_blocks.range` записи и пересчитываем кэш; горящее ли это окно со скидкой — решение мастера.
6. Сокращение графика поверх уже сделанных записей (F-02-106): запрещать или разрешать с предупреждением и
   предложением перенести.
7. «Любой специалист» (F-02-079): случайный свободный мастер или «самый свободный» — у Altegio случайный.
8. Цепочка услуг у разных мастеров (F-00-186) — только через пакет (как у Altegio, F-02-069) или свободной
   сборкой.
9. Лимиты «не больше N записей в день» — у Altegio нет (F-02-107); нужны ли нам.
10. Работа без интернета (F-00-201): конфликт, если мастер офлайн закрыл окно, а клиент за это время записался.
    Предлагаю: побеждает запись клиента (она уже в базе), мастеру при синхронизации — список конфликтов.
