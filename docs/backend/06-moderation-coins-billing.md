# 06 · Модерация, монеты, подписка, промокоды, заморозка

Всё здесь — деньги и видимость для клиентов. Поэтому правило одно: **решает только сервер, в одной
транзакции**. Сейчас все эти правила живут в срезе `platform` и в браузере (`src/api/platform.ts`), монетного
баланса нет вовсе.

---

## 1. Модерация

### 1.1 Правила (решено)

| Правило | F |
|---|---|
| Всё новое (фото, услуга, текст, диплом, сторис) не видно клиентам до нашего одобрения | F-00-168 |
| Проверяем сами, руками, один проверяющий; уровней доверия, ИИ и нескольких входов нет (снято) | F-00-168, F-00-179 |
| Без проверки: сторис и горящие окна **из шаблона** и **уже одобренных** фото; одобренное фото повторно не проверяется (предл.) | F-00-169 |
| Фото салона, снятые нами на визите («Подключить салон»), — без проверки | F-00-171 |
| Мастер видит статус «на проверке / одобрено / отклонено» и причину из списка | F-00-170 |
| Отклонили платное → монеты назад (предл.) | F-00-170, F-00-027 |
| Жалоба клиента на контент попадает в ту же очередь | F-00-091 |

### 1.2 Состояния

```
         submit                approve
 (новое) ───────► pending ─────────────► approved ──► видно клиентам
                    │  reject(причина)
                    └──────────────────► rejected ──► не видно; платное → возврат монет
 шаблон / визит / повтор одобренного ──► auto ──────► видно сразу
 жалоба на approved ──► pending (reopened), материал остаётся виден? — открыто (предл.: скрывать до решения)
```

### 1.3 Как сервер держит «не видно до проверки»

- У каждого проверяемого объекта (`media`, `services`, тексты описаний, `diplomas`, `story_bookings`,
  `news_posts`) — колонка `moderation_status`. Клиентские и публичные маршруты читают **только** `approved`
  и `auto`. Это фильтр в запросе, а не в экране.
- Правка уже одобренного текста или замена фото = новая версия на проверке; **до одобрения клиенты видят
  прежнюю одобренную версию** (предл.; иначе мастер, поправивший опечатку, пропадает из каталога на день).
  Поэтому у текстовых полей две колонки: `*_published` (видно клиентам) и `*_draft` (на проверке).
- Новая услуга без одобрения в каталоге не видна, но **в журнале мастера работает сразу** — мастер может
  записать на неё клиента по телефону (вывод: проверка защищает витрину, а не работу).
- Сейчас `isVisibleToClients()` никто вне раздела platform не вызывает (`qa/requests/platform.md`) — в моке
  проверка ничего не скрывает.

### 1.4 API проверяющего

`GET /v1/platform/moderation?status=pending&kind=…` · `POST …/{id}/approve` · `POST …/{id}/reject
{reasonId, note}` · справочник причин `GET/PUT /v1/platform/reject-reasons`. Одобрение одним нажатием делает
материал видимым (F-00-179) — в той же транзакции меняется `moderation_status` объекта и сбрасывается кэш
каталога.

## 2. Монеты

### 2.1 Правила

| Правило | Статус | F |
|---|---|---|
| Монеты покупаются пакетами в веб-кабинете | решено (система монет); покупка в вебе — предл. | F-00-026 |
| Монеты не выводятся деньгами и не передаются другому бизнесу | предл. | F-00-026 |
| Монеты не смешиваются с деньгами клиентов | предл. | F-00-026 |
| Тратятся на: сторис вверху главной, место под фото сверх 6 | решено | F-00-027, F-00-086, F-00-159 |
| Ещё возможно: выше в поиске, место на главной, пуши сверх лимита новостей, выделить горящее окно | открыто | F-00-027, F-00-167 |
| Подарок монетами: первому в районе/сфере, по промокоду, за приведённый салон | предл. | F-00-026, F-00-181 |
| Отклонили на проверке → монеты назад | предл. | F-00-170 |

### 2.2 Хранение — только журнал движений

```
coin_entries(id, business_id, amount /* + пришло, − ушло */, kind, reason, ref_type, ref_id,
             idempotency_key, at, by)
баланс = SUM(amount) по business_id   (+ кэш balance в businesses, обновляется в той же транзакции)
```

| `kind` / `reason` | Когда |
|---|---|
| `purchase` | оплачен пакет монет (после подтверждения платёжного провайдера) |
| `spend` / `photoSlot`, `storyPlace`, `storyQueue`, … | покупка чего-то за монеты |
| `refund` / `moderationReject`, `storyCancelled` | отказ на проверке, отмена сторис до показа |
| `gift` / `firstAward`, `promo`, `referralSalon`, `manual` | подарки от нас |

- Списание: `SELECT … FOR UPDATE` строки баланса бизнеса → проверка `balance ≥ цена` → запись `spend` →
  создание покупки. Не хватает — `402 insufficient_coins` и экран «Пополнить» (не серой кнопкой).
- Возврат при отказе и сама смена статуса проверки — одна транзакция. Сейчас в моке запись о возврате
  (`coinEntries`) появляется, но **баланса, на который она ляжет, нет** (`qa/requests/platform.md`).
- Цена монеты, пакеты, цена места под фото и сторис — не решены (00 «Открыто» №7). Цены храним в таблице
  настроек платформы, а в `spend` пишем фактическую цену — изменение цен не переписывает историю.

### 2.3 Сторис за монеты (F-00-159…162)

| Правило | Статус |
|---|---|
| Видят **все** клиенты вверху главной (не только подписчики) | решено (поправка) |
| Фиксированное число мест на день; места заняты → очередь по более дорогой цене | решено |
| 5, 6 или 10 мест; на район или на город; места продаются по дням заранее; последние места дороже; без аукциона | предл.; сейчас настраивается в нашей панели (`StoryPlacesConfig`) |
| Кнопка «Записаться» прямо в окно; пометка «Реклама»; охват до оплаты; статистика просмотры → нажатия → записи | предл. |
| Проверка до показа, кроме сторис из шаблона и одобренных фото; отклонили — монеты назад | решено / предл. |

Сервер: `story_bookings(business_id, date, district?, mode place|queue, price_coins, status, media_id,
moderation_status)`. Покупка места — транзакция: проверить свободные места на дату (с блокировкой строки
дня), списать монеты, создать бронь. Показ на главной — выборка на сегодня по району клиента, порядок —
случайный для каждого клиента (F-00-161, предл.). Подсчёт просмотров и нажатий — на сервере (сейчас
`trackAdImpression`/`trackAdClick` пишут в браузере, их можно накрутить).

## 3. Подписка

### 3.1 Цена (решено, но цифры под вопросом — 00 «Открыто» №1)

| Кто | Формула | Пример |
|---|---|---|
| Индивидуал | 5 000 ֏/мес | 5 000 |
| Салон | 4 000 ֏ × max(число мастеров, 2) | 1 мастер → 8 000; 5 мастеров → 20 000 |
| Администраторы салона | первый бесплатно, каждый следующий +2 000 ֏/мес | 3 админа → +4 000 |
| Сеть | каждый филиал — отдельный салон со своим минимумом 2 мастера | филиалы по 3 и 1 мастеру → 12 000 + 8 000 |
| Мастер и в салоне, и сам | две независимые подписки; неоплата одной не замораживает другую | салон платит за него 4 000, он за себя — 5 000 |

**Кто считается мастером салона** (F-00-014, предл.): сотрудник со статусом `active`, у которого есть хотя бы
одна услуга **и** график в периоде; администратор без услуг — нет; владелец с услугами в расписании — да.
Бесплатный админ — на каждый филиал или один на сеть — открыто (00 «Открыто» №11).

**Когда число мест меняется в течение месяца** (предл.): плата за месяц фиксируется при списании по числу мест
на этот момент; добавленный мастер увеличивает **следующий** платёж (F-00-013 «добавление мастера меняет
сумму следующего платежа»); доплаты за неполный месяц нет. Отключённый администратор перестаёт считаться
со следующего платежа (F-00-016, предл.).

### 3.2 Сущности

```
subscriptions(business_id PK, status: trial_free|active|grace|frozen|cancelled|left,
              period_start, period_end, free_until?, autorenew bool default true,
              saved_card_id?, promo_redemption_id?, discount_until?, next_charge_at, next_amount)
subscription_charges(id, business_id, period_start, period_end, seats_masters, seats_admins,
                     base_amount, discount_pct, amount, status: pending|paid|failed|refunded,
                     provider, provider_payment_id, receipt_url?, attempted_at, paid_at)
saved_cards(id, business_id, provider, token, mask, expires)
free_period_grants(id, business_id, days, reason: visit|first|promo|manual, by, at, note)
```

### 3.3 Ход подписки во времени

```
 подключили на визите (F-00-176) ──► free_until = +30 дней (F-00-019); без визита — бесплатного месяца нет
 зарегистрировался сам ─────────────► сразу платить или ждать визита? — открыто (00 «Открыто» №4)

 за 7, 3, 1 день до period_end ─────► пуш + колокольчик владельцу (F-00-023)
 period_end, autorenew = on ────────► списание с сохранённой карты
        успех ──► новый период; чек/документ (вид — по ответу бухгалтера, F-00-025)
        неудача ─► status = grace, повтор списания раз в сутки, пуш «оплата не прошла»
 grace 3 дня (предл.) истёк ────────► status = frozen: бизнес скрыт из каталога, поиска и по ссылке (F-00-024)
 оплатил в frozen ──────────────────► status = active сразу, всё видно, данные на месте
 autorenew = off ───────────────────► в period_end сразу grace → frozen (без попыток списания)
```

Фоновые задачи сервера: ежедневно в 03:00 по Еревану — предупреждения, списания, переход в `grace` и
`frozen`; каждые 5 минут — повтор неудачных списаний по расписанию провайдера.

### 3.4 Что происходит при заморозке — открытые вопросы (00 «Открыто» №5)

| Вопрос | Предложение |
|---|---|
| Уже сделанные будущие записи | остаются в силе, клиенты получают напоминания — «записи не сгорают» (предл.) |
| Может ли мастер вести журнал в заморозке | только смотреть и отмечать «пришёл / не пришёл» по старым записям; новые — после оплаты |
| Что видит клиент по старой ссылке | «Мастер временно не принимает онлайн-записи» + «похожие мастера рядом» (предл., F-00-024) — **но** это противоречит F-00-006 «по ссылке салона — без соседей»; решить |
| Сколько храним данные замороженного | открыто |
| Индивидуал переходит в салон | оплаченные месяцы замораживаются и ждут (F-00-043, предл.): `subscriptions.paused_days_left` |

### 3.5 Оплата

Решено: только онлайн в веб-кабинете, без наличных на визите; карты ArCa, Visa, Mastercard, Idram, Telcell;
салону-фирме — счёт на оплату (F-00-022). Провайдер не выбран. Требования к провайдеру для сервера:
сохранение карты токеном (для автопродления), уведомление сервера о платеже (webhook) с подписью, возвраты
через API. Покупка монет в iPhone-приложении — через Apple с комиссией (по памяти, не проверено, F-00-026) —
поэтому монеты и подписка покупаются в вебе.

## 4. Промокоды

### 4.1 Правила

| Правило | Статус | F |
|---|---|---|
| Скидки на подписку — **только** промокодом; лестницы «для всех» нет | решено | F-00-020 |
| Промокод одноразовый | решено | F-00-020 |
| Вводится при регистрации; ввести позже нельзя | решено / вывод | F-00-020, F-00-035 |
| Раздаёт сам пользователь при обходе салонов | решено | F-00-020, F-00-178 |
| Скидка зависит от выбранного числа месяцев (ступени 10–25%) | ступени — открыто | F-00-020 |
| Годовая оплата = промокод 25% | упомянуто | F-00-152 |
| После скидочного срока — обычная цена помесячно | вывод, открыто | F-00-021 |
| Личный на салон, срок действия | открыто | 00 «Открыто» №2 |

### 4.2 Сущности и проверка

```
promo_codes(id, code UNIQUE ci, kind: discount|freeMonth, tiers jsonb [{months, percent}],
            free_days?, personal bool, issued_to jsonb?, valid_until?, revoked_at?, created_by, note)
promo_redemptions(id, promo_code_id UNIQUE, business_id, months, percent, redeemed_at)
```

- «Одноразовый» держит **уникальный индекс** `promo_redemptions.promo_code_id`: два салона с одним кодом в одну
  секунду — второй получает `promo_used`. Сейчас `redeemPromo` проверяет и пишет в срезе браузера — гонку не
  ловит.
- Код применяется только в запросе регистрации бизнеса (`POST /v1/biz` с `promoCode`) или первой оплаты
  подписки; отдельного маршрута «ввести промокод» у бизнеса нет.
- Скидка фиксируется в подписке (`discount_pct`, `discount_until = старт + months`), а не пересчитывается от
  кода: отзыв кода после применения скидку не отнимает (предл.).
- Ответы проверки: `notFound`, `used`, `expired`, `revoked`, `personal` — как в моке (`PromoCheck`).

## 5. Бесплатный месяц и награда «первому»

| Что | Правило | Сервер |
|---|---|---|
| Бесплатный месяц | только тем, к кому пользователь пришёл сам (подключение на визите) — 30 дней | `free_period_grants(reason=visit)` создаёт `finishConnect`; сейчас `grantFreeMonth` двигает `bizMeta.freeUntil` в срезе |
| Награда первому в районе или сфере | бесплатный месяц + монеты + значок «первый» (предл.); первому в новой сфере — значок и верх поиска (подтверждено) | `first_awards` + `free_period_grants(reason=first)` + `coin_entries(gift/firstAward)` одной транзакцией; значок — поле карточки мастера в каталоге (сейчас значок нигде не показывается, `qa/requests/platform.md`) |
| Новая сфера по заказу — подписка на год | год считается со дня, когда сфера готова; список согласуется заранее; первому — значок (подтверждено) | `sphere_requests(status, agreed_scope, ready_at)`; подписка стартует с `ready_at` |

## 6. Выгрузка при уходе и копии данных (F-00-183)

- Владелец выгружает клиентов и записи сам из кабинета (сейчас такого входа у владельца нет — только в нашей
  панели, `qa/requests/platform.md`). Формат — CSV/XLSX; телефоны полностью (это его база); каждая выгрузка —
  в `data_exports`.
- Копии: ежедневная копия базы целиком (средствами хостинга) + возможность выгрузить один бизнес целиком
  (все таблицы с его `business_id`) в архив по запросу. Нынешние «копии» в моке (`makeBackupCopy`) — только
  счётчики строк со случайным размером.
- Ушедший бизнес: `left_at`, выгрузка отдана (`data_handed_at`), срок хранения — открытый вопрос; по сроку —
  обезличивание клиентов (`03` P11).
