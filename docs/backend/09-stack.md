## Вариант А · Свой сервер на TypeScript + PostgreSQL

**Состав:** Node.js (NestJS или Fastify) · PostgreSQL · Redis (коды входа, пределы, очереди) · очередь задач
(BullMQ) · S3-совместимое хранилище для фото · WebSocket/SSE для живых изменений · FCM + APNs + Web Push ·
размещение — любой облачный хостинг с управляемой базой. Вариант «А-лайт»: тот же PostgreSQL, но
управляемый сервис с готовой авторизацией и живыми изменениями (например, Supabase) — меньше своего кода на
старте, та же модель данных.

| Плюсы | Минусы |
|---|---|
| Двойная запись запрещается **самой базой**: ограничение `EXCLUDE … tstzrange &&` на `busy_blocks` и `resource_busy` — ни один баг в коде её не пропустит | Больше своего кода на старте: вход, сессии, очереди, живой канал |
| Модель `01` ложится как есть: связи, внешние ключи, индексы, транзакции на деньги | Нужен кто-то, кто следит за сервером, копиями и обновлениями (или управляемые сервисы — дороже) |
| Отчёты, фильтры клиентов, зарплата — обычный SQL; конструктор «И/Или» транслируется в запрос | Живые изменения — своя подсистема (WebSocket), на Firebase это «из коробки» |
| Типы `src/domain/**` становятся общим пакетом для фронтенда и сервера — фасад `src/api/*` меняется на `fetch` без переделки экранов | Офлайн-работа мастера (F-00-201) — самим (локальная очередь изменений в приложении) |
| Строки с проверкой доступа (Row Level Security) можно включить в базе вторым рубежом к проверкам кода | |
| Нет привязки к одному поставщику; перенос — дамп базы | |
| Цена предсказуема: платим за сервер и базу, а не за каждое чтение каталога | |

## Вариант Б · Firebase (Firestore + Cloud Functions + Auth + FCM + Storage)

**Состав:** Firestore — документы по коллекциям (близко к нынешней форме мока: ядро + срезы) · Cloud Functions —
вся логика записи, окон, денег · Firebase Auth с собственными токенами (вход по коду WhatsApp/Telegram — своей
функцией, стандартный вход Firebase по телефону умеет только SMS) · FCM для пушей · Storage для фото · это
же предложено в `00` для мобильных приложений на RN + Expo.

| Плюсы | Минусы |
|---|---|
| Живые изменения «из коробки»: подписка на документ — окно исчезает у клиента сразу (F-00-001) | **Нет ограничения на пересечение интервалов.** Защиту от двойной записи держим сами: транзакция по документу «день мастера» (все занятия человека за дату в одном документе) — работает, но это договорённость кода, а не гарантия базы |
| Быстрый старт: вход, хранилище, пуши, хостинг — готовые | Сложные выборки (фильтры клиентов «И/Или», отчёты, P&L, зарплата) — неудобны: нужны заранее посчитанные агрегаты или выгрузка в BigQuery |
| Офлайн-режим в клиентских библиотеках (F-00-201) | Правила безопасности Firestore плохо выражают «маскировать телефон без права» — чтение CRM всё равно придётся пускать только через функции, и выигрыш «клиент читает базу сам» пропадает |
| Опыт уже есть (DirectLine) — меньше нового для команды | Цена растёт с числом чтений: каталог «кто когда свободен» читают все клиенты постоянно; нужен кэш |
| | Привязка к Google; перенос на другое решение — переписывание |
| | Занятость человека через два бизнеса и «занято дома без имени» — отдельная коллекция-проекция, которую функции поддерживают вручную |

## Сравнение по главным рискам

| Риск | А (PostgreSQL) | Б (Firebase) |
|---|---|---|
| Двойная запись | гарантия базы | транзакция по документу дня — надёжно при аккуратном коде |
| Утечка CRM клиенту | проверка в коде + RLS | всё через функции; прямое чтение Firestore клиентом закрыть |
| Отчёты и фильтры на больших базах | SQL | агрегаты / BigQuery |
| Живое обновление | своя подсистема | из коробки |
| Скорость первой версии | медленнее | быстрее |
| Цена при росте каталога | предсказуема | зависит от чтений |
| Вход по WhatsApp/Telegram | свой код (в обоих вариантах) | свой код + custom token |

**Моё предложение** (решает пользователь): вариант **А**, потому что продукт по сути реляционный (записи ×
мастера × ресурсы × клиенты × деньги), а главный риск — двойная запись — закрывается одной строкой в схеме
базы. Если важнее скорость запуска и опыт DirectLine — вариант **Б**, но тогда с первого дня: все записи
только через функции и документ «день человека» как единственное место проверки занятости.

Что **не** зависит от выбора (делается одинаково): вход по коду (`05`), права и маскировка (`03`), алгоритм
окон (`04`), очередь уведомлений (`05` §4), журнал изменений (`01` §11), подписка и монеты (`06`).
