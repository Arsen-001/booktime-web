потерялось: что хранить, какие вызовы, какие правила обязан держать сервер и что сейчас держится только на
моке. **Кода здесь нет, и выбор стека не сделан.**

Опора (снимок 25.09.2026): типы `src/domain/**`, срезы `src/mock/**`, фасад `src/api/**`, ТЗ
`booking-research/functional-map/` (у `00-our-decisions.md` приоритет; «Снято» не строим).

## Главные выводы

1. **Человек один — ролей много.** Клиент, мастер салона и индивидуал — один `user` с несколькими членствами
   `staff`. На этом держатся F-00-045 (запись в салоне закрывает время дома) и F-00-046 (админ видит
   «занято дома» без имени). В моке это невозможно: у мастера в двух бизнесах два разных `staffId`, и
   занятость считается по одному из них.
2. **Двойную запись должна запрещать база, а не код.** Проекция `busy_blocks` по человеку с ограничением на
   пересечение интервалов закрывает сразу F-00-045, F-00-092 «окно уже заняли» и гонку двух клиентов.
   Сейчас проверка идёт в браузере и работает только внутри одной вкладки.
3. **CRM клиенту не видна по устройству сервера, а не по вёрстке.** Клиентские маршруты вообще не читают
   таблицы CRM; клиенту календарь не отдаётся — только список свободных окон; телефоны маскируются в
   сериализаторе. Сейчас база всех салонов лежит в браузере любого посетителя — это первое, что уходит.
4. **Окна считает сервер, каталог читает кэш.** Точный расчёт — при открытии мастера; каталог «кто когда
   свободен» — из кэша доступности, который пересчитывается по событию (запись, отметка, график) и
   рассылается живым каналом.
5. **Деньги — журналом движений в одной транзакции.** Монеты — только `coin_entries`, баланс = сумма;
   промокод «одноразовый» держит уникальный индекс; возврат монет при отказе проверки — в той же транзакции,
   что и отказ. Сейчас у монет нет баланса вовсе.
6. **Мок уже расходится с решениями ТЗ** — это ошибки, а не только «нет сервера»: поздняя отмена ставит
   «не пришёл» до визита, счётчик неявок нигде не растёт; запись из приложения игнорирует «записываю сразу»;
   длительность «от–до» бронирует нижнюю границу; выезд не требует подтверждения; чёрный список не мешает
   онлайн-записи; запас после услуги в виджете не учитывается. Список — `07`, разделы 2–4.
7. **12 разделов из 18 не имеют данных совсем** (notify, loyalty, finance, stock, payroll, staff, network,
   reports, integrations, settings, resources, services) — для них модель и API взяты из ТЗ Altegio 1:1.
8. **Стек — выбран 27.09.2026 (PLAN.md Р1): вариант А, но на MySQL, не PostgreSQL** (запрет двойной записи —
   «замок на мастера», PLAN §4.2). Ниже — исходная запись до выбора: продукт реляционный, и главный риск закрывается
   ограничением базы. Firebase быстрее на старте и даёт живые изменения из коробки, но защиту от двойной
   записи и отчёты придётся строить руками.
